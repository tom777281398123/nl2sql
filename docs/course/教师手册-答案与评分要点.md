# 教师手册 · 思考题答案与扩展练习评分要点

> 本手册供**授课教师**使用，覆盖 9 讲的「思考题」参考答案与「扩展练习」评分要点。
> 答案为参考方向，鼓励学生给出有依据的不同见解——**评分重在“理由是否站得住”，而非答案是否与本手册一字不差**。
> 标注难度：⭐基础 / ⭐⭐进阶 / ⭐⭐⭐挑战。
>
> 使用建议：思考题可作课堂提问/小测；扩展练习按“是否完成 + 理解深度 + 工程规范”三档给分。

---

## 第 1 讲：项目概述与系统架构

### 思考题
**1. 为什么把“校验”和“执行”分成两个独立节点，而不是直接执行、出错再说？**
- 校验用 `EXPLAIN`，**不真正动数据**就能发现语法/表字段错误，代价低、无副作用。
- 分离后，校验失败可走“纠错”分支自我修复，再执行；若直接执行出错，错误处理逻辑会和执行耦合，且可能产生副作用（虽本项目限只读，但理念上要隔离“检查”和“动作”）。
- 体现“**先验证后执行**”的防御式设计。

**2. “过滤”节点裁掉必需的表会怎样？系统能自我恢复吗？**
- 会导致 `generate_sql` 缺少必要表/字段，生成的 SQL 引用不存在的对象 → `validate_sql` 失败 → 进 `correct_sql`。
- 但纠错节点拿到的上下文**仍然缺那张表**，所以大概率改不对——**当前系统无法从“过滤过度”中自我恢复**。
- 这正是第 6 讲扩展练习“过滤安全网”要解决的问题。好的回答应指出“纠错无法弥补上游信息缺失”。

**3. 向量索引与全文索引各擅长什么？为什么两种都要？**
- 向量（语义）：擅长**同义/近义**（“营收”≈“销售额”），对字段/指标召回友好；不擅长精确专名。
- 全文（关键词）：擅长**精确字面匹配**（取值“华东”），对取值召回友好；不擅长语义改写。
- 两者互补：字段/指标用语义、取值用关键词，覆盖不同召回需求。第 5 讲有对照实验印证。

### 扩展练习评分要点
- ⭐1/2：架构图方向正确、每节点“为什么需要”说得通即可；能列出“答不了的问题”并归因到“知识库无此表/指标”为佳。
- ⭐⭐3：对比有具体维度（架构/召回方式/可控性），不空泛。
- ⭐⭐4：能指出瓶颈在“逐关键词检索 + 召回规模/过滤 LLM 上下文”，2000 表时召回噪声和 token 成本上升。
- ⭐⭐⭐5（立项设想）：方向明确、改动层判断正确、预期效果可衡量 → 满分。这是大作业起点，应认真批阅并给反馈。

## 第 2 讲：开发环境与中间件编排

### 思考题
**1. `make clean` 为何保留 embedding 模型缓存？不保留会怎样？**
- 模型约 1.2G，重新准备耗时（且本项目离线，无法联网下载）。保留可让重建中间件秒级恢复 embedding。
- 不保留：每次 clean 后都要重新拷贝/挂载模型，否则 embedding 起不来、知识库无法构建。

**2. healthcheck 的 `start_period` 与 `interval` 区别？为何 ES 的 `start_period` 更长？**
- `start_period`：容器启动后的“宽限期”，期间检查失败**不计入**失败次数（避免启动慢被误判不健康）。
- `interval`：两次检查的间隔。
- ES 启动慢（JVM 起、可能装 IK 插件），需要更长宽限期。

**3. 删掉三者数据卷重启后，哪些能自动恢复、哪些要重建？**
- **能自动恢复**：MySQL 的库结构和示例数据——首次启动空卷会跑 `scripts/mysql/init/*.sql`。
- **需要重建**：Qdrant 向量、ES 取值索引、以及 meta 库里的元数据——这些靠 `build-kb` 灌入，删卷后必须重跑。
- 关键区分点：**“初始化脚本灌的” vs “build-kb 灌的”**。

### 扩展练习评分要点
- ⭐2（改回 repo-id 实验）：能复现“卡在 HF 下载”并说清离线价值即可。
- ⭐⭐3（verify 子命令）：脚本能跑通 5 项检查并汇总 pass/fail。
- ⭐⭐4（Kibana）：能起来并看到 ES 索引。
- ⭐⭐⭐5/6（异地复现/部署文档）：文档完整可复现（含模型文件处理）是关键，能让另一人照做成功 → 满分。

## 第 3 讲：工程基础设施

### 思考题
**1. 为何 `app_config` 可单例、session 不可？**
- `app_config` 是**只读配置**，无状态、线程/协程安全，单例无副作用。
- session 是**有状态的事务上下文**，多请求共享会导致事务串扰、对象状态污染、并发错误。

**2. `pool_pre_ping=True` 解决什么问题？不开会怎样？**
- 解决“连接池里的连接被数据库/网络中途断开（如 MySQL `wait_timeout`、防火墙）后仍被取用”的问题。
- 不开：取到失效连接 → 第一条语句报 `connection closed/gone away`，表现为偶发查询失败（尤其空闲后首个请求）。

**3. 能否让 `clients` 依赖 `repositories`？为什么不行？**
- 不行。依赖应单向向下（repositories → clients）。反向会造成**循环依赖**、破坏分层、降低可测试性与可替换性。

**4. 换 Qdrant 为 Milvus，需改哪几层？**
- 主要改 `clients`（连接管理）+ `repositories/qdrant`（检索实现）。
- 不需改：`entities`、`services`、`agent` 节点（它们依赖 repository 抽象而非具体实现）——前提是新 repository 保持相同方法签名。这正是分层的价值。

### 扩展练习评分要点
- ⭐1：能加配置块、能复现类型错误报错。
- ⭐⭐3（verify 方法）：仿 embedding 写法，`SELECT 1` 自检返回 bool。
- ⭐⭐⭐5（密钥环境化）：用 `${oc.env:...}` 或等价方式把密钥移出 YAML，且文档同步、Git 不含密钥 → 满分。这是真实项目必备的安全意识。

## 第 4 讲：元数据知识库（上）

### 思考题
**1. 为何字段类型/示例取值构建时现查、不写死配置？体现什么原则？**
- 它们是 dw 库的**既有事实**，写进配置会重复、易与真实库不一致（漂移）。现查保证一致性、降低维护成本。
- 原则：**单一事实来源（Single Source of Truth）**，不冗余已有数据。

**2. entity 和 ORM model 合并成一套行不行？分开的代价与收益？**
- 收益：领域对象（entity）干净可序列化（作 payload、JSON），ORM 绑定 DB 细节；分开可独立演化、便于测试、跨层传递安全。
- 代价：多一套类 + mapper 转换代码，样板增多。
- 小项目可合并，但本项目要把对象塞进 Qdrant payload、跨层流动，分开更合理。

**3. `column_metric` 多对多桥表 vs “在 metric_info 存字段列表字符串”？**
- 桥表：规范、可双向查询（按字段查指标 / 按指标查字段）、可加关联属性、可加约束。
- 存字符串：简单，但查询不便、无法用 SQL join、易脏数据。
- 多对多关系正确建模应用桥表。

### 扩展练习评分要点
- ⭐2（ER 图）：主外键、多对多标注正确。
- ⭐⭐4（百万取值 sync）：能指出“索引膨胀、构建慢、召回噪声、ES 压力”，并提出取舍（如只 sync 基数低的维度、或取 top-N）。
- ⭐⭐⭐5（知识库扩域）：建表+灌数+配置完整，能问出 5 个有意义问题 → 满分。直接对接第 9 讲扩域大作业。

## 第 5 讲：元数据知识库（下）

### 思考题
**1. 为何字段用向量、取值用全文？取值全部向量化的代价？**
- 字段需语义匹配（用户措辞多变）；取值需精确匹配且**量大**。
- 取值全部向量化：embedding 成本和存储暴涨、且精确值的语义检索反而不如关键词精准、阈值难调 → 得不偿失。

**2. `ensure_collection/ensure_index` 幂等的好处？对反复构建意味着什么？**
- 幂等 = 多次调用结果一致、不重复建。好处：构建脚本可安全反复运行、不报“已存在”错。
- 对反复构建：建索引这步安全；但注意**数据写入不是幂等的**，配合 `SYS_ISCLEAN_CONFIG=true` 的清空才能避免重复堆积。

**3. 同一字段多个 point，检索时如何去重？**
- 在 `recall_column` 里用 `retrieved_columns_map`（按 `payload.id` 去重）——多个 point 命中同一字段 id 只保留一份。

**4. 新增大量同义词：加 alias 还是换 embedding 模型？**
- 少量、明确的业务同义词 → 加 alias（精准、可控、成本低）。
- 大范围语义泛化能力不足 → 考虑更强 embedding 模型（成本高、影响全局，需评测）。
- 一般**先加 alias，再考虑换模型**，并用第 5 讲评测集量化收益。

### 扩展练习评分要点
- ⭐1（阈值实验）：记录 0.4/0.6/0.8 下召回数量变化并解释 precision/recall 权衡。
- ⭐⭐4（ik_max_word vs ik_smart）：用 `_analyze` 给出分词对比并讨论影响。
- ⭐⭐⭐5（召回评测集）：金标准集 ≥15 条、Recall@K 计算正确、≥2 项改进且有前后对比数据 → 满分。第 9 讲评测大作业核心。

## 第 6 讲：问数智能体（上）

### 思考题
**1. 为何依赖放 Context 注入而非 import？对测试的影响？**
- 解耦：节点不绑定具体实例，运行时可注入不同实现。
- 测试：可注入 mock repository/embedding，**无需真连数据库**即可单测节点逻辑。

**2. 两个并行节点更新同一 key 会怎样？如何避免？**
- LangGraph 对并发更新同一 key 需要定义 reducer（合并函数），否则可能冲突/覆盖。
- 本项目避免方式：**各写各的 key**（retrieved_columns/values/metrics 互不重叠），fan-in 后由 merge 节点统一汇总。

**3. 两段式（高召回→高精度过滤）相比一步精确召回的优势？**
- 单步精确召回易“漏”（recall 低），漏了无法补救。
- 两段式：召回先保证“该有的都在”（高 recall），再用 LLM 理解语义裁噪（高 precision），更鲁棒，符合检索增强常见范式。

**4. merge 为何必须补主外键？不补会怎样？**
- 多表查询要 JOIN，JOIN 依赖主外键字段。若召回只命中度量/维度字段而没召回键，大模型无法正确关联表。
- 不补：`generate_sql` 缺 join 键 → 生成错误 JOIN 或笛卡尔积 → 校验失败或结果错误。

### 扩展练习评分要点
- ⭐⭐3（批量向量化）：改成一次 `aembed_documents` 多关键词，有性能对比数据。
- ⭐⭐4（过滤安全网）：result 为空时回退保留全部召回表，逻辑正确。
- ⭐⭐⭐5（新增表级召回）：知识库建表向量索引 + 新 repository + 新节点 + 正确接入 fan-out/fan-in → 满分。
- ⭐⭐⭐6（多轮预研）：State 扩展（history）方案合理，说清召回/生成如何用历史 → 满分。

## 第 7 讲：问数智能体（下）

### 思考题
**1. 为何用 `EXPLAIN` 校验而非真执行？能/不能发现哪些错误？**
- `EXPLAIN` 只做解析与查询规划，不返回数据、开销小、无副作用。
- 能发现：语法错误、表/字段不存在、类型不匹配等。
- 发现不了：**逻辑错误**（语法对但业务口径错，如该 SUM 写成 COUNT、该 join 的表没 join）——这类需要结果验证/评测才能发现。

**2. 节点忘了设置 `error` 会怎样？如何防御？**
- 路由函数读 `state["error"]`，若该 key 不存在会 KeyError；若是脏值会误判分支。
- 防御：State 给 `error` 默认值、或路由函数用 `state.get("error")` 容错、`validate_sql` 保证两条路径都显式 set。

**3. 给出错误信息为何能提高改对概率？与人改 bug 何其相似？**
- 错误信息把“哪里错、怎么错”定位出来，大模型据此**针对性**修改，而非盲猜。
- 与人改 bug 一致：有报错栈/信息时改得快且准，没有时只能瞎试。

**4. `execute_sql` 为何可只 writer 不 return？**
- 它是终点节点，结果通过**流式事件**（`type:result`）推给前端，不需要再写回 state 供下游使用——下游就是 END。

### 扩展练习评分要点
- ⭐⭐3（循环纠错）：改条件边 + 重试计数 + 上限保护，超限返回错误，逻辑正确无死循环。
- ⭐⭐4（few-shot）：prompt 加 2–3 个示例，复杂问题有改善案例。
- ⭐⭐⭐5（安全护栏节点）：用 sqlglot 等解析，确保只读/单语句/无危险函数/强制 LIMIT，正确接入图并能拦截危险 SQL → 满分。
- ⭐⭐⭐6（多候选自洽）：生成多条、分别校验、择优执行，有稳定性对比 → 满分。

## 第 8 讲：API 服务化与流式接口

### 思考题
**1. 为何长连接 lifespan 建、session Depends 建？session 单例会怎样？**
- 长连接（引擎/连接池/ES/Qdrant 客户端）建立成本高、无请求态，应启动建一次复用 → lifespan。
- session 有事务态、应短命每请求 → Depends + async with。
- session 单例：并发请求共享同一事务，状态串扰、并发异常、数据错乱。

**2. SSE 相比一次性返回，对体验和资源的影响？何时必须流式？**
- 体验：用户**立即看到进度**，无需干等（本项目链路含多次 LLM 调用，耗时秒级以上）。
- 资源：连接保持更久；但避免了“憋到最后一次性传大结果”。
- 必须流式：长耗时、分步骤产出、需实时反馈的场景（LLM 应用典型）。

**3. Depends 的 IoC 相比手动 new 的好处？**
- 自动装配依赖链、按请求管理生命周期（含自动关闭 session）、便于替换与测试（可 override 依赖）、路由代码只声明“要什么”不关心“怎么造”。

**4. 客户端中途断开，graph 还会继续跑吗？如何优雅处理？**
- 默认情况下，异步生成器在下次 `yield` 写入断开的连接时才会感知断开（抛异常），此前节点可能已执行。
- 优雅处理：检测断开（`request.is_disconnected()`）后取消任务、提前 break；或对 graph 执行加超时/取消机制。

### 扩展练习评分要点
- ⭐1（schema 校验）：query 非空/长度限制，非法返回 422。
- ⭐⭐3（耗时统计）：中间件记录请求耗时，落日志/响应头。
- ⭐⭐⭐5（会话管理）：session_id + 服务端历史 + 打通 graph State，会话隔离正确 → 满分（多轮对话大作业）。
- ⭐⭐⭐6（限流并发）：限流逻辑正确，有压测对比，能说清 LLM 应用为何尤需限流（成本/资源）→ 满分。

## 第 9 讲：前后端联调与课程设计

### 思考题（系统级，重在论证）
**1. 最影响准确率的环节？**
- 无标准答案。常见有理有据的回答：**召回+过滤**（喂错上下文则后续全错，garbage in garbage out）、或 **generate/纠错**（最终成文）。
- 评分看：是否用实验/案例支撑判断，而非空谈。引导学生用第 5 讲评测集做实验。

**2. 推向生产最需加固的三处？**
- 参考方向：① 召回规模化（千表时的分层召回/路由）；② 安全（只读护栏、权限、注入防护、敏感数据脱敏）；③ 性能与稳定（缓存、限流、并发、连接池调优、LLM 超时重试）。能讲出具体措施为佳。

**3. 大模型变强后，这套工程会被淘汰吗？**
- 开放题。优秀回答应辩证：模型变强会简化部分环节（如召回/纠错负担减轻），但**可控性、可审计、成本、私域知识约束**仍需工程；知识库/校验短期不会消失，形态可能演化。

**4. 迁移到另一领域（医疗/法律）复用什么、改什么？**
- 复用：知识库+多路召回+生成+校验+流式 的整体骨架，分层与 DI。
- 改：领域知识库内容、检索策略、领域 prompt/口径、合规与安全要求（医疗/法律更严）、可能不再是 SQL 而是检索/结构化输出。

### 大作业评分细则（40%）
| 维度 | 分值 | 满分要点 |
| --- | --- | --- |
| 代码 | 20% | 功能完整可运行、改动在正确的层、commit 清晰、无破坏原功能 |
| 报告 | 10% | 需求→方案→关键实现(贴改动代码)→测试效果(可量化)→不足，结构完整 |
| 答辩 | 10% | 能讲清“为什么这么做”、回答设计权衡、演示顺畅 |

**加分项**：效果有量化对比、考虑了边界/异常、工程规范（配置/日志/安全）、有自己的创新点。
**扣分项**：直接执行未约束的 SQL（除非就是做安全方向）、密钥入库、改坏原有链路、报告与代码不符。

## 附：课堂组织建议

1. **每讲开头**用上一讲的思考题做 5 分钟提问，检验理解、衔接。
2. **上机课**让学生两两结对，一人操作一人记录“坑”，课后汇总成班级“避坑清单”。
3. **第 1 讲就让学生选定大作业方向**，之后每讲的挑战题都为其积累，避免最后赶工。
4. **答辩**采用“演示 + 三问”：是什么、为什么这么做、还能怎么改进。
5. 鼓励学生在 GitHub 上以分支/PR 形式提交，体验真实协作流程。

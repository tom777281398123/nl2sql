# 专题：RAG 与检索系统全景设计

> 本文是课程的**横向拓展专题**。前面 9 讲讲透了「掌柜问数」这一个 NL2SQL 项目；本讲把视野拉开，把你在本项目里看到的检索做法，放进**主流 RAG 系统设计**的全景里，逐层对标、逐点展开优化细节。
>
> 阅读方式：每一节都先给「本项目怎么做的（带文件锚点）」，再讲「主流的完整做法有哪些选择、什么场景选什么」。你已经懂整体流程，本文重点补的是**每个点的设计空间与取舍**。

---

## 0. 先建立一张全景地图

一个"检索增强"系统，不管叫 RAG 还是 NL2SQL 还是 Agentic Search，骨架都是同一条链：

```
数据源 → 解析/清洗 → 切分(chunk) → 向量化/索引化 → 存储
                                                      ↓
用户 query → 查询理解/改写 → 召回(recall) → 融合 → 重排(rerank) → 上下文组装 → 生成 → 校验/引用
                                                      ↑____________ Agent 可在任意环节介入回路 ____________↑
```

**本项目在这张地图上的位置**（重要认知）：掌柜问数是一个**结构化元数据检索 + NL2SQL** 系统，它的"知识"不是长文档，而是数据库的 schema/指标/字段取值。所以：

- 它**没有 chunking**（元数据本来就是原子粒度的 entity）——见 [第 3 节](#3-切片chunking结构化数据免了但一般场景是重头戏)
- 它的"生成"不是答文本，而是**生成 SQL 再执行**——这是 RAG 的一个特化分支
- 它已经具备了主流 RAG 的多数关键部件：**多路召回、向量+全文混合、阈值过滤、LLM 精排、查询改写、纠错回路**

把它当"最小可用但五脏俱全"的参考实现，非常合适。下面逐层展开。

## 1. 数据处理：从原始数据到"可索引单元"

检索系统的天花板，很大程度由这一步决定。**Garbage in, garbage out** 在 RAG 里尤其致命——切错了、抽错了，后面 rerank 再强也救不回来。

### 1.1 本项目的数据处理

本项目的数据源是**人工编写的结构化 YAML**（`backend/conf/meta_config.yaml`），由 `build_meta_knowledge` 脚本读进来，写入三处存储。没有解析、没有清洗、没有切分——因为数据本身就是干净的结构化元数据。

这其实是一种**理想状态**：知识已经被人类专家结构化了。真实世界里，你更多面对的是下面这些"脏"数据源。

### 1.2 主流数据源与解析策略

| 数据类型 | 主流解析工具 | 关键难点 | 建议做法 |
|---|---|---|---|
| **纯文本 / Markdown** | 直接读 | 几乎没有 | 保留标题层级（后面切片要用） |
| **PDF（文本型）** | PyMuPDF(fitz)、pdfplumber、pypdf | 分栏、页眉页脚、跨页段落 | pdfplumber 提表格更强；fitz 快 |
| **PDF（扫描/图片型）** | OCR：PaddleOCR、Tesseract、云 OCR | 版面还原、公式、手写 | 版面分析(layout)优先，再 OCR |
| **PDF（复杂版面/学术）** | **专用版面模型**：Marker、Nougat、MinerU、Unstructured | 双栏、公式、图表标注 | 输出结构化 Markdown，效果远超裸文本抽取 |
| **Word (docx)** | python-docx、Unstructured | 样式=语义（标题级别） | 用样式名还原层级结构 |
| **Excel / CSV** | pandas、openpyxl | 表是二维语义，不能当纯文本 | 见 [第 6 节表格处理](#63-表格数据别当纯文本) |
| **HTML / 网页** | trafilatura、readability、BeautifulSoup | 去导航/广告/样板 | trafilatura 提正文最省心 |
| **PPT** | python-pptx | 每页要点分散、图多 | 每页当一个单元，图走多模态 |
| **图片（图文混合）** | 多模态模型 / OCR + caption | 图里的信息如何进检索 | 见 [第 6 节图文混合](#61-图文混合的三种主流范式) |
| **代码 / 结构化** | AST 解析、语言 parser | 按函数/类切，不按行 | tree-sitter 按语法单元切 |

**一个反复被低估的点：解析质量 > 模型选择。** 很多 RAG 效果差，根因是 PDF 抽出来的文本里，表格串行了、公式变乱码了、页眉页脚混进正文了。**在 2024 年后，"解析为结构化 Markdown"（保留标题/表格/列表）已成为高质量 RAG 的事实标准**——工具如 Unstructured、Marker、MinerU、LlamaParse 都是往这个方向做。

### 1.3 清洗与元数据抽取

解析完不是直接切，中间还有两件事常被跳过但很重要：

1. **清洗**：去重、去乱码、规范空白、剥离样板文字（页眉页脚、"版权所有"）。脏文本会污染 embedding。
2. **元数据抽取（metadata）**：给每个未来的 chunk 打上结构化标签——来源文件、页码、章节标题、时间、作者、文档类型、权限标签……

> **元数据是被低估的一等公民。** 它支撑三件事：①**过滤式检索**（先按 `department=finance AND year=2024` 缩小范围再向量搜，见 [4.4 元数据过滤](#44-元数据过滤先缩范围再相似度)）；②**引用溯源**（答案标注来自哪页）；③**权限控制**（多租户下只能搜到自己有权的文档）。
>
> 本项目其实也有元数据思想：ES 的 value 文档里存了 `column_id`（`value_es_repository.py`），Qdrant 的 payload 里存了整个 ColumnInfo。召回后能反查到"这个值属于哪个字段/哪张表"——这就是元数据在起作用。

## 2. Embedding：把语义变成向量

### 2.1 本项目的做法

- **模型**：`BAAI/bge-large-zh-v1.5`，1024 维，中文语义 embedding（`app_config.yaml:34`）
- **服务化**：不在 Python 进程里跑模型，而是用 HuggingFace **TEI**（Text Embeddings Inference）起一个独立服务，Python 端用 `HuggingFaceEndpointEmbeddings` 通过 HTTP 调用（`embedding_client_manager.py`）
- **批处理**：建库时 `aembed_documents(batch_size=10)`（`meta_knowledge_service.py`）

这套架构（**embedding 独立服务化 + 客户端 HTTP 调用**）是生产级做法，值得学：模型资源和业务进程解耦，可独立扩容、可换模型不动业务代码。

### 2.2 主流 embedding 的选型维度

| 维度 | 选择 | 说明 |
|---|---|---|
| **中/英/多语** | bge / m3e / gte（中文强）、OpenAI text-embedding-3、Cohere embed v3、E5 | 中文场景 bge 系列是稳妥默认 |
| **稠密 vs 稀疏** | 稠密(dense)：语义相似；稀疏(sparse, 如 SPLADE/BM25)：关键词精确 | 见 [4.3 混合检索](#43-混合检索densesparse-融合) |
| **对称 vs 非对称** | query-doc 是否同分布。检索是非对称的（短 query 找长 doc） | bge 有专门的 query 前缀指令，别忘了加 |
| **维度** | 384 / 768 / 1024 / 1536… | 维度↑精度↑但存储和计算↑；可用**降维/量化**权衡 |
| **上下文长度** | 512 / 8192 tokens | 长 chunk 需要长上下文 embedding，否则被截断 |
| **是否可微调** | 开源模型可用自己领域数据微调 | 垂直领域（医疗/法律）微调收益大 |

### 2.3 三个容易踩的 embedding 坑

1. **query 和 doc 用的模型/前缀必须一致。** bge 要求检索时给 query 加指令前缀（如 `为这个句子生成表示以用于检索相关文章：`），建库的 doc 不加。本项目因为 query 和 doc 都是短文本、且直接对称使用，简化处理了；一般 RAG 别省这一步。
2. **embedding 会随模型版本漂移。** 换了 embedding 模型，**全库必须重建索引**——新老向量不在同一空间，不能混用。本项目 `build_meta_knowledge --clean` 就是干这个的。
3. **归一化。** cosine 相似度要求向量归一化。用 dot product 度量时尤其要确认模型输出是否已归一化。

## 3. 切片（Chunking）：结构化数据免了，但一般场景是重头戏

### 3.1 本项目为什么没有切片

本项目的索引单元是**天然原子的 entity**：一个字段（column）、一个指标（metric）、一个字段取值（value）。粒度已经最细，无需切分。而且它有个精巧设计——

> **每个 entity 的 name / description / 每个 alias 都被单独 embedding 成独立向量**（`meta_knowledge_service.py:78-120`），共享同一份 payload。这样无论用户用官方名、口语别名还是描述性说法来问，都能命中同一个字段。
>
> 这其实是切片思想的一种变体：**"一个语义实体，多个检索入口"**。在通用 RAG 里对应的技术叫 **multi-representation / multi-vector indexing**（下面 3.4 会讲）。

### 3.2 为什么切片对长文档如此关键

两个硬约束逼你必须切：

1. **embedding 上下文窗口有限**——太长的文本塞不进去，或塞进去语义被"平均"稀释。
2. **检索精度**——chunk 太大，一个 chunk 里混了多个主题，向量成了"大杂烩"，query 匹配不准；chunk 太小，语义不完整，检索到了也没用。

**核心矛盾：chunk 大 → 上下文完整但检索不准；chunk 小 → 检索准但上下文碎。** 所有切片策略都在这条轴上找平衡。

### 3.3 主流切片策略光谱（从简单到高级）

| 策略 | 做法 | 适用 | 缺点 |
|---|---|---|---|
| **固定长度** | 按 token/字符数切，如 512 token | 通用兜底 | 会切断句子/语义 |
| **重叠窗口** | 相邻 chunk 重叠 10~20% | 缓解边界切断 | 冗余、有重复 |
| **按分隔符递归** | 段落→句子→词 逐级退让（LangChain RecursiveCharacterTextSplitter） | 通用默认之选 | 不理解语义 |
| **按结构** | 按 Markdown 标题 / 章节 / HTML 标签切 | 结构化文档（**首选**） | 依赖解析质量 |
| **语义切片(semantic)** | 用 embedding 找语义断点，相邻句相似度骤降处切 | 语义连贯性要求高 | 计算贵 |
| **命题化(proposition)** | LLM 把段落拆成独立"命题"句 | 高精度问答 | 贵、慢 |
| **代码切片** | 按函数/类（tree-sitter/AST） | 代码库 RAG | 需语言 parser |

**实践建议**：优先"**按结构切**"（尊重文档天然边界），在结构单元内再用"递归+重叠"控制长度。语义切片作为高要求场景的升级项。

### 3.4 高级索引结构（切片之上的一层）

普通切片是"一个 chunk 一个向量"。主流高级做法把**"用于检索的东西"和"用于生成的东西"解耦**：

- **Parent-Child / Small-to-Big**：用**小 chunk 检索**（准），但喂给 LLM 的是它所在的**大父块**（全）。鱼与熊掌兼得，非常常用。
- **Multi-representation（多表示）**：为每个 chunk 额外生成**摘要**或**假设性问题(HyDE 建库版)**，用这些去建向量索引，检索命中后返回原文。——**本项目的 name/description/alias 分别 embedding，正是这个思路的结构化版。**
- **Sentence-window**：检索粒度是单句，返回时带上前后 N 句的窗口。
- **层级索引 / RAPTOR**：对 chunk 递归聚类+摘要，形成"摘要树"，可在不同抽象层检索。适合超长文档、需要全局概览的问答。

> **对标记忆点**：你在本项目看到的"一个实体挂多个向量入口"，在通用 RAG 里是 multi-vector indexing 的一种。理解了这个映射，你就把本项目的一个具体技巧，升级成了一类通用模式。

## 4. 存储与召回：向量库、全文库、混合检索

这是你最想系统搞懂的部分，也是本项目做得最完整的部分。

### 4.1 本项目的三路召回

```
                    ┌─→ recall_column  → Qdrant 向量库 (data-agent-column)   topk=5, score≥0.6, COSINE
extract_keywords ───┼─→ recall_metric  → Qdrant 向量库 (data-agent-metric)   topk=5, score≥0.6, COSINE
                    └─→ recall_value   → Elasticsearch 全文库 (data-agent-value) topk=5, min_score≥0.6, IK分词+match(BM25)
                                            ↓
                                    merge_retrieved_info（去重 + 关联补全）
                                            ↓
                              filter_table / filter_metric（LLM 精排/剪枝）
```

- **向量路**（column/metric）：捕捉**语义相似**——"客户"能匹配到"顾客"、"会员"。
- **全文路**（value）：捕捉**精确关键词**——字段取值往往是专有名词/枚举值（"北京"、"已支付"），语义向量反而不如 BM25 精确匹配靠谱。

> **这个分工本身就是一堂课**：*不是所有东西都该用向量搜。* 高基数、强精确性的字面量（ID、枚举值、人名地名）用倒排索引/BM25 更准更快；概念性、语义性的内容才用向量。本项目让 value 走 ES、让 column/metric 走 Qdrant，是深思熟虑的存储分工。

### 4.2 向量数据库的核心机制（你必须懂的底层）

向量检索的本质是 **ANN（近似最近邻）**——在百万/十亿级向量里找最相似的 topk，精确算太慢，所以"近似"。

| 概念 | 说明 | 本项目 |
|---|---|---|
| **距离度量** | cosine（方向）、dot（含模长）、L2（欧氏） | COSINE（`column_qdrant_repository.py`） |
| **索引算法** | **HNSW**（图，主流默认，快+准）、IVF（倒排+聚类）、IVF-PQ（+量化省内存） | Qdrant 默认 HNSW |
| **量化** | PQ/SQ/二值量化，用精度换内存和速度 | 小库无需，大库必用 |
| **过滤** | 向量搜同时按 payload 元数据过滤（filtered search） | Qdrant 支持，本项目未大量使用 |

**主流向量库横向对比**（选型参考）：

| 库 | 定位 | 特点 |
|---|---|---|
| **Qdrant**（本项目） | 生产级独立服务 | Rust 写、filtered search 强、易部署 |
| **Milvus** | 大规模分布式 | 十亿级、云原生、组件多偏重 |
| **Weaviate** | 带混合检索+模块化 | 内置多模态、GraphQL |
| **pgvector** | Postgres 扩展 | 数据和向量同库，中小规模省心 |
| **FAISS** | 库不是服务 | Meta 出品、极快、需自己封装持久化 |
| **Elasticsearch/OpenSearch** | 全文+向量一体 | 一套系统做混合检索 |
| **Chroma / LanceDB** | 轻量、本地/嵌入式 | 原型、小项目 |

**选型心法**：小规模原型 → pgvector/Chroma；生产中等规模 → Qdrant/Weaviate；超大规模 → Milvus；已经在用 ES → 直接用 ES 的向量能力做混合检索。

### 4.3 混合检索（Dense + Sparse 融合）

**这是当前提升召回质量最"便宜"的一招，几乎所有严肃 RAG 都会做。**

- **Dense（稠密/向量）**：懂语义、抗同义词，但对精确关键词、罕见专名、数字/ID 弱。
- **Sparse（稀疏/BM25/SPLADE）**：精确关键词命中强，但不懂同义。
- **混合**：两路都召回，再融合。互补，召回率显著提升。

**融合算法**：最常用 **RRF（Reciprocal Rank Fusion）**——不依赖两路分数可比性，只看排名，`score = Σ 1/(k + rank_i)`，鲁棒且无需调权重。也可加权求和（需归一化两路分数）。

> **本项目的"类混合检索"**：它用 Qdrant(dense) 搜 column/metric，用 ES(sparse) 搜 value——这是一种**按数据类型分工的混合**，而不是"同一份数据两路搜再融合"。真正的混合检索是后者。想升级本项目，可以让 column 同时走向量和 BM25，再 RRF 融合——这是很好的课程设计延伸题。

### 4.4 元数据过滤：先缩范围，再相似度

大库场景的关键优化。与其在千万向量里全局搜，不如**先用元数据把候选集砍到几万**（`WHERE tenant_id=X AND year=2024 AND doc_type=report`），再在子集里做向量搜。

- **性能**：搜索空间小几个数量级。
- **正确性**：天然实现多租户隔离、权限控制、时效过滤。

Qdrant/Milvus/Weaviate 都支持 **filtered ANN search**（过滤和向量搜在一次查询里协同，而非搜完再过滤）。本项目数据量小没用到，但这是**大数据 RAG 的必备技能**。

### 4.5 查询理解与改写（召回前的功夫）

召回质量不只看索引，还看**你拿什么去搜**。本项目在这块其实做得不少：

1. **关键词抽取**：`extract_keywords` 用 jieba 分词+词性过滤，从口语问题里抽出实体词。
2. **LLM 关键词扩展**：三个 recall 节点各自用 LLM 把关键词**扩展/改写**后再检索（prompt `extend_keywords_for_*_recall`）——比如把"卖得最好的"扩成"销量、销售额、订单量"。

**主流查询改写技术全景**：

| 技术 | 做法 | 解决什么 |
|---|---|---|
| **同义词/关键词扩展** | LLM 或词典扩展查询词 | query 和 doc 用词不一致 |
| **Multi-query** | LLM 生成多个改写版 query，各自召回后合并 | 单一表述覆盖不全 |
| **HyDE** | 让 LLM 先"假想一个答案"，用假想答案去搜 | query 太短、和 doc 分布差异大 |
| **Query decomposition** | 复杂问题拆成子问题分别检索 | 多跳/复合问题 |
| **Step-back** | 先问一个更抽象的上位问题 | 需要背景知识铺垫 |
| **HyPE / 问题反向索引** | 建库时给 chunk 生成"它能回答的问题"，query 去匹配问题 | query-doc 语义鸿沟 |

> 本项目用了"关键词扩展"这一档。想加深理解，可以在本项目上实验 multi-query 或 HyDE，观察 recall 命中率变化。

## 5. Rerank（重排）：召回之后的精排

### 5.1 为什么召回之后还要重排

召回（recall）追求**高召回率**——宁可多召点，别漏。所以 topk 会取得比较宽（本项目 topk=5，大库常取 50~200）。但召回用的向量相似度是**双塔（bi-encoder）**——query 和 doc 分别编码再算距离，快，但精度有限。

**Rerank 用交叉编码器（cross-encoder）**——把 query 和每个候选 doc **拼在一起**送进模型，直接输出相关性分。精度高得多，但慢，所以只能对召回的少量候选做。

```
query → [召回 topk=100，快而糙] → [rerank 精排取 top5，慢而准] → 喂给 LLM
```

**这是"漏斗"架构：先粗筛保召回，再精排保精度。** 是提升最终质量最有效的单点优化之一。

### 5.2 主流 rerank 方案

| 类型 | 代表 | 说明 |
|---|---|---|
| **Cross-encoder 重排模型** | bge-reranker(中文强)、Cohere Rerank、Jina Reranker、mixedbread | 首选，几行代码接入，收益明显 |
| **LLM-as-reranker** | 让 LLM 对候选打分/排序 | 灵活、可解释，但贵、慢 |
| **RRF 融合** | 多路结果按排名融合 | 严格说是"融合"不是"重排"，但常放在这一层 |
| **MMR（最大边际相关）** | 兼顾相关性和多样性，去冗余 | 候选高度重复时用 |

### 5.3 本项目的"重排"在哪

本项目**没有 cross-encoder rerank**，但它有一个功能等价物：

> **`filter_table` / `filter_metric` 是 LLM-as-reranker 的一种。** 召回并 merge 后，把候选表/字段/指标连同用户问题一起交给 LLM，让它**选出真正需要的**（`filter_table.py`, `filter_metric.py`）。这本质是"上下文感知的精排/剪枝"——用 LLM 的理解力，从粗召回里挑出精准子集。
>
> 差别在于：经典 rerank 输出**分数排序**，本项目 filter 输出**选中集合**（硬过滤）。对 NL2SQL 场景，硬过滤更合适——你要么用这张表要么不用，不需要给表打分排序。

**升级方向（课程设计好题）**：在 recall 和 filter 之间插一个 bge-reranker，先把 topk=5 扩大到 topk=20 召回、rerank 到 top8、再交给 filter。观察 NL2SQL 准确率变化。

### 5.4 阈值与 topk 的设计

本项目：三路都是 `topk=5` + `score≥0.6`。这是两种截断的组合：

- **topk 截断**：最多要几个。
- **score 阈值**：低于分数的即使在 topk 内也不要（防止"矮子里拔将军"召回垃圾）。

**主流设计经验**：
- **召回阶段 topk 宜大**（几十到几百），把精排交给 rerank；**只有无 rerank 时才把 topk 压小**（本项目就是这种，直接靠 filter 兜底，所以 topk=5 合理）。
- **score 阈值要按数据实测**——0.6 在一个模型/数据上合适，换模型就得重标。cosine 的绝对值不同模型不可比。
- **有 rerank 时**：召回不设或松设阈值（保召回），阈值卡在 rerank 之后。

## 6. 特殊场景：大数据、图文混合、多模态

这是你特别想补的部分——"主流所有情况"。

### 6.1 图文混合的三种主流范式

文档里有图（图表、示意图、截图、扫描件），怎么让图里的信息可检索？

| 范式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 图转文（caption/OCR）** | 用多模态模型给图生成描述文字/OCR 出文字，把文字纳入文本索引 | 复用现有文本 RAG 管线，简单 | 丢信息，描述不全 |
| **② 多模态 embedding** | 用 CLIP/BGE-M3-visual/多模态模型，把图和文**编码到同一向量空间**，统一检索 | 图文同空间、跨模态检索（用文搜图） | 需多模态 embedding 基建 |
| **③ 多模态 LLM 直读** | 检索到相关页，把**页面图片**直接喂给多模态 LLM（GPT-4o/Claude）生成答案 | 保真、版面/图表信息不丢 | 贵、上下文占用大 |

**当前趋势**：②+③ 组合。用多模态 embedding 召回相关页 → 把页面图（而非抽取的文本）喂给多模态 LLM。这条路线（如 **ColPali** 直接对文档页面图做检索、不做 OCR）在复杂版面文档上效果突出，正在成为新主流。

### 6.2 表格数据：别当纯文本

Excel/PDF 里的表，二维语义（行列关系）一旦拉平成文本就毁了。主流做法：

- **表转 Markdown/HTML** 保留结构，整表或按行作为 chunk。
- **表 + 摘要双索引**：给每张表生成自然语言摘要（"这是各季度销售额表，含华北华东…"），用摘要建向量索引召回，命中后把**原始结构化表**喂给 LLM。
- **NL2SQL 路线**：如果表其实是数据库，**别做文本 RAG，直接 NL2SQL**——这正是本项目的路线。**认清"这个问题该用 RAG 还是 NL2SQL"本身就是一项关键判断力**：事实型/统计型/聚合型问题（"上季度华北销售额多少"）走 NL2SQL 精确计算；语义型/开放型问题（"这份合同有什么风险"）走文本 RAG。

### 6.3 大数据场景（百万~十亿级）的工程要点

小 demo 和大规模 RAG 是两个物种。规模上来后的关键变化：

1. **索引算法与量化**：HNSW 内存吃紧 → 上 **IVF-PQ / DiskANN**，用量化和磁盘索引换内存。精度略降换成本可控。
2. **元数据预过滤是刚需**（见 4.4）：不预过滤，十亿级全局搜又慢又不准。
3. **分片与分布式**：Milvus 这类分布式向量库，按 shard 水平扩展。
4. **分层存储**：热数据内存、冷数据磁盘/对象存储。
5. **离线批量建库**：embedding 是瓶颈，用 GPU 批量、异步、断点续建。本项目 `batch_size=10` 是玩具级；生产要 batch 几百 + 多进程/多卡。
6. **增量更新**：文档会变。要能**增量 upsert / 删除 / 重建单文档的向量**，而不是每次全量重建。本项目 `--clean` 全量重建只适合小库。
7. **缓存**：query 结果缓存、embedding 缓存，热点查询别重复算。
8. **监控与评估**：召回率、命中率、时延 P99、成本，要有 dashboard。

### 6.4 不同业务场景的设计取向

| 场景 | 侧重 | 典型设计 |
|---|---|---|
| **企业知识库/客服** | 准确+可溯源+权限 | 混合检索 + rerank + 元数据权限过滤 + 引用标注 |
| **法律/医疗** | 精确+可解释+防幻觉 | 领域微调 embedding + 强 rerank + 强制引用 + 人工兜底 |
| **代码助手** | 结构感知 | AST 切片 + 符号索引 + 仓库级图检索 |
| **多跳/研究型** | 推理链 | Agentic RAG + query 分解 + 迭代检索（见第 7 节） |
| **数据分析/BI** | 精确计算 | **NL2SQL（本项目）** / Text2API |
| **实时/新鲜度** | 时效 | 流式更新索引 + 时间衰减排序 |

## 7. Agent 介入：从"一次性 RAG"到"Agentic RAG"

### 7.1 传统 RAG 的天花板

经典 RAG 是**一条直线、一次检索**：query → 检索一次 → 生成。它的问题：

- 检索没命中就直接答错，没有"再试一次"的机会。
- 复杂问题（多跳、需要多轮信息）一次检索不够。
- 不能判断"我到底需不需要检索""检索到的够不够"。

### 7.2 本项目已经是"半个 Agent"

看 `graph.py` 的编排（LangGraph StateGraph），本项目**已经具备 agentic 的关键特征**：

```
generate_sql → validate_sql ──(有错)──→ correct_sql ──┐
                     │                                 │
                     └──(无错)────────→ execute_sql ←──┘
```

- **条件分支**：`validate_sql` 根据 `state["error"]` 走不同边（LangGraph 条件边）。
- **纠错回路**：SQL 校验失败 → 带着错误信息让 LLM 重新生成 → 这就是 **reflection（反思/自我修正）**，Agent 的核心模式之一。
- **状态机编排**：整个流程是一张有状态、有分支、有循环的图，而不是线性 pipeline。

**这已经超越了朴素 RAG**——它把"生成"变成了"生成→校验→纠错"的闭环。你可以把它当作 Agentic RAG 的一个具体实例来理解。

### 7.3 Agentic RAG 的主流模式

| 模式 | 机制 | 本项目对应 |
|---|---|---|
| **Routing（路由）** | Agent 判断走哪条检索路/要不要检索 | 三路 recall 并行（未做动态路由，可升级） |
| **Query planning（规划）** | 把复杂问题拆成子任务/子查询 | 关键词扩展算轻量版 |
| **Iterative retrieval（迭代检索）** | 检索→评估→不够再检索，多轮 | 未做（可升级：召回不足时二次检索） |
| **Reflection（反思自纠）** | 生成后自我校验、发现问题重做 | ✅ **validate→correct 回路** |
| **Tool use（工具调用）** | Agent 决定调哪个工具（SQL/搜索/计算器） | execute_sql 算工具执行 |
| **Self-RAG / CRAG** | 模型自己判断检索质量、决定是否重检索/纠正 | 部分对应校验回路 |
| **Multi-agent** | 多个专职 agent 协作（检索员/审校员/答题员） | filter/generate/validate 分工的雏形 |

### 7.4 从本项目升级到完整 Agentic RAG 的路线（学习实践建议）

1. **加迭代检索**：`filter_table` 若发现召回的表不足以回答问题，触发**二次召回**（放宽 topk 或换关键词），而不是硬着头皮生成。
2. **加检索质量自评（CRAG 思路）**：召回后让 LLM 判断"这些元数据够不够回答"，不够就改写 query 重召回。
3. **加路由**：先判断问题类型——是查数（走 NL2SQL）、是问概念（走文本 RAG）、还是闲聊（直接答）。
4. **加多轮对话记忆**：让"上一个问题问了华北，这个问题问'那华东呢'"能理解指代。
5. **纠错回路加上限与降级**：`correct_sql` 若连续失败 N 次，应降级为"我无法生成正确 SQL"而非无限循环——**生产级 Agent 必须有终止条件和 fallback**。

## 8. 评估：没有评估的 RAG 是盲目的

前面所有优化，怎么知道有没有效？**必须能量化。** 这是最常被跳过、却最重要的一环。

### 8.1 分层评估

| 层 | 指标 | 说明 |
|---|---|---|
| **检索层** | Recall@k、MRR、NDCG、命中率 | 该召回的召回了吗、排得靠前吗 |
| **生成层** | 忠实度(faithfulness)、答案相关性、无幻觉 | 答案是否基于检索内容、有没有编 |
| **端到端** | 正确率、人工评分、A/B | 用户视角对不对 |
| **NL2SQL 专属** | **执行准确率(EX)**、SQL 精确匹配(EM)、执行成功率 | 生成的 SQL 跑出来对不对 |

### 8.2 工具与方法

- **RAGAS、TruLens、DeepEval**：RAG 专用评估框架，能算 faithfulness/relevance 等。
- **LLM-as-judge**：用强模型给答案打分，规模化评估。
- **金标准集**：人工标一批 (问题, 正确答案/正确SQL) 作为回归测试集。
- **本项目建议**：建一个 `问题→期望SQL→期望结果` 的测试集，每次改 prompt/topk/阈值后跑一遍执行准确率——**这是把"我感觉变好了"变成"数据证明变好了"的唯一办法**。

## 9. 一页纸总览：本项目 vs 主流 RAG 全景

| 环节 | 本项目做法 | 主流完整设计 | 本项目可升级点 |
|---|---|---|---|
| **数据处理** | 人工结构化 YAML | 多格式解析→清洗→元数据抽取 | （场景不同，无需） |
| **切片** | 无（原子 entity） | 结构/语义/父子/多表示切片 | name/alias 多向量已是 multi-vector 雏形 |
| **Embedding** | bge-large-zh + TEI 服务化 | 多语/稀疏稠密/可微调 | query 前缀指令 |
| **存储** | Qdrant(向量) + ES(全文) 分工 | 向量库+全文库，或一体化 | 同数据双路+RRF 真混合检索 |
| **召回** | 三路并行, topk=5, 阈值0.6 | 混合检索+大 topk | 加 multi-query / HyDE |
| **查询改写** | jieba抽词 + LLM 扩展 | multi-query/HyDE/分解/step-back | 已有基础，可扩展 |
| **Rerank** | filter_table/metric（LLM硬过滤） | cross-encoder 精排 | 插 bge-reranker |
| **生成** | 生成 SQL | 生成答案/SQL/API | — |
| **Agent** | validate→correct 反思回路 | 路由/迭代/自评/多agent | 迭代检索、CRAG、路由 |
| **评估** | 无 | RAGAS/执行准确率/金标准集 | **建测试集测执行准确率** |

# 第 2 讲：开发环境与中间件编排

> 对应笔记：第 3 章「项目开发环境」、`docs/01-掌柜问数-启动文档.md`、`docs/02-掌柜问数-环境验证脚本.md`、根目录 `run.sh`
> 学时：4（理论 2 + 上机 2）

---

## 一、本讲要解决的问题

第 1 讲我们已经知道：掌柜问数不是“把问题直接丢给大模型”，而是先建设一套元数据知识库，再让智能体按步骤召回、生成、校验和执行 SQL。

本讲要把这套系统真正跑起来。重点不是背 Docker 命令，而是看懂一条启动命令背后的工程分工：

```sh
./run.sh start
```

这条命令会按顺序拉起：

1. 中间件层：MySQL、Elasticsearch、Kibana、Qdrant、Embedding。
2. 后端层：FastAPI 服务。
3. 前端层：Vite 页面。

其中 MySQL、Elasticsearch、Qdrant、Embedding 是 NL2SQL 主链路必须依赖的四个核心中间件；Kibana 是 Elasticsearch 的调试界面，用来观察 ES 索引，不直接参与问数链路。

学完本讲后，你应该能独立回答三个问题：

1. 这些服务分别做什么，为什么一个都不能少？
2. `Makefile`、`docker compose`、`run.sh` 分别负责哪一层封装？
3. 服务启动失败时，应该从哪个命令、哪个日志、哪个端口开始排查？

## 二、教学目标

1. 能用 `make middleware` 或 `./run.sh start` 拉起本项目开发环境。
2. 能说清 MySQL、Elasticsearch、Kibana、Qdrant、Embedding 在本项目中的职责。
3. 能区分“容器 Running”和“服务 Ready”，理解 healthcheck、`--wait`、HTTP 探活的作用。
4. 掌握 TEI 离线加载本地 embedding 模型的方法，并能判断 candle 回退日志是否正常。
5. 能用验证命令逐项检查环境：端口、服务健康、IK 分词、向量维度、MySQL 账号。
6. 能处理常见环境问题：端口冲突、Docker 未启动、模型目录缺失、初始化脚本未执行、数据卷被清空。
7. 能从项目代码中找到每个中间件的客户端管理器、repository，以及智能体节点里的调用位置。

## 三、教学重点

- `Makefile`、`docker/docker-compose-debug.yml`、`run.sh` 三者的分工。
- 四个核心中间件和一个调试界面的职责、端口、数据卷。
- TEI 本地模型挂载与 `MODEL_ID` 离线路径。
- 客户端管理器（clients）、仓储层（repositories）、智能体节点（agent nodes）如何共同使用中间件。
- 用“现象 -> 定位命令 -> 修复动作”的方式排查环境问题。

## 四、教学难点

- TEI 的模型加载规则：`MODEL_ID` 是 repo-id 时会联网下载，是本地路径时才离线加载。
- TEI cpu 镜像的 ORT 后端失败与 candle 后端回退：哪些日志是正常现象，哪些才是故障。
- MySQL 初始化脚本只在空数据卷首次启动时执行，旧数据卷不会重新跑初始化 SQL。
- 主机端口与容器端口的区别：本项目 MySQL 容器内是 `3306`，当前主机映射端口来自 `docker/.env.debug`，默认为 `3307`。

## 五、环境心智图

### 5.1 服务分工

| 服务 | 镜像 | 主机端口 | 数据目录 | 在本项目中的职责 |
| --- | --- | --- | --- | --- |
| MySQL | `mysql:8.0` | `3307 -> 3306` | `docker/data/mysql` | 同时承载 `dw` 真实数仓和 `meta` 元数据结构化表 |
| Elasticsearch | `elasticsearch:8.19.10` | `9200` | `docker/data/elasticsearch` | 存字段取值的全文索引，支持 IK 中文分词 |
| Kibana | `kibana:8.19.10` | `5601` | 容器内状态 | ES 调试界面，方便查看 `data-agent-value` 索引 |
| Qdrant | `qdrant:v1.16` | `6333` / `6334` | `docker/data/qdrant` | 存字段、指标的语义向量索引 |
| Embedding (TEI) | `text-embeddings-inference:cpu-1.8` | `8081 -> 80` | `docker/data/embedding` | 把中文文本转成 1024 维向量，供 Qdrant 检索使用 |

> 记忆方式：MySQL 存结构化元数据和示例数仓，ES 找“字面取值”，Qdrant 找“语义相似”，Embedding 负责把文本变成向量，Kibana 只是观察 ES 的窗口。

### 5.2 启动链路

```text
./run.sh start
    |
    |-- make middleware
    |     |
    |     |-- docker compose up -d --wait
    |     |-- MySQL / Elasticsearch / Kibana / Qdrant / Embedding
    |
    |-- wait_http http://localhost:8081/health
    |
    |-- uv run python -m backend.main
    |
    |-- npm run dev
```

`make middleware` 只负责中间件。`./run.sh start` 在它之上又补了三件事：等待 embedding HTTP 健康、启动后端、启动前端。

## 六、原理精讲

### 6.1 为什么不是一个数据库解决所有问题

掌柜问数的知识库需要处理三类完全不同的信息：

| 信息类型 | 示例 | 更适合的存储 |
| --- | --- | --- |
| 结构化元数据 | 表、字段、主外键、指标定义 | MySQL |
| 字段真实取值 | 华东、数码、会员客户 | Elasticsearch |
| 语义相似关系 | “营收”接近 `order_amount`，“地区”接近 `region_name` | Qdrant + Embedding |

如果只用 MySQL，语义相似能力弱；如果只用向量库，精确取值和结构化关系不好维护；如果只用 ES，业务口径、主外键、指标定义不够结构化。三类存储组合起来，才是第 1 讲里“给模型喂对、喂准、喂少”的物理基础。

### 6.2 Makefile 封装了 docker compose

`Makefile` 顶部把冗长的 compose 命令收成了一个变量：

```makefile
DOCKER_COMPOSE := PROJECT_ROOT=$(PROJECT_DIR) docker compose \
	-p $(COMPOSE_PROJECT_NAME) \
	-f docker/docker-compose-debug.yml \
	--env-file docker/.env.debug \
	--profile middleware
```

关键参数含义：

| 参数 | 作用 |
| --- | --- |
| `PROJECT_ROOT=$(PROJECT_DIR)` | 把项目根目录传给 compose，方便容器和脚本定位路径 |
| `-p storekeeper-nl2sql` | 设置 compose 项目名，影响容器、网络前缀 |
| `-f docker/docker-compose-debug.yml` | 指定本项目开发环境编排文件 |
| `--env-file docker/.env.debug` | 读取 MySQL 端口、账号、密码等变量 |
| `--profile middleware` | 只启动标记为 middleware profile 的服务 |

常用命令：

```sh
make middleware     # 启动中间件，并等待可等待的服务就绪
make ps             # 查看 compose 管理的容器状态
make logs           # 跟踪所有中间件日志
make down           # 停止中间件，不删除数据卷
make clean          # 停止并删除中间件数据卷，保留 embedding data 目录
```

课堂上优先使用 `./run.sh start`，因为它会继续启动后端和前端；只调试中间件时再用 `make middleware`。

### 6.3 Running 不等于 Ready

Docker 显示容器 `Up`，只代表进程启动了；服务可能还在初始化。例如：

- MySQL 正在创建数据库和导入初始化 SQL。
- Elasticsearch 正在启动 JVM、安装 IK 插件、恢复索引。
- TEI 正在加载 1.2G 的 embedding 模型并 warmup。

所以工程上要区分两个状态：

```text
容器 Running：进程在运行
服务 Ready：端口可访问，内部初始化完成，可以处理请求
```

compose 中 MySQL 的 healthcheck：

```yaml
healthcheck:
  test:
    [
      "CMD-SHELL",
      "mysqladmin ping -h 127.0.0.1 -uroot -p$${MYSQL_ROOT_PASSWORD} --silent",
    ]
  interval: 10s
  timeout: 5s
  retries: 30
  start_period: 30s
```

含义：

- `test`：真正执行的探测命令。
- `interval`：每隔多久检查一次。
- `timeout`：单次检查最多等多久。
- `retries`：连续失败多少次后判定不健康。
- `start_period`：启动宽限期，宽限期内失败不计入 retries。

`make middleware` 使用 `docker compose up -d --wait`，会等待具备 healthcheck 的服务进入健康状态。`run.sh` 又额外调用：

```sh
wait_http "http://localhost:8081/health" "Embedding 模型" 60
```

这是因为 embedding 模型加载慢，必须等它真正可以响应 HTTP 请求后，后端构建知识库和查询流程才稳定。

### 6.4 MySQL 初始化脚本只在空卷首次执行

compose 中 MySQL 挂载了两类目录：

```yaml
volumes:
  - ./data/mysql:/var/lib/mysql
  - ../scripts/mysql/init:/docker-entrypoint-initdb.d:ro
```

`/docker-entrypoint-initdb.d` 下的 SQL 只会在 `/var/lib/mysql` 是空目录时自动执行。它负责创建：

- `dw`：示例数据仓库。
- `meta`：元数据知识库结构化表。
- `storekeeper` 用户及对两个库的权限。

如果你改过初始化 SQL，但旧的 `docker/data/mysql` 还在，重启容器不会重新执行初始化脚本。需要重建时使用：

```sh
make clean
make middleware
```

注意：`make clean` 会删除 MySQL、ES、Qdrant 的数据卷。`dw` 示例数据可以由初始化脚本恢复，但 `meta` 库中的知识库数据、Qdrant 向量、ES 取值索引需要后续重新执行：

```sh
./run.sh build-kb
```

### 6.5 本项目最大的环境坑：TEI 离线加载

TEI 的 `MODEL_ID` 如果写成 HuggingFace repo-id，例如：

```text
BAAI/bge-large-zh-v1.5
```

启动时会访问 `huggingface.co` 下载模型。在网络受限或课堂机房环境里，这通常会卡住并反复重试，导致 embedding 一直不可用。

本项目采用本地离线加载。compose 中 embedding 配置如下：

```yaml
embedding:
  image: ghcr.io/huggingface/text-embeddings-inference:cpu-1.8
  platform: linux/amd64
  ports:
    - "8081:80"
  environment:
    MODEL_ID: /models/bge-large-zh-v1.5
    MAX_CONCURRENT_REQUESTS: "16"
    MAX_BATCH_TOKENS: "16384"
  volumes:
    - ./models/bge-large-zh-v1.5:/models/bge-large-zh-v1.5
    - ./data/embedding:/data
```

关键点：

1. `MODEL_ID` 必须是容器内本地路径：`/models/bge-large-zh-v1.5`。
2. 本机模型目录必须存在：`docker/models/bge-large-zh-v1.5`。
3. 目录里必须有 `pytorch_model.bin`、`config.json`、`tokenizer.json` 等模型文件。

检查模型是否就位：

```sh
ls -lh docker/models/bge-large-zh-v1.5/pytorch_model.bin
```

正常情况下，`pytorch_model.bin` 约 1.2G。如果目录不存在或文件很小，embedding 容器可能启动后仍然不可用。

### 6.6 ORT 失败不是一定错误：看是否回退到 candle

TEI cpu 镜像启动时通常会先尝试 ONNX Runtime。如果本地模型目录里没有 `model.onnx`，日志里可能出现：

```text
Could not start ORT backend: ... model.onnx does not exist
```

只看到这句不要立刻判定失败。继续往下看，如果出现类似日志：

```text
Starting Bert model on Cpu
Warming up model
```

说明 TEI 已经回退到 candle 后端，并开始加载 `pytorch_model.bin`。这在本项目里是正常现象。

快速查看关键日志：

```sh
docker logs storekeeper-embedding 2>&1 | grep -E "ORT backend|Bert model|Warming up|Ready"
```

判断标准：

| 日志现象 | 判断 |
| --- | --- |
| ORT backend 失败后出现 `Starting Bert model on Cpu` | 正常回退 |
| 出现 `Warming up model`，随后 `/health` 返回成功 | 正常 |
| 反复出现 `Download failed`、`huggingface.co` | 仍在联网下载，`MODEL_ID` 或挂载路径有问题 |
| 提示找不到模型文件，且没有 candle 加载日志 | 本地模型目录缺失或挂载错误 |

### 6.7 IK 中文分词器为什么重要

Elasticsearch 默认不适合中文分词。compose 的 elasticsearch 启动命令会自动安装 `analysis-ik`：

```yaml
command: >
  bash -c '
    if [ ! -d /usr/share/elasticsearch/plugins/analysis-ik ]; then
      elasticsearch-plugin install --batch https://get.infini.cloud/elasticsearch/analysis-ik/8.19.10;
    fi;
    exec /usr/local/bin/docker-entrypoint.sh eswrapper
  '
```

第 5 讲构建字段取值索引时会用到 `ik_max_word`。本讲先记住：ES 负责匹配真实取值，IK 决定中文文本能不能被切成有意义的词。

## 七、从代码看中间件怎么用

本节把“服务已经启动”继续往后推一步：项目代码到底怎么连接这些服务，怎么读写它们？

本项目的代码分四层使用中间件：

```text
配置层
backend/conf/app_config.yaml
        |
客户端管理器
backend/app/clients/*_client_manager.py
        |
仓储层 repository
backend/app/repositories/*
        |
服务/智能体节点
MetaKnowledgeService / QueryService / agent nodes
```

后端启动时，这些客户端统一在 FastAPI lifespan 中初始化，见 `backend/app/core/lifespan.py`：

```python
embedding_client_manager.init()
qdrant_client_manager.init()
es_client_manager.init()
meta_mysql_client_manager.init()
dw_mysql_client_manager.init()
```

应用关闭时，再关闭 Qdrant、ES、MySQL 这些连接型客户端。这正是第 3 讲会继续展开的“客户端生命周期管理”。

### 7.1 统一入口：配置怎么进入代码

所有中间件地址都先写在 `backend/conf/app_config.yaml`：

```yaml
db_meta:
  host: localhost
  port: 3307
  database: meta

db_dw:
  host: localhost
  port: 3307
  database: dw

qdrant:
  host: localhost
  port: 6333
  embedding_size: 1024

embedding:
  host: localhost
  port: 8081

es:
  host: localhost
  port: 9200
```

`backend/app/conf/app_config.py` 用 dataclass 定义配置结构，再用 OmegaConf 加载 YAML：

```python
schema = OmegaConf.structured(AppConfig)
app_config: AppConfig = OmegaConf.to_object(OmegaConf.merge(schema, context))
```

这意味着后续代码不用到处写 `localhost:6333`、`localhost:9200`，而是统一从 `app_config` 取。学生要掌握的点：**配置文件描述环境，代码只依赖配置对象**。

### 7.2 TEI 是什么，项目为什么要它

TEI 全称是 **Text Embeddings Inference**，可以把它理解成“专门提供 embedding 推理的 HTTP 服务”。它不负责聊天，也不生成 SQL，只做一件事：

```text
中文文本 -> 1024 维浮点向量
```

例如：

```text
"销售额" -> [0.012, -0.034, ...]  # 共 1024 个数
```

向量的意义是：语义相近的文本，在向量空间里距离更近。比如“营收”“销售额”“GMV”字面不完全一样，但向量可能相近。Qdrant 正是靠这种向量相似度做字段和指标召回。

本项目对 TEI 的使用有两层：

1. **环境层**：Docker 启动 TEI 服务，加载本地 `bge-large-zh-v1.5` 模型。
2. **代码层**：Python 通过 LangChain 的 `HuggingFaceEndpointEmbeddings` 调用 TEI HTTP 接口。

代码入口在 `backend/app/clients/embedding_client_manager.py`：

```python
def _get_url(self):
    return f"http://{self.config.host}:{self.config.port}"

def init(self):
    self.client = HuggingFaceEndpointEmbeddings(model=self._get_url())
```

注意这里的 `model` 不是模型名，而是 TEI 服务地址，例如 `http://localhost:8081`。LangChain 客户端会把 `embed_query`、`aembed_query`、`aembed_documents` 这些方法转成对 TEI 的 HTTP 调用。

在构建知识库时，`MetaKnowledgeService` 会批量向量化字段名、字段描述、字段别名：

```python
batch_embeddings = await self.embedding_client.aembed_documents(batch_embedding_texts)
```

在查询时，字段召回节点会把用户问题中的关键词向量化：

```python
embedding = await embedding_client.aembed_query(keyword)
payloads = await column_qdrant_repository.search(embedding)
```

所以 TEI 在本项目里不是“可选加速项”，而是 Qdrant 语义检索的前置能力。没有 TEI，字段召回和指标召回都无法正常工作。

学生要掌握的代码知识点：

| 知识点 | 在本项目中的体现 |
| --- | --- |
| embedding | 把文本变成 1024 维向量 |
| endpoint client | `HuggingFaceEndpointEmbeddings(model="http://localhost:8081")` |
| 单条向量化 | `aembed_query(keyword)` |
| 批量向量化 | `aembed_documents(texts)` |
| 离线模型 | compose 的 `MODEL_ID: /models/bge-large-zh-v1.5` |

#### TEI 操作演示：从文本到向量

演示目标：让学生亲眼看到 TEI 不是“聊天接口”，而是“文本进、向量出”的推理服务。

第一步，确认 TEI HTTP 服务就绪：

```sh
curl -i http://localhost:8081/health
```

预期：HTTP 状态码是 `200 OK`。TEI 的 `/health` 通常没有正文，`content-length: 0` 是正常现象。

第二步，调用 `/embed`，把一句中文变成向量：

```sh
curl -sS http://localhost:8081/embed \
  -H "Content-Type: application/json" \
  -d '{"inputs":"销售额"}' | jq '{dims:(.[0]|length), first5:(.[0][0:5])}'
```

预期输出形态：

```json
{
  "dims": 1024,
  "first5": [-0.038963895, -0.009481946, -0.009277513, -0.0025802443, 0.0012404367]
}
```

这里 `dims=1024` 说明模型把“销售额”编码成了 1024 维向量；`first5` 只是截取前 5 个数，避免课堂上打印整屏浮点数。

第三步，批量向量化多句话：

```sh
curl -sS http://localhost:8081/embed \
  -H "Content-Type: application/json" \
  -d '{"inputs":["销售额","营收","地区"]}' \
  | jq '{rows:length, dims:(.[0]|length), first5:(.[0][0:5])}'
```

预期输出形态：

```json
{
  "rows": 3,
  "dims": 1024,
  "first5": [-0.038963895, -0.009481946, -0.009277513, -0.0025802443, 0.0012404367]
}
```

`rows=3` 表示三条输入各得到一个向量；每个向量仍然是 1024 维。

第四步，算一个余弦相似度，直观看“语义接近”：

```sh
curl -sS http://localhost:8081/embed \
  -H "Content-Type: application/json" \
  -d '{"inputs":["销售额","营收","地区"]}' > /tmp/tei_vectors.json

node - <<'NODE'
const fs = require('fs');
const v = JSON.parse(fs.readFileSync('/tmp/tei_vectors.json', 'utf8'));
function dot(a, b) { return a.reduce((s, x, i) => s + x * b[i], 0); }
function norm(a) { return Math.sqrt(dot(a, a)); }
function cos(a, b) { return dot(a, b) / (norm(a) * norm(b)); }
console.log({
  "销售额 vs 营收": Number(cos(v[0], v[1]).toFixed(4)),
  "销售额 vs 地区": Number(cos(v[0], v[2]).toFixed(4)),
});
NODE
```

本机一次演示结果：

```json
{
  "销售额 vs 营收": 0.653,
  "销售额 vs 地区": 0.4146
}
```

这个结果说明：“销售额”和“营收”在向量空间里更接近，所以 Qdrant 用向量检索时，更容易把它们匹配到相同或相近的字段/指标。

如果宿主机访问 `localhost:8081` 不稳定，但容器显示已经 Ready，可以用容器内访问做兜底演示：

```sh
docker exec storekeeper-embedding curl -sS http://127.0.0.1:80/embed \
  -H "Content-Type: application/json" \
  -d '{"inputs":["销售额","营收","地区"]}' \
  | jq '{rows:length, dims:(.[0]|length), first5:(.[0][0:5])}'
```

这条命令绕过主机端口转发，直接访问 TEI 容器内部的 80 端口，适合排查“容器内服务正常，但宿主机端口访问异常”的情况。

### 7.3 MySQL：两个库，两种角色

MySQL 在本项目里不是一个库，而是两个库：

| 库 | 作用 | 代码中的访问 |
| --- | --- | --- |
| `dw` | 真实数仓示例数据，存 `dim_*`、`fact_order` | `dw_mysql_client_manager` / `DWMySQLRepository` |
| `meta` | 元数据知识库结构化部分，存表、字段、指标、字段指标关系 | `meta_mysql_client_manager` / `MetaMySQLRepository` |

客户端管理器在 `backend/app/clients/mysql_client_manager.py`：

```python
def _get_url(self):
    return f"mysql+asyncmy://{user}:{password}@{host}:{port}/{database}?charset=utf8mb4"

def init(self):
    self.engine = create_async_engine(..., pool_size=10, pool_pre_ping=True)
    self.session_factory = async_sessionmaker(...)
```

这里有三个必须讲清楚的工程点：

1. `mysql+asyncmy://` 表示使用异步 MySQL 驱动。
2. `engine` 是连接池，应该应用启动时建一次，关闭时释放。
3. `session` 是一次工作单元，应该每个请求新建，用完释放。

`dw` 库的 repository 会读取真实数仓结构和取值：

```python
async def get_column_types(self, table_name: str):
    sql = f"show columns from {table_name}"

async def get_column_values(self, table_name: str, column_name: str, limit: int):
    sql = f"select distinct {column_name} from {table_name} limit {limit}"
```

`meta` 库的 repository 会保存和读取元数据：

```python
async def save_table_infos(self, table_infos):
    self.session.add_all(models)

async def get_key_columns_by_table_id(self, table_id):
    select * from column_info
    where table_id = :table_id
    and role in ('primary_key', 'foreign_key')
```

这就是为什么第 1 讲反复强调 `dw` 和 `meta` 不能混：`dw` 是被查询的数据，`meta` 是帮助大模型理解 `dw` 的知识。

### 7.4 Qdrant：向量索引存什么，怎么查

Qdrant 是向量数据库。它存的不是普通 SQL 行，而是 point：

```text
point = id + vector + payload
```

在本项目中：

- `vector`：由 TEI 生成的 1024 维向量。
- `payload`：字段或指标的结构化信息，例如 `ColumnInfo`、`MetricInfo`。
- `collection`：一类向量的集合。

客户端管理器在 `backend/app/clients/qdrant_client_manager.py`：

```python
self.client = AsyncQdrantClient(url=self._get_url())
```

字段向量 repository 在 `backend/app/repositories/qdrant/column_qdrant_repository.py`：

```python
collection_name = 'data-agent-column'

await self.client.create_collection(
    collection_name,
    vectors_config=VectorParams(size=app_config.qdrant.embedding_size,
                                distance=Distance.COSINE)
)
```

这里的 `size=1024` 必须和 TEI 模型输出维度一致；`Distance.COSINE` 表示用余弦相似度判断语义接近程度。

写入时：

```python
PointStruct(id=id, vector=embedding, payload=asdict(payload))
await self.client.upsert(collection_name=self.collection_name, points=batch_points)
```

查询时：

```python
result = await self.client.query_points(
    collection_name=self.collection_name,
    query=embedding,
    score_threshold=0.6,
    limit=5
)
```

指标向量 repository 同理，只是 collection 名换成 `data-agent-metric`。

学生要掌握的代码知识点：

| 知识点 | 在本项目中的体现 |
| --- | --- |
| collection | `data-agent-column`、`data-agent-metric` |
| point | `id + vector + payload` |
| payload | `ColumnInfo` / `MetricInfo` 转成 dict |
| 向量维度 | `app_config.qdrant.embedding_size = 1024` |
| 相似度 | `Distance.COSINE`、`score_threshold=0.6` |

### 7.5 Elasticsearch：全文索引存什么，怎么查

Elasticsearch 在本项目里只做一个核心任务：**字段取值召回**。

比如用户问“华东地区销售额”，模型生成 SQL 时不能凭空猜数据库里到底叫“华东”“华东区”还是“华东大区”。所以系统要先从真实数仓取出字段取值，再把它们建进 ES：

```text
dim_region.region_name -> 广东省、浙江省、四川省...
dim_region.region_area -> 华南、华东、西南...
dim_product.category   -> 手机数码、家用电器...
```

客户端管理器在 `backend/app/clients/es_client_manager.py`：

```python
self.client = AsyncElasticsearch(hosts=[self._get_url()])
```

取值 repository 在 `backend/app/repositories/es/value_es_repository.py`：

```python
index_name = 'data-agent-value'
index_mappings = {
    "dynamic": False,
    "properties": {
        "id": {"type": "keyword"},
        "value": {"type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_max_word"},
        "column_id": {"type": "keyword"}
    }
}
```

这里要讲清三个 ES 概念：

1. `index`：类似一类文档的集合，本项目叫 `data-agent-value`。
2. `mapping`：字段类型定义，决定哪些字段分词、哪些字段精确匹配。
3. `analyzer`：分词器。`value` 用 `ik_max_word`，因为它存中文取值。

写入时，代码用 bulk 批量插入：

```python
operations.append({"index": {"_index": self.index_name, "_id": value_info.id}})
operations.append(asdict(value_info))
await self.client.bulk(operations=operations)
```

查询时，用 `match` 做全文检索：

```python
result = await self.client.search(
    index=self.index_name,
    query={"match": {"value": keyword}},
    min_score=score_threshold,
    size=limit
)
```

智能体的 `recall_value` 节点会对扩展后的关键词逐个查 ES：

```python
values = await value_es_repository.search(keyword)
```

所以 ES 和 Qdrant 的分工非常明确：Qdrant 解决“语义相似”，ES 解决“取值匹配”。

### 7.6 Kibana：代码不用它，但调试会用它

Kibana 不参与后端代码调用，所以在 `backend/app/clients/` 里没有 `kibana_client_manager.py`。它的价值是给人看的：

- 看 ES 是否真的有 `data-agent-value` 索引。
- 看字段取值文档是否写入成功。
- 调试 analyzer 和搜索结果。

课堂上可以这样定位 Kibana：

```text
后端代码 -> 访问 Elasticsearch
开发人员 -> 通过 Kibana 观察 Elasticsearch
```

所以 Kibana 是调试工具，不是业务依赖。生产系统可以没有 Kibana，但不能没有 Elasticsearch。

### 7.7 构建知识库时，四个核心中间件如何串起来

`./run.sh build-kb` 最终会执行：

```sh
uv run python -m backend.app.scripts.build_meta_knowledge --conf backend/conf/meta_config.yaml
```

构建过程在 `MetaKnowledgeService.build()` 里：

```text
1. 读 meta_config.yaml
2. 从 dw MySQL 读取表结构、字段类型、字段取值样例
3. 把表、字段、指标写入 meta MySQL
4. 用 TEI 把字段名/描述/别名向量化
5. 把字段向量写入 Qdrant: data-agent-column
6. 把字段真实取值写入 ES: data-agent-value
7. 用 TEI 把指标名/描述/别名向量化
8. 把指标向量写入 Qdrant: data-agent-metric
```

这条链路可以画成：

```text
meta_config.yaml
      |
      v
MySQL(dw) ----取字段类型/取值----+
                                |
                                v
                         MetaKnowledgeService
                                |
       +------------------------+-------------------------+
       |                        |                         |
       v                        v                         v
MySQL(meta)              TEI Embedding                  ES
表/字段/指标结构          文本 -> 向量                  字段取值全文索引
                                |
                                v
                             Qdrant
                         字段/指标向量索引
```

### 7.8 查询时，四个核心中间件如何配合

后端运行时，FastAPI 通过 `backend/app/api/dependencies.py` 把客户端和 repository 注入到 `QueryService`：

```python
return QueryService(
    embedding_client=embedding_client,
    column_qdrant_repository=column_qdrant_repository,
    value_es_repository=value_es_repository,
    metric_qdrant_repository=metric_qdrant_repository,
    meta_mysql_repository=meta_mysql_repository,
    dw_mysql_repository=dw_mysql_repository
)
```

`QueryService` 再把它们放进 `DataAgentContext`，交给 LangGraph 的各个节点：

```python
context = DataAgentContext(
    embedding_client=self.embedding_client,
    column_qdrant_repository=self.column_qdrant_repository,
    value_es_repository=self.value_es_repository,
    metric_qdrant_repository=self.metric_qdrant_repository,
    meta_mysql_repository=self.meta_mysql_repository,
    dw_mysql_repository=self.dw_mysql_repository
)
```

查询阶段的分工是：

| 节点 | 使用的中间件 | 做什么 |
| --- | --- | --- |
| `recall_column` | TEI + Qdrant | 关键词向量化，召回相关字段 |
| `recall_metric` | TEI + Qdrant | 关键词向量化，召回相关指标 |
| `recall_value` | Elasticsearch | 召回真实字段取值 |
| `merge_retrieved_info` / 后续节点 | MySQL(meta) | 补齐表、字段、主外键信息 |
| `validate_sql` / `execute_sql` | MySQL(dw) | `EXPLAIN` 校验 SQL，并执行最终 SQL |

这就是第 1 讲“多路召回”的真实代码落点：不是抽象概念，而是三个并行节点分别查不同的中间件。

## 八、代码精读：`run.sh`

`run.sh` 是给开发者和学生使用的“一键起停入口”。它把完整启动顺序写清楚了：

```sh
do_start() {
  start_middleware || return 1
  wait_http "http://localhost:8081/health" "Embedding 模型" 60 || return 1
  start_backend || return 1
  start_frontend || return 1
}
```

三点值得读懂：

1. **先中间件，后应用**：后端依赖 MySQL、ES、Qdrant、Embedding，不能反过来。
2. **单独等待 embedding**：模型 warmup 比普通端口监听更慢；现在等待失败会中止启动，避免后端带病运行。
3. **PID 与日志分离**：后端、前端是本机后台进程，PID 写入 `.run/`，日志写入 `logs/`。

常用命令：

```sh
./run.sh start              # 启动中间件 + 后端 + 前端
./run.sh stop               # 停止前端 + 后端 + 中间件
./run.sh restart            # 重启全部
./run.sh status             # 查看容器、进程、端口健康
./run.sh logs               # 跟踪后端和前端日志
./run.sh build-kb           # 构建元数据知识库，第 5 讲重点使用

./run.sh start middleware   # 只启动中间件
./run.sh start backend      # 只启动后端
./run.sh start frontend     # 只启动前端
```

## 十、排错手册

排错时不要反复重启。按下面顺序看证据：

```sh
./run.sh status
make ps
make logs
docker logs <容器名>
```

| 现象 | 优先定位命令 | 常见原因 | 修复动作 |
| --- | --- | --- | --- |
| `Docker 守护进程未运行` | `docker info` | Docker Desktop 没启动 | 先启动 Docker Desktop，再重跑命令 |
| MySQL 连不上 | `make ps`、`lsof -iTCP:3307` | 端口冲突或端口写错 | 以 `docker/.env.debug` 的 `MYSQL_PORT` 为准；必要时改端口后重启 |
| `SHOW DATABASES` 看不到 `meta` | `docker logs storekeeper-mysql` | 旧数据卷中初始化脚本没重新执行 | 确认可清数据后执行 `make clean && make middleware` |
| `make middleware` 一直等待 | `make logs` | 某个有 healthcheck 的服务不健康 | 看具体服务日志，不要盲目重启 |
| ES 起不来或反复退出 | `docker logs storekeeper-elasticsearch` | 内存不足、IK 下载失败、数据目录权限问题 | 给 Docker 分配更多内存；检查网络和 `docker/data/elasticsearch` |
| Qdrant 不可达 | `curl localhost:6333/healthz` | 容器未启动或端口被占用 | `make ps` 看状态；必要时检查 6333/6334 端口 |
| Embedding 不健康 | `docker logs storekeeper-embedding` | 模型目录缺失、挂载路径错、仍在联网下载 | 检查 `docker/models/bge-large-zh-v1.5/pytorch_model.bin`；确认 `MODEL_ID` 是本地路径 |
| 日志里有 ORT backend failed | `docker logs storekeeper-embedding` | 没有 ONNX 权重 | 如果随后出现 `Starting Bert model on Cpu` 和 `Warming up model`，这是正常回退 |
| 前端打不开 | `tail -f logs/frontend.out` | npm 依赖未安装、5173 被占用 | 看日志；必要时在 `fronted/` 下检查 npm 安装 |
| 后端打不开 | `tail -f logs/backend.out` | 配置、依赖、LLM 环境变量或中间件连接失败 | 先保证中间件健康，再看后端错误栈 |
| `make clean` 后问数失败 | `./run.sh build-kb` 输出 | Qdrant、ES、meta 数据被清空 | 重新执行 `./run.sh build-kb` |

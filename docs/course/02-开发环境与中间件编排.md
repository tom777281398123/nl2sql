# 第 2 讲：开发环境与中间件编排

> 对应笔记：第 3 章「项目开发环境」、`docs/00~02`、根目录 `run.sh`
> 学时：4（理论 2 + 上机 2）

---

## 一、教学目标

1. 能用 Docker Compose **一键拉起**四个中间件：MySQL、Elasticsearch、Qdrant、Embedding（TEI）。
2. 理解每个中间件在本项目中扮演的角色，以及它们的端口、健康检查、数据卷。
3. 掌握 **TEI 离线加载本地模型** 的方法（本项目的关键工程实践）。
4. 学会用 `run.sh` 起停整套系统，并用验证脚本逐项确认服务就绪。
5. 具备排查环境问题的能力（端口冲突、模型下载失败、容器不健康）。

## 二、教学重点

- `Makefile` + `docker/docker-compose-debug.yml` 的协作方式。
- 四个中间件各自的职责、端口、健康检查。
- Embedding 服务为什么要离线、怎么离线。

## 三、教学难点

- TEI（text-embeddings-inference）的模型加载机制：`MODEL_ID` 用 repo-id 会联网下载，用本地路径才离线。
- candle 后端 vs ONNX 后端的回退逻辑。
- 数据卷与初始化脚本的执行时机（只在首次启动空卷时跑）。

## 四、原理精讲

### 4.1 为什么要四个中间件

| 服务 | 镜像 | 端口 | 在本项目的职责 |
| --- | --- | --- | --- |
| **MySQL** | mysql:8.0 | 3306 | 存两类数据：`meta`（元数据知识库）+ `dw`（真实数仓） |
| **Elasticsearch** | elasticsearch:8.19.10 | 9200 | 字段**取值**的全文索引（带 IK 中文分词器） |
| **Qdrant** | qdrant:v1.16 | 6333/6334 | 字段、指标的**语义向量**索引 |
| **Embedding (TEI)** | text-embeddings-inference:cpu-1.8 | 8081 | 把文本转成 1024 维向量（`BAAI/bge-large-zh-v1.5`） |

> 这正是第 1 讲“元数据知识库”三索引（MySQL + Qdrant + ES）+ 向量化能力（Embedding）的物理载体。

### 4.2 Makefile 与 docker-compose 的协作

项目用 `Makefile` 封装冗长的 `docker compose` 命令。看 `Makefile` 顶部：

```makefile
DOCKER_COMPOSE := PROJECT_ROOT=$(PROJECT_DIR) docker compose \
	-p $(COMPOSE_PROJECT_NAME) \
	-f docker/docker-compose-debug.yml \
	--env-file docker/.env.debug \
	--profile middleware
```

关键点：
- `-p storekeeper-nl2sql`：项目名（容器、网络的前缀）。
- `-f docker/docker-compose-debug.yml`：编排文件。
- `--env-file docker/.env.debug`：注入 MySQL 账号密码等环境变量。
- `--profile middleware`：只启动带 `middleware` profile 的服务。

常用目标：`make middleware`（启动并等待健康）、`make down`、`make ps`、`make logs`、`make clean`（删容器和数据卷，但**保留 embedding 模型缓存**）。

### 4.3 健康检查（healthcheck）：为什么 `--wait` 能等到“真就绪”

看 compose 里 MySQL 的健康检查（`docker/docker-compose-debug.yml`）：

```yaml
healthcheck:
  test: ["CMD-SHELL", "mysqladmin ping ... --silent"]
  interval: 10s
  retries: 30
  start_period: 30s
```

`make middleware` 用了 `up -d --wait`，会一直等到所有服务 healthcheck 通过才返回。这避免了“容器起来了但服务还没准备好”导致的连接失败。

> 工程素养点：**区分“容器 Running”和“服务 Ready”**。前者只是进程起来了，后者才是能对外服务。

### 4.4 本项目最大的环境坑：Embedding 离线加载

TEI 的 `MODEL_ID` 默认填 HuggingFace repo-id（如 `BAAI/bge-large-zh-v1.5`），启动时会去 `huggingface.co` 下载模型。在国内/无外网环境，这会**一直卡住超时重试**。

本项目的解法（已写进 `CLAUDE.md`，并在 compose 中固化）：把模型放本地，`MODEL_ID` 填**容器内本地路径**。看 `docker/docker-compose-debug.yml` 的 embedding 段：

```yaml
embedding:
  image: ghcr.io/huggingface/text-embeddings-inference:cpu-1.8
  environment:
    MODEL_ID: /models/bge-large-zh-v1.5     # ← 本地路径，不是 repo-id
  volumes:
    - ./models/bge-large-zh-v1.5:/models/bge-large-zh-v1.5   # ← 把本地模型挂进容器
    - ./data/embedding:/data
```

模型文件（约 1.2G 的 `pytorch_model.bin` 等）来自 `2.资料/2.docker compose/embedding/bge-large-zh-v1.5`，拷到项目 `docker/models/` 下即可。

**candle 后端回退**：TEI cpu 镜像默认想用 ONNX 权重（`model.onnx`），本地模型只有 pytorch 权重。启动日志会先报 `Could not start ORT backend: ... model.onnx does not exist`，随后自动回退：

```
Starting Bert model on Cpu     ← candle 后端接管，加载 pytorch_model.bin
Warming up model
```

这是**正常现象**，不是错误。

### 4.5 IK 中文分词器的自动安装

ES 默认不带中文分词器。compose 里通过启动命令自动安装 `analysis-ik`（见 `docker/docker-compose-debug.yml` 的 elasticsearch `command` 段），这样取值的全文检索才能正确切分中文。第 5 讲会用到 `ik_max_word`。

## 五、代码精读

### 5.1 起停脚本 `run.sh`（项目根目录）

本项目提供了一键起停脚本，封装了“中间件 → 等 embedding 就绪 → 后端 → 前端”的完整顺序。核心片段：

```sh
do_start() {
  start_middleware || return 1
  wait_http "http://localhost:8081/health" "Embedding 模型" 60   # 等模型 warmup
  start_backend
  start_frontend
}
```

为什么要 `wait_http` 等 embedding？因为本地加载模型需要 warmup 时间，过早启动后端、构建知识库会因为 embedding 没就绪而失败。**这体现了 4.3 的“服务 Ready”理念。**

`run.sh` 用“PID 文件 + 端口探测”双重判活，PID 记在 `.run/`，日志在 `logs/`。常用：
```sh
./run.sh start | stop | restart | status | logs
./run.sh build-kb            # 构建知识库（第5讲用）
./run.sh start backend       # 只启某一层
```

## 六、环境与上机

### 上机任务 1：从零启动并验证
```sh
./run.sh stop           # 先停干净（若之前起过）
./run.sh start          # 全启
./run.sh status         # 看 5 项健康检查
```

### 上机任务 2：逐项手动验证（对照 `docs/02-掌柜问数-环境验证脚本.md`）
```sh
# Embedding：应返回 1024 维向量
curl -sS http://localhost:8081/embed -X POST \
  -H "Content-Type: application/json" -d '{"inputs":["测试"]}' | head -c 200

# ES：集群健康 + 验证 IK 分词
curl -sS http://localhost:9200/_cluster/health?pretty
curl -sS -X POST "http://localhost:9200/_analyze" -H "Content-Type: application/json" \
  -d '{"analyzer":"ik_max_word","text":"尚硅谷掌柜问数"}'

# Qdrant
curl -sS http://localhost:6333/healthz

# MySQL（业务账号）
mysql -h 127.0.0.1 -P 3306 -u storekeeper -p'178121' --protocol=TCP -e "SHOW DATABASES;"
```

### 上机任务 3：观察 embedding 离线加载日志
```sh
docker logs storekeeper-embedding 2>&1 | grep -E "ORT backend|Bert model|Warming up"
```
找到“ORT 失败 → candle 接管 → warmup”的三行，理解 4.4 的回退逻辑。

## 七、常见坑速查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 3306 端口冲突 | 本机已装 MySQL（如 brew）占用 | `lsof -iTCP:3306` 找到进程；停掉本机 MySQL 或改映射端口 |
| embedding 一直不健康、日志刷 `Download failed ... huggingface.co` | `MODEL_ID` 用了 repo-id，联网失败 | 改为本地路径并挂载模型（见 4.4） |
| `make middleware` 卡在 Waiting | 某服务 healthcheck 没过 | `make logs` 看哪个服务报错；ES 内存不足可调 `ES_JAVA_OPTS` |
| Docker 命令报 daemon 未运行 | Docker Desktop 没开 | 先启动 Docker Desktop |
| `make clean` 后查询报错 | 数据卷被清，知识库没了 | 重新 `./run.sh build-kb`（第5讲） |

## 八、扩展练习

### 基础级
1. 画一张表，列出四个中间件的「镜像 / 端口 / 数据卷 / 健康检查方式 / 在本项目的职责」。
2. 故意把 `MODEL_ID` 改回 `BAAI/bge-large-zh-v1.5`，重启 embedding，观察日志卡在哪、用了多久超时，再改回来。**体会离线加载的价值。**

### 进阶级
3. 为 `run.sh` 增加一个 `./run.sh verify` 子命令，自动跑完上机任务 2 的全部验证并汇总通过/失败。
4. 研究 `docker-compose-debug.yml` 里被注释掉的 Kibana 段，取消注释并启动，用 Kibana 可视化查看 ES 索引（第 5 讲建完索引后效果更佳）。

### 挑战级（指向课程设计）
5. 当前 embedding 用的是 CPU 镜像。调研 GPU 版 TEI（`text-embeddings-inference:1.x` GPU tag），写一份“如果学院有 GPU 服务器，如何把 embedding 切到 GPU 加速”的方案（含 compose 改动点、性能预期）。
6. 把整套中间件改造成「一条命令在另一台机器复现」：编写一份完整的部署文档 + 一个打包脚本（含模型文件的处理），让同学拿到后能离线复现你的环境。

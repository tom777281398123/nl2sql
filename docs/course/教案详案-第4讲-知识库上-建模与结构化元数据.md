## 一、本讲定位与教学法说明

- **性质**：开始建造“支柱一：元数据知识库”。本讲只到结构化部分（写 MySQL meta 库），向量/全文索引留第 5 讲。
- **核心矛盾**：学生（有数仓基础）会觉得“元数据不就是建几张表”。要让他们理解——**这层是大模型防幻觉的根，是“喂准”的来源**；并接受“同一份数据为什么要 entity/ORM/mapper 三套表示”这个看似啰嗦的设计。
- **必须钉死的认知**：
  1. **元数据知识库 = 约束大模型的“知识”**，不是可有可无的优化。
  2. **entity（领域对象）/ model（ORM）/ mapper（转换）三层分离**及其理由。
  3. **配置只写“描述”，类型/取值从 dw 库现查**（单一事实来源）。
- **教学法**：从“配置文件”这个学生能直接看懂的入口切入，再追到三套数据表示，最后看写库流程。**从配置倒推到代码**。
- **总时长**：4 学时（理论约 85 分钟 + 上机约 95 分钟）。

### 段落 1 · 什么是元数据知识库（12 min）

⏱ 0:06–0:18

> 钉死认知 1。

🗣 **讲稿**：
- “**元数据 = 描述数据的数据。**”先讲清楚和 dw 真实数据的区别（回收第 1/2 讲的高频混淆）。
- 本项目的元数据包含四类：表信息、字段信息、指标信息、字段取值。
- 它分别落到三个存储：MySQL（结构化）+ Qdrant（向量）+ ES（取值）。今天只碰 MySQL。

🗣 **讲“为什么是根”（口头禅式反问）**：
> “**没有这层会怎样？**——大模型不知道你有哪些表、字段叫什么、‘GMV’到底怎么算，只能瞎猜、编字段、口径乱来。有了这层真实元数据做约束，它才‘有据可依’。所以这层不是优化，是**地基中的地基**。”

✍ **板书（副板）**：
```
元数据 = 描述数据的数据 (≠dw真实数据)
四类: 表 / 字段 / 指标 / 取值
三存储: MySQL(结构化,今天) + Qdrant(向量) + ES(取值)  [后两个→第5讲]
作用: 给大模型"有据可依"的约束 → 防幻觉
```

### 段落 2 · meta 库四张表（12 min）

⏱ 0:18–0:30

🗣 **讲稿**：打开 `scripts/mysql/init/03-meta-schema.sql` 或 `backend/app/models/`，讲四张表的关系：
```
table_info      表的"目录"
  └─ column_info   字段(外键 table_id 指向 table_info)
metric_info     指标
  └─ column_metric 指标↔字段 多对多桥表
```
🗣 逐个一句话：
- `table_info`：一表一行。
- `column_info`：一字段一行，`table_id` 关联所属表。
- `metric_info`：一指标一行。
- `column_metric`：指标和它相关字段的**多对多**关联（一个指标可关联多字段，一个字段可服务多指标）。

❓ **提问（第 4 讲思考题 3，先埋）**：“指标和字段是多对多。能不能不要这张桥表，直接在 metric_info 里存一个‘字段列表字符串’？”（先抛，段落 5 或小结回答。）

✍ **板书（画四表关系）**：
```
table_info ──1:N──> column_info
metric_info ──N:M(column_metric)──> column_info
```

### 段落 3 · entity / model / mapper 三套表示（难点，22 min）

⏱ 0:30–0:52

> 本讲最难、最易被学生质疑“多此一举”的点。钉死认知 2，必须讲透“为什么值得”。

🗣 **抛认知冲突**：
> “同一个‘字段信息’，项目里居然有**三种形态**。第一次看会觉得啰嗦。但这是大厂代码的标配，听完你会服气。”

✍ **板书（三表示对照，副板）**：
```
同一个"字段信息"的三种形态:
 entity  backend/app/entities/column_info.py          领域对象(dataclass) 跨层传/作payload
 model   backend/app/models/column_info_mysql.py      ORM, 映射column_info表, 读写MySQL
 mapper  .../meta/mappers/column_info_mapper.py        entity ↔ model 互转
```

🗣 **讲透“为什么分”（核心，用反问）**：
> “**为什么不一套到底？**
> - ORM model 绑定数据库、带 SQLAlchemy 的‘魔法’（会话、惰性加载）。你把它到处传、塞进 Qdrant 当 payload、`json.dumps`——会出问题（脱离会话就报错、不可序列化）。
> - entity 是**纯数据对象**，干净、可序列化，适合在 service/agent 层自由流动，第 5 讲直接当 Qdrant payload 存进去。
> - mapper 把两者**解耦**：哪天数据库表结构变了，只改 model + mapper，**entity 和上层业务逻辑一行都不用动**。”

🗣 **打开三个文件对照看**（entity / model / mapper 各扫一眼，指出字段对应关系、mapper 的互转方法）。

🗣 **拔高**：“这叫‘**领域模型与持久化模型分离**’。它的回报在‘变化’时显现——表结构变、换数据库、对象要跨系统传，分离的设计让影响面最小。”

⚠ **预案**：学生反驳“小项目没必要”——**认同**：“对，写个一次性脚本确实没必要。但本项目要把对象塞进 Qdrant、跨层流动、还可能换存储——这时分离就值了。学会**判断何时该分、何时不该**，比无脑套用更重要。”

### 段落 4 · meta_config.yaml + role/alias/sync（18 min）

⏱ 0:52–1:10

> 钉死认知 3。这三个字段直接决定召回质量，是承上启下的关键。

🗣 **讲稿**：打开 `backend/conf/meta_config.yaml`，看一段：
```yaml
tables:
  - name: dim_region
    role: dim
    columns:
      - name: region_name
        role: dimension
        description: 订单所属的大区名称...
        alias: [地区, 区域, 大区]
        sync: true
metrics:
  - name: GMV
    relevant_columns: [fact_order.order_amount]
    alias: [成交总额, 订单总额]
```
对应 schema 在 `backend/app/conf/meta_config.py`（dataclass：ColumnConfig/TableConfig/MetricConfig/MetaConfig）。

🗣 **重点讲三个字段（逐个挂到下游影响）**：
1. **`role`**：表级 dim/fact，字段级 primary_key/foreign_key/dimension/measure。
   > “作用：让大模型知道**哪些能聚合（measure）、哪些能分组（dimension）、哪些能 join（键）**。第 6 讲 merge 补主外键，靠的就是 role。”
2. **`alias`（别名，最关键）**：
   > “用户问‘大区’，字段叫 `region_name`，**靠别名才能召回**。第 5 讲会把 name、description、每个 alias 都向量化入库——别名直接决定召回率。”
3. **`sync`（取值同步开关）**：
   > “是否把这列的**实际取值**灌进 ES 全文索引。地区、品牌这种维度开 true；主键、度量开 false（取值无检索意义、量还大）。”

❓ **提问**：“`customer_name` 这种可能有上百万个取值的字段，该不该 `sync: true`？”（引导：会让 ES 索引膨胀、召回噪声——取舍。留作思考。）

✍ **板书（重点）**：
```
meta_config.yaml = 知识库内容的"源头真相"
role:  dim/fact; pk/fk/dimension/measure → 告诉模型能聚合/分组/join
alias: 别名 → 召回率关键(name+desc+alias都建索引,第5讲)
sync:  该列取值是否进ES全文索引(维度开,主键/度量关)
```

### 段落 5 · 写库流程 + 小结（12 min）

⏱ 1:10–1:22

🗣 **讲稿**：入口 `backend/app/scripts/build_meta_knowledge.py` → `MetaKnowledgeService.build()`。本讲只看 `_save_tables_to_meta_db`（`backend/app/services/meta_knowledge_service.py`）：
```python
for table in meta_config.tables:
    column_types  = await self.dw_mysql_repository.get_column_types(table.name)      # 从dw现查类型
    for column in table.columns:
        column_values = await self.dw_mysql_repository.get_column_values(table.name, column.name, 10)  # 现查10个示例值
        column_info = ColumnInfo(id=f"{table.name}.{column.name}", type=column_types[column.name],
                                 examples=column_values, ...)
async with self.meta_mysql_repository.session.begin():     # 一个事务批量写
    await self.meta_mysql_repository.save_table_infos(table_infos)
    await self.meta_mysql_repository.save_column_infos(column_infos)
```
🗣 **两个讲点（钉死认知 3）**：
1. **配置只写“描述”，类型和示例取值从 dw 库现查**（口头禅）：
   > “**为什么不把类型、取值也写进配置？**——那是 dw 库已有的事实，写进配置就重复、还会和真实库不一致（漂移）。现查保证一致，这叫**单一事实来源**。配置只管它独有的‘描述、别名、role、sync’。”
2. **`session.begin()` 事务**：“批量写包在一个事务里——要么全成功，要么全回滚。”

🗣 **回答段落 2 的提问**：“桥表 vs 字符串列表？——桥表能双向查询、能 join、能加约束、不脏数据；字符串列表简单但查询难、易脏。多对多就该用桥表。”

🗣 **小结三句**：
1. 元数据知识库是治幻觉的根。
2. entity/model/mapper 分离，回报在“变化”时。
3. 配置只写描述，事实从 dw 现查（单一事实来源）。

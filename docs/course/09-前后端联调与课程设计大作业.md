## 四、原理精讲

### 4.1 前端工程

前端在 `fronted/`（注意拼写是 `fronted` 不是 `frontend`），Vue 3 + Vite：
```sh
cd fronted && npm install && npm run dev      # http://127.0.0.1:5173
```
或直接 `./run.sh start frontend`。

后端 CORS 白名单只放行 `localhost:5173` / `127.0.0.1:5173`（见 `backend/main.py`），所以前端必须跑在这个端口。

### 4.2 前端如何消费 SSE

前端向 `POST /api/query` 发请求，按 SSE 逐条读取 `data: {...}`，根据 `type` 分别处理：
- `progress`：更新进度条/步骤状态（running/success/error）——让用户看到“正在召回字段…”。
- `result`：拿到 `data`（结果行数组），渲染成表格。
- `error`：弹出错误提示。

这正是第 8 讲“事件协议”在前端的落地。建议学生打开浏览器开发者工具的 Network 面板，观察 `/api/query` 的 EventStream。

### 4.3 全链路回顾（把 9 讲串起来）

一次“统计各地区销售前三产品”的完整旅程：

```
前端输入(第9讲)
  → POST /api/query (第8讲: 路由+Depends装配QueryService)
    → lifespan 早已备好的长连接 + 每请求新session (第8讲/第3讲)
    → graph.astream + Context注入 (第8讲/第6讲)
      → extract_keywords: jieba (第6讲)
      → 并行召回: Qdrant向量(字段/指标) + ES全文(取值) (第6讲/第5讲)
          ← 知识库由 build-kb 预先构建 (第5讲/第4讲)
      → merge: 补主外键、并取值 (第6讲)
      → filter: LLM裁剪候选 (第6讲)
      → add_extra_context: 日期/方言 (第7讲)
      → generate_sql: LLM + prompt硬约束 (第7讲)
      → validate_sql: EXPLAIN → 条件边 (第7讲)
          → (失败) correct_sql: 喂错误重写 (第7讲)
      → execute_sql: dw库执行, writer推result (第7讲)
    → service包成 data:...\n\n SSE (第8讲)
  → 前端按type渲染进度与结果表 (第9讲)
全程: 配置/日志/异步/分层/依赖注入 作为地基 (第3讲)
环境: 4中间件由Compose编排, embedding离线加载 (第2讲)
为什么这么设计: 防幻觉/可控/省token (第1讲)
```

### 4.4 端到端 debug 方法论

查询出问题时，**自底向上**逐层排除：

| 层 | 怎么查 | 工具 |
| --- | --- | --- |
| 中间件 | 5 项健康检查 | `./run.sh status` |
| 知识库 | 三索引是否有数据 | 第 5 讲上机任务 2 |
| 智能体 | 命令行跑 graph，看哪个节点报错 | `python -m backend.app.agent.graph` |
| API | curl 打接口看 SSE | 第 8 讲上机任务 2 |
| 前端 | 浏览器 Network/Console | 开发者工具 |
| 日志 | 按 request_id 串起一次请求 | `logs/app_*.log` |

## 五、环境与上机

### 上机任务 1：完整联调
```sh
./run.sh start
./run.sh status          # 全绿
```
浏览器 http://127.0.0.1:5173 ，依次问：
- “统计一下各个地区销售排行前三的产品”
- “各品牌的成交总额是多少”
- “上个季度华东地区的订单数量”
观察进度流与结果表。

### 上机任务 2：故障演练
故意制造一个故障（如停掉 embedding：`./run.sh stop` 后只 `make middleware` 不构建知识库，或清空某索引），用 4.4 的方法论定位问题、修复，并写一段“故障定位报告”。

## 六、课程设计大作业（综合验收）

在掌柜问数基础上完成一项**可演示的功能增强**，并提交代码 + 报告 + 答辩。前面每一讲的“挑战级”练习都在为这些方向铺垫——现在把它做完整。

### 选题方向（任选其一，或自拟报教师批准）

| 方向 | 核心改动层 | 关联讲次 | 验收要点 |
| --- | --- | --- | --- |
| **① 结果可视化** | 前端 | 第 8、9 讲 | 根据结果自动选图（柱/折线/饼），合理映射维度/度量 |
| **② 多轮对话** | State + API + 召回/生成 | 第 6、8 讲挑战题 | 支持上下文追问（“那华东呢？”），会话隔离 |
| **③ SQL 安全护栏** | 新增校验节点 | 第 7 讲挑战题 | 只读、防多语句、强制 LIMIT/超时，拦截危险 SQL |
| **④ 召回评测** | 评测脚本 | 第 5 讲挑战题 | 金标准集 + Recall@K 量化 + ≥2 项改进及效果对比 |
| **⑤ 知识库扩域** | dw建表 + meta配置 | 第 4 讲挑战题 | 接入新主题（库存/物流），能问出 ≥5 个有意义的问题 |

### 进阶/自拟方向（鼓励）
- 循环纠错 + 多候选自洽（第 7 讲）。
- 新增“表级召回”一路（第 6 讲）。
- 把密钥与配置安全化、加健康检查与限流（第 3、8 讲）。
- 接入更强的中文 embedding 或换 LLM，做 A/B 对比。

### 交付物
1. **可运行代码**：在原仓库新建分支提交，commit 清晰。
2. **设计报告**（参照 `docs/04-掌柜问数-设计文档.md` 风格）：需求 → 方案 → 关键实现（贴关键代码与你改动的节点/层）→ 测试与效果 → 不足与展望。
3. **5 分钟现场演示 + 答辩**：展示功能 + 回答“为什么这么做”。

### 评分（与大纲一致）
代码 20% + 报告 10% + 答辩 10%（大作业共 40%）。重点看：是否真正理解了所改动的层、改动是否合理、效果是否可量化、能否讲清设计权衡。

## 七、扩展练习（课后持续）

### 基础级
1. 给前端结果表加“导出 CSV”“复制 SQL”小功能。
2. 把生成的 SQL 也作为一个事件（`type:"sql"`）推给前端展示，让用户看到“它到底查了什么”。

### 进阶级
3. 给系统加“问题历史记录”侧边栏（前端本地存储即可）。
4. 做一个 mini 压测：用脚本并发打 N 个查询，观察响应时间和中间件负载，写性能小报告。

### 挑战级
5. 把你课程设计的方向，做成一篇“技术博客 + Demo 视频”对外分享，体会“把项目讲清楚”也是工程能力的一部分。

## 八、思考题（系统级）

1. 回看整张系统，你认为**最影响最终准确率**的是哪一个环节？给出你的判断依据（最好用实验支撑）。
2. 如果要把掌柜问数推向真实生产（上千张表、高并发、敏感数据），现在的架构有哪三处最需要加固？
3. 本项目用“工程设计”而非“更大模型”来保证准确性。随着大模型能力增强，这套“知识库 + 召回 + 校验”的工程是否会被淘汰？说说你的看法。
4. 学完整个项目，如果让你从零设计一个面向**另一个领域**（如医疗病历问答、法律条文检索）的“自然语言问 X”系统，你会复用掌柜问数的哪些设计、改掉哪些？

---

## 结语

掌柜问数不是一个“调通了就结束”的 Demo，而是一套可以不断生长的工程骨架。希望你学完这门课，不只是会跑它，而是**理解它每一处设计的取舍**，并能在它之上长出属于自己的、更优秀的增强。把课程设计当成一次真实的小型工程，去发挥你的能动性——这正是这门课最想留给你的东西。

第 01 讲 · LECTURE 01

项目概述与系统架构

问题 · 架构 · 数据流 · 心智模型

对应笔记：第 1 章「项目概述」、第 2 章「项目架构」 学时：4（理论 2 + 上机 2）

一、教学目标

学完本讲，学生应能够：

  1. 说清问题：用一句话讲明白「掌柜问数」要解决什么——让不懂 SQL 的业务人员用自然语言查数仓。
  2. 区分概念：分清「业务库（OLTP）」与「数据仓库（OLAP）」的定位差异，并能解释星型模型。
  3. 复述架构：画出系统的三大支柱（元数据知识库 / 问数智能体 / 服务化）与端到端数据流。
  4. 理解关键设计动机：能回答「为什么不直接把表结构丢给大模型让它写 SQL」这个核心问题。

本讲是“建立心智模型”的一讲，不写代码，但决定了后面 8 讲能不能学懂。

二、教学重点

  • NL2SQL 系统的整体架构与数据流。
  • “检索增强（RAG）+ 大模型生成 + 校验纠错”如何共同保障准确性与可控性。
  • 星型模型在本项目中的具体落地（dim_* 维度表 + fact_order 事实表）。

三、教学难点

  • 把“多路召回 → 合并 → 过滤 → 生成 → 校验 → 执行”这条链路在脑中跑通。
  • 理解“元数据知识库”这一层为什么是整个系统的“地基”，而不是可有可无的优化。

四、原理精讲

4.1 问题的本质：业务人员与数据之间的“翻译鸿沟”

企业的数据躺在数据仓库里，但会写 SQL 的人很少。传统路径是「业务提需求 → 数据团队写 SQL → 出报表」，链路长、响应慢。掌柜问数要做的，是把这条链路压缩成一句话：“问一句，出报表”。

技术上，这就是 NL2SQL（自然语言转 SQL） 任务：输入一句中文，输出一条能在数仓上跑出正确结果的 SQL。

4.2 为什么不能“直接问大模型”

最朴素的想法：把所有建表语句拼进 prompt，让大模型直接写 SQL。这在玩具项目里能跑，但在真实数仓里会崩，原因有三：

  1. 表太多放不下：真实数仓动辄上千张表、上万个字段，全部塞进 prompt 会爆上下文，也烧钱。
  2. 大模型会“幻觉”：它可能编造不存在的表名、字段名，或误解业务口径（比如“销售额”到底算不算退款）。
  3. 生成结果不可控：可能生成 DELETE、可能语法不符合目标数据库方言、可能一次返回多条语句。

掌柜问数用三招破解，这正是后面要逐讲实现的内容：

问题 解法 对应讲
表太多放不下 多路召回 + 过滤：只把和问题相关的表/字段/指标喂给大模型 第 5、6 讲
大模型幻觉 元数据知识库：用真实 schema、别名、取值、指标定义约束它 第 4、5 讲
结果不可控 校验 → 纠错闭环 + prompt 约束（只读、单条、指定方言） 第 7 讲

这是本课程最重要的一句话：掌柜问数的准确性，不是靠“更大的模型”，而是靠“给模型喂对、喂准、喂少”的工程设计。

4.3 数据仓库与星型模型（大数据专业的“主场”）

大数据专业的同学对这部分有天然优势，这里只做对齐：

  • 业务库（OLTP）管“干活”：支撑日常交易，强调写入、事务、实时。
  • 数据仓库（OLAP）管“复盘”：面向分析、集成、非易失、随时间变化，支撑报表与决策。

本项目的数仓采用经典 星型模型（见 backend/conf/meta_config.yaml 与 scripts/mysql/init/02-dw-schema.sql）：

                 dim_date(时间维度)
                       │
 dim_region ───┐       │       ┌─── dim_customer
 (地区维度)     │       │       │     (客户维度)
               ▼       ▼       ▼
            ┌──────────────────────┐
            │   fact_order(订单事实)  │   ← 中心事实表，存度量：order_amount, order_quantity
            └──────────────────────┘
                       ▲
                       │
                 dim_product(商品维度)
  • 维度表 dim_*：描述“谁、什么、何时、何地”（客户、商品、时间、地区）。
  • 事实表 fact_order：记录“发生了什么、多少”，通过外键关联各维度，存放可度量的数值（金额、数量）。

4.5 端到端数据流（一定要背下来）

以问题“统计一下各个地区销售排行前三的产品”为例：

  1. 抽取关键字：jieba 分词 → [地区, 销售, 产品, ...]。
  2. 多路召回（并行）： - 字段召回：向量检索 Qdrant → 找到 region_name、product_name、order_amount 等字段。 - 取值召回：全文检索 ES → 找到“华东/华南”等地区取值。 - 指标召回：向量检索 Qdrant → 找到 GMV（成交总额）指标定义。
  3. 合并召回信息：把字段、取值、指标拼成结构化的“表信息 + 指标信息”，并补齐主外键。
  4. 过滤：用大模型从候选里裁掉无关表/字段（减少干扰）。
  5. 补充上下文：注入当前日期、数据库方言/版本。
  6. 生成 SQL：大模型基于上述信息产出一条 SQL。
  7. 校验：用 EXPLAIN 验证 SQL 是否合法；不合法 → 纠错（把错误信息喂回大模型重写）。
  8. 执行：在 dw 库上跑 SQL，返回结果。
  9. 全程通过 SSE 把每一步进度和最终结果流式推给前端。

这条链路你已经在本机跑通过了（第 9 讲会再做一次完整联调）。本讲要做的，是在脑中把它“跑”一遍。

六、常见误区

  • ❌ “知识库就是个缓存/优化”——错。它是约束大模型、防幻觉的核心，没有它系统不可用。
  • ❌ “大模型越大越准”——本项目准确性主要来自工程设计，不是模型规模。
  • ❌ 把 dw（真实数据）和 meta（描述数据的数据）搞混。务必记住：meta 描述 schema，dw 存真实业务数据。

四、原理精讲

4.1 为什么要四个中间件

服务 镜像 端口 在本项目的职责
MySQL mysql:8.0 3306 存两类数据：meta（元数据知识库）+ dw（真实数仓）
Elasticsearch elasticsearch:8.19.10 9200 字段取值的全文索引（带 IK 中文分词器）
Qdrant qdrant:v1.16 6333/6334 字段、指标的语义向量索引
Embedding (TEI) text-embeddings-inference:cpu-1.8 8081 把文本转成 1024 维向量（BAAI/bge-large-zh-v1.5）

这正是第 1 讲“元数据知识库”三索引（MySQL + Qdrant + ES）+ 向量化能力（Embedding）的物理载体。

4.2 Makefile 与 docker-compose 的协作

项目用 Makefile 封装冗长的 docker compose 命令。看 Makefile 顶部：

DOCKER_COMPOSE := PROJECT_ROOT=$(PROJECT_DIR) docker compose \
    -p $(COMPOSE_PROJECT_NAME) \
    -f docker/docker-compose-debug.yml \
    --env-file docker/.env.debug \
    --profile middleware

关键点： - -p storekeeper-nl2sql：项目名（容器、网络的前缀）。 - -f docker/docker-compose-debug.yml：编排文件。 - --env-file docker/.env.debug：注入 MySQL 账号密码等环境变量。 - --profile middleware：只启动带 middleware profile 的服务。

常用目标：make middleware（启动并等待健康）、make down、make ps、make logs、make clean（删容器和数据卷，但保留 embedding 模型缓存）。

4.3 健康检查（healthcheck）：为什么 --wait 能等到“真就绪”

看 compose 里 MySQL 的健康检查（docker/docker-compose-debug.yml）：

healthcheck:
 test: ["CMD-SHELL", "mysqladmin ping ... --silent"]
 interval: 10s
 retries: 30
 start_period: 30s

make middleware 用了 up -d --wait，会一直等到所有服务 healthcheck 通过才返回。这避免了“容器起来了但服务还没准备好”导致的连接失败。

工程素养点：区分“容器 Running”和“服务 Ready”。前者只是进程起来了，后者才是能对外服务。

4.4 本项目最大的环境坑：Embedding 离线加载

TEI 的 MODEL_ID 默认填 HuggingFace repo-id（如 BAAI/bge-large-zh-v1.5），启动时会去 huggingface.co 下载模型。在国内/无外网环境，这会一直卡住超时重试。

本项目的解法（已写进 CLAUDE.md，并在 compose 中固化）：把模型放本地，MODEL_ID 填容器内本地路径。看 docker/docker-compose-debug.yml 的 embedding 段：

embedding:
 image: ghcr.io/huggingface/text-embeddings-inference:cpu-1.8
 environment:
 MODEL_ID: /models/bge-large-zh-v1.5 # ← 本地路径，不是 repo-id
 volumes:
 - ./models/bge-large-zh-v1.5:/models/bge-large-zh-v1.5 # ← 把本地模型挂进容器
 - ./data/embedding:/data

模型文件（约 1.2G 的 pytorch_model.bin 等）来自 2.资料/2.docker compose/embedding/bge-large-zh-v1.5，拷到项目 docker/models/ 下即可。

candle 后端回退：TEI cpu 镜像默认想用 ONNX 权重（model.onnx），本地模型只有 pytorch 权重。启动日志会先报 Could not start ORT backend: ... model.onnx does not exist，随后自动回退：

Starting Bert model on Cpu     ← candle 后端接管，加载 pytorch_model.bin
Warming up model

这是正常现象，不是错误。

4.5 IK 中文分词器的自动安装

ES 默认不带中文分词器。compose 里通过启动命令自动安装 analysis-ik（见 docker/docker-compose-debug.yml 的 elasticsearch command 段），这样取值的全文检索才能正确切分中文。第 5 讲会用到 ik_max_word。

五、代码精读

5.1 起停脚本 run.sh（项目根目录）

本项目提供了一键起停脚本，封装了“中间件 → 等 embedding 就绪 → 后端 → 前端”的完整顺序。核心片段：

do_start() {
  start_middleware || return 1
  wait_http "http://localhost:8081/health" "Embedding 模型" 60 # 等模型 warmup
  start_backend
  start_frontend
}

为什么要 wait_http 等 embedding？因为本地加载模型需要 warmup 时间，过早启动后端、构建知识库会因为 embedding 没就绪而失败。这体现了 4.3 的“服务 Ready”理念。

run.sh 用“PID 文件 + 端口探测”双重判活，PID 记在 .run/，日志在 logs/。常用：

./run.sh start | stop | restart | status | logs
./run.sh build-kb            # 构建知识库（第5讲用）
./run.sh start backend       # 只启某一层

4.1 配置管理：YAML × dataclass × OmegaConf

配置与代码分离是工程铁律。本项目用 OmegaConf 把 backend/conf/app_config.yaml 加载成强类型 dataclass 对象。

看 backend/app/conf/app_config.py：

@dataclass
class DBConfig:
host: str
port: int
user: str
password: str
database: str
@dataclass
class AppConfig:
logging: LoggingConfig
db_meta: DBConfig
db_dw: DBConfig
qdrant: QdrantConfig
embedding: EmbeddingConfig
es: ESConfig
llm: LLMConfig
config_file = Path(__file__).parents[2] / 'conf' / 'app_config.yaml'
context = OmegaConf.load(config_file) # 读 YAML
schema = OmegaConf.structured(AppConfig) # 用 dataclass 当 schema
app_config: AppConfig = OmegaConf.to_object(OmegaConf.merge(schema, context)) # 合并并校验类型

精读要点： - OmegaConf.structured(AppConfig)：把 dataclass 变成带类型约束的 schema。 - OmegaConf.merge(schema, context)：用 YAML 的值填充 schema，类型不符会报错——这就是“结构化配置”的价值：配置写错（比如 port 写成字符串）在启动时就暴露，而不是运行到一半才崩。 - app_config 是模块级单例，全项目 from ... import app_config 直接用。

4.4 客户端管理器：统一的 init/close 模式

四个中间件各有一个“客户端管理器”，模式高度统一：__init__ 存配置，init() 建连接，close() 释放。

Embedding（backend/app/clients/embedding_client_manager.py）：

class EmbeddingClientManager:
def __init__(self, config: EmbeddingConfig):
self.client = None
self.config = config
def _get_url(self):
return f"http://{self.config.host}:{self.config.port}"
def init(self):
self.client = HuggingFaceEndpointEmbeddings(model=self._get_url())
embedding_client_manager = EmbeddingClientManager(app_config.embedding) # 模块级单例

Qdrant / ES（qdrant_client_manager.py / es_client_manager.py）：同样 init() 建异步客户端，close() 释放。

MySQL（backend/app/clients/mysql_client_manager.py）最值得精读，它涉及连接池和 session 工厂：

class MysqlClientManager:
def _get_url(self):
return f"mysql+asyncmy://{user}:{password}@{host}:{port}/{database}?charset=utf8mb4"
def init(self):
self.engine = create_async_engine(url=self._get_url(),
pool_size=10, pool_pre_ping=True) # 连接池
self.session_factory = async_sessionmaker(self.engine,
autoflush=True,
expire_on_commit=False,
autobegin=True)
dw_mysql_client_manager = MysqlClientManager(app_config.db_dw) # 两个库两个管理器
meta_mysql_client_manager = MysqlClientManager(app_config.db_meta)

精读要点： - mysql+asyncmy://：异步驱动（asyncmy），配合 async/await 实现高并发。 - pool_size=10：连接池，复用连接、控制并发。 - pool_pre_ping=True：取连接前先 ping，避免拿到已失效的连接。 - engine（连接池）单例长存，session 每次用 session_factory() 新建——这是第 4.5 节的关键。

4.5 为什么“引擎单例、session 每请求”

  • 引擎/连接池：建立成本高（TCP、握手），应在应用启动时建一次、全程复用 → 单例 + init/close。
  • session（会话）：代表“一次工作单元/一个事务上下文”，应短生命周期、每个请求新建用完即弃 → session_factory() 配合 async with。

混用会出事：多个请求共享一个 session 会导致事务串扰、状态污染。第 8 讲会看到 FastAPI 如何用 Depends 为每个请求注入一个新 session。

4.6 分层架构与依赖方向

api(路由/schema/依赖)  →  services(业务编排)  →  agent(智能体节点)
                                                      ↓
                              repositories(数据读写)  →  clients(连接管理)
  • entities/：领域对象（dataclass，作为 Qdrant/ES 的 payload）。
  • models/：SQLAlchemy ORM 模型（仅 meta 库）。
  • repositories/：封装数据读写（隔离 SQL/检索细节）。
  • 依赖单向向下，上层依赖下层抽象，不反向。这让每层可独立测试、替换。

四、原理精讲

4.1 什么是“元数据知识库”

元数据 = “描述数据的数据”。本项目把数仓的 schema 与业务知识，组织成大模型可消费的“知识”，包括：

  • 表信息：表名、角色（维度/事实）、业务描述。
  • 字段信息：字段名、类型、角色（主键/外键/维度/度量）、示例取值、描述、别名。
  • 指标信息：业务指标（如 GMV）的名称、口径描述、相关字段、别名。
  • 字段取值：维度字段的实际取值（如地区有“华东/华南”）。

这套知识分别落到三个存储（第 1 讲讲过）：MySQL 存结构化部分，Qdrant 存向量，ES 存取值。本讲聚焦 MySQL（结构化）这一份。

4.2 meta 库的四张表

见 scripts/mysql/init/03-meta-schema.sql 与 backend/app/models/：

table_info        字段表/指标表的“目录”
  └─ column_info  字段信息（外键 table_id 指向 table_info）
metric_info       指标信息
  └─ column_metric  指标↔字段的多对多关联表
  • table_info：每个表一行。
  • column_info：每个字段一行，table_id 关联所属表。
  • metric_info：每个指标一行。
  • column_metric：指标与其相关字段的多对多桥表（一个指标可关联多个字段，一个字段可服务多个指标）。

4.3 三套数据表示：entities / models / mappers

这是本讲最易混淆、也最能体现工程功底的地方。同一个“字段信息”，在项目里有三种形态：

形态 位置 用途
entity backend/app/entities/column_info.py 领域对象（dataclass），跨层传递、作 Qdrant payload
model（ORM） backend/app/models/column_info_mysql.py SQLAlchemy ORM，映射到 column_info 表，负责读写 MySQL
mapper backend/app/repositories/mysql/meta/mappers/column_info_mapper.py 在 entity ↔ model 之间转换

为什么要分两套（entity 和 model）？ - ORM model 绑定数据库表结构，带 SQLAlchemy 的“魔法”（会话、惰性加载），不适合到处传递。 - entity 是纯数据对象，干净、可序列化（能直接当 Qdrant 的 payload、能 json.dumps），适合在 service/agent 层流动。 - mapper 把两者解耦：数据库表结构变了，只改 model + mapper，entity 和业务逻辑不动。

这是“领域模型与持久化模型分离”的经典实践，大厂代码里非常常见。

4.4 meta_config.yaml：知识库的“源头真相”

整个知识库的内容由一份 YAML 定义（backend/conf/meta_config.yaml）。看一段：

 - name: dim_region

 description: 地区维度表... # 给大模型看的业务描述

 - name: region_name

4.5 三个关键字段的语义（重点）

  • role（角色）：
  • 表级：dim（维度）/ fact（事实）。
  • 字段级：primary_key / foreign_key / dimension / measure。

  • 作用：让大模型知道哪些是度量（可聚合）、哪些是维度（可分组）、哪些是键（可 join）。第 6 讲合并召回时会“显式补齐主外键”，靠的就是 role。

  • alias（别名）：业务人员问“大区”，字段叫 region_name，靠别名才能召回。别名是召回率的关键。 第 5 讲会把 name、description、每个 alias 都向量化入库。

  • sync（取值同步）：是否把该列的实际取值灌入 ES 全文索引。维度字段（地区、品牌）开启，主键/度量不开（取值无检索意义、且量大）。

4.6 从配置写入 meta 库的流程（本讲范围）

入口脚本 backend/app/scripts/build_meta_knowledge.py 调用 MetaKnowledgeService.build()（backend/app/services/meta_knowledge_service.py）。本讲只看“写结构化元数据”这一步 _save_tables_to_meta_db：

async def _save_tables_to_meta_db(self, meta_config) -> list[ColumnInfo]:
for table in meta_config.tables:
table_info = TableInfo(id=table.name, name=table.name, role=table.role, description=table.description)
column_types = await self.dw_mysql_repository.get_column_types(table.name) # 从 dw 库查真实字段类型
for column in table.columns:
column_values = await self.dw_mysql_repository.get_column_values(table.name, column.name, 10) # 取10个示例值
column_info = ColumnInfo(id=f"{table.name}.{column.name}", name=column.name,
type=column_types[column.name], role=column.role,
examples=column_values, description=column.description,
alias=column.alias, table_id=table.name)
async with self.meta_mysql_repository.session.begin(): # 一个事务里批量写
await self.meta_mysql_repository.save_table_infos(table_infos)
await self.meta_mysql_repository.save_column_infos(column_infos)
return column_infos

精读要点： - 配置只写“描述性信息”，真实的字段类型和示例取值从 dw 库现查（get_column_types、get_column_values）——配置不重复数据库已有的事实，降低维护成本。 - id 用 表名.字段名 这种自然主键，全局唯一、可读。 - 用 session.begin() 包成一个事务，保证“要么全写成功，要么全回滚”。

4.1 两类检索：语义 vs 关键词

向量检索（Qdrant） 全文检索（ES）
原理 文本→向量，比余弦相似度 分词→倒排索引，比关键词匹配
擅长 语义相近（“营收”≈“销售额”） 精确/字面匹配（取值“华东”）
本项目用于 字段信息、指标信息的召回 字段取值的召回
失效场景 专有名词、精确值 同义词、语义改写

本项目的设计： - 字段/指标 → 向量检索（用户用什么词都可能，需要语义匹配）。 - 取值 → 全文检索（“华东”就是“华东”，要精确匹配，且取值量大、不适合全部向量化）。

两者互补，覆盖不同的召回需求——这就是第 1 讲思考题的答案。

4.2 向量索引：Embedding + Qdrant

Embedding：把文本映射到 1024 维向量空间，语义相近的文本向量距离近。本项目用 BAAI/bge-large-zh-v1.5（中文向量模型），通过 TEI 服务提供（第 2 讲）。

Qdrant 的数据模型： - collection：相当于“表”，建时要指定向量维度和距离度量。 - point：一条数据 = id + vector（向量）+ payload（原始数据，这里是 ColumnInfo）。

看 backend/app/repositories/qdrant/column_qdrant_repository.py：

class ColumnQdrantRepository:
collection_name = 'data-agent-column'
async def ensure_collection(self):
if not await self.client.collection_exists(self.collection_name):
await self.client.create_collection(
self.collection_name,
vectors_config=VectorParams(size=app_config.qdrant.embedding_size, # 1024
distance=Distance.COSINE)) # 余弦相似度
async def search(self, embedding, score_threshold=0.6, limit=5) -> list[ColumnInfo]:
result = await self.client.query_points(self.collection_name, query=embedding,
score_threshold=score_threshold, limit=limit)
return [ColumnInfo(**point.payload) for point in result.points]

精读要点： - ensure_collection：幂等——不存在才建，可反复调用。 - Distance.COSINE + score_threshold=0.6：只返回相似度 ≥ 0.6 的，过滤噪声。 - limit=5：每次召回 top-5，控制候选规模。 - payload 直接反序列化成 ColumnInfo entity（第 4 讲的“entity 可序列化”优势在此体现）。

index_mappings = {
"dynamic": False,
"properties": {

async def search(self, keyword, score_threshold=0.6, limit=5) -> list[ValueInfo]:

async def extract_keywords(state, runtime):

keywords = jieba.analyse.extract_tags(state["query"], allowPOS=allow_pos) # 只取指定词性

4.4 节点 2-4：三路召回（含 LLM 关键词扩展）

以字段召回 recall_column.py 为例：

async def recall_column(state, runtime):
writer = runtime.stream_writer
writer({"type": "progress", "step": "召回字段", "status": "running"})
embedding_client = runtime.context["embedding_client"] # ← 依赖从 context 取
column_qdrant_repository = runtime.context["column_qdrant_repository"]
# 1) 用 LLM 扩展关键词（提高召回）
chain = PromptTemplate(template=load_prompt("extend_keywords_for_column_recall"),
input_variables=["query"]) | llm | JsonOutputParser()
result = await chain.ainvoke({"query": state["query"]})
keywords = list(set(state["keywords"] + result))
# 2) 逐关键词向量化 + Qdrant 检索 + 去重
retrieved_columns_map = {}
for keyword in keywords:
embedding = await embedding_client.aembed_query(keyword)
for payload in await column_qdrant_repository.search(embedding):
retrieved_columns_map.setdefault(payload.id, payload) # 按 id 去重
writer({"type": "progress", "step": "召回字段", "status": "success"})
return {"retrieved_columns": list(retrieved_columns_map.values())}

精读要点： - 两层关键词扩展：jieba 已抽一批，这里再用 LLM 扩一批（同义词/相关词），合并去重——尽量提高召回率。 - 依赖全部来自 runtime.context，不在节点里 import 具体实例——这让节点可在测试中注入 mock。 - retrieved_columns_map 按字段 id 去重（呼应第 5 讲：同一字段有多个 point，会被多次命中）。 - 取值召回 recall_value.py、指标召回 recall_metric.py 结构几乎一致，只是换了 repository 和 prompt。

extract_keywords 用规则（jieba），召回里用 LLM 扩展——规则 + 模型结合，各取所长。

4.5 节点 5：merge_retrieved_info（合并与补全）

merge_retrieved_info.py 是前半段最复杂的节点，干三件事：

  1. 指标→字段补全：指标的 relevant_columns 若没被召回，从 meta 库补进来。
  2. 取值并入字段：把召回的取值挂到对应字段的 examples 上（让大模型看到“地区有华东/华南”）。
  3. 补主外键：每张表显式补上主键/外键字段——否则大模型没法写 JOIN。

for key_column in key_columns:
if key_column.id not in column_ids:
table_to_columns_map[table_id].append(key_column)

最终把召回的零散信息，组装成结构化的 table_infos（表→字段树）和 metric_infos，写回 state。这一步把“检索结果”翻译成“大模型能直接用的上下文”。

4.6 节点 6-7：filter_table / filter_metric（LLM 相关性过滤）

召回偏向“宁多勿漏”（高召回），但候选里有噪声。过滤节点用 LLM 把无关的表/字段裁掉（提精度）。看 filter_table.py：

chain = PromptTemplate(template=load_prompt("filter_table_info"),
input_variables=["query", "table_infos"]) | llm | JsonOutputParser()
result = await chain.ainvoke({"query": query,
"table_infos": yaml.dump(table_infos, allow_unicode=True, sort_keys=False)})
# result 形如 {"fact_order":["order_amount","region_id"], "dim_region":["region_id","region_name"]}
for table_info in table_infos[:]: # 用切片副本遍历，边遍历边删
if table_info["name"] not in result:
table_infos.remove(table_info) # 整张表无关 → 删表
else:
for column_info in table_info["columns"][:]:
if column_info["name"] not in result[table_info["name"]]:
table_info["columns"].remove(column_info) # 字段无关 → 删字段

精读要点： - prompt（backend/prompts/filter_table_info.prompt）严格约束 LLM：只能从候选里选、不能新增、要保留 join 主外键、只输出 JSON。 - 用 list[:] 切片副本遍历，避免“边遍历边删原列表”的坑。 - 这是“召回高 recall → 过滤提 precision”的经典两段式检索增强。

4.7 进度流式输出协议

每个节点开头/结尾都 writer({"type":"progress","step":..., "status":"running"/"success"/"error"})。这是和前端约定的 SSE 协议（第 8 讲详讲），让用户实时看到“进行到哪一步”。

4.1 后半段的整体结构

add_extra_context → generate_sql → validate_sql ──(error is None)──→ execute_sql → END
                                        │                               ▲
                                        └──(error 非空)──→ correct_sql ──┘

validate_sql 后是一个条件边：校验通过直接执行，校验失败先纠错再执行。这就是系统“可控性”的核心闭环。

4.2 节点 8：add_extra_context（补充上下文）

backend/app/agent/nodes/add_extra_context.py：

async def add_extra_context(state, runtime):
dw_mysql_repository = runtime.context["dw_mysql_repository"]
today = datetime.today()
date_info = DateInfoState(date=today.strftime("%Y-%m-%d"),
weekday=today.strftime("%A"),

为什么需要这一步？ - 日期信息：用户问“今年”“上季度”，大模型需要知道“今天是哪天、现在第几季度”才能算出时间范围。 - 数据库信息：方言（MySQL）和版本决定 SQL 语法（函数名、分页写法）。get_db_info() 执行 select version() 并取 dialect（backend/app/repositories/mysql/dw/dw_mysql_repository.py）。

4.3 节点 9：generate_sql（生成）

generate_sql.py：

chain = PromptTemplate(template=load_prompt("generate_sql"),
input_variables=["query","table_infos","metric_infos","date_info","db_info"]) | llm | StrOutputParser()
result = await chain.ainvoke({
"query": query,
"table_infos": yaml.dump(table_infos, allow_unicode=True, sort_keys=False), # 过滤后的表
"metric_infos": yaml.dump(metric_infos, allow_unicode=True, sort_keys=False), # 指标口径
"date_info": yaml.dump(date_info, ...),
"db_info": yaml.dump(db_info, ...),
})
return {"sql": result}

精读要点： - 输入是过滤后的精简上下文（第 6 讲的成果）——喂得准、喂得少。 - 用 yaml.dump(..., allow_unicode=True) 把结构化信息转成可读文本喂给大模型（YAML 比 JSON 更省 token、更易读）。 - 用 StrOutputParser（SQL 是纯文本，不是 JSON）。

prompt（backend/prompts/generate_sql.prompt）里把“可控性”写死成硬约束：

1. 仅允许使用数据表信息中真实存在的表与字段，禁止编造。      ← 防幻觉
2. 若有指标定义，必须严格遵循其业务口径。                  ← 口径一致
3. 只能查询，不能写入/更新/删除。                          ← 安全
4. 语法必须符合数据库环境指定的类型与版本。                ← 方言
5. 默认只生成一条 SQL。                                    ← 可执行
6. 仅输出纯文本 SQL，禁止 Markdown 代码块。                ← 可解析

关键认知：可控性不是靠模型“自觉”，而是靠 prompt 硬约束 + 下游校验。这是 LLM 应用工程的精髓。

4.4 节点 10：validate_sql（校验）——条件边的驱动者

validate_sql.py：

async def validate_sql(state, runtime):
dw_mysql_repository = runtime.context["dw_mysql_repository"]
try:
await dw_mysql_repository.validate_sql(state["sql"]) # 内部执行 EXPLAIN <sql>
return {"error": None} # 校验通过
except Exception as e:
return {"error": str(e)} # 校验失败，记录错误信息

校验用 EXPLAIN（dw_mysql_repository.validate_sql 执行 explain {sql}）： - EXPLAIN 只解析和规划，不真正执行，能在不动数据的前提下发现语法错误、表/字段不存在等问题。 - 关键：校验失败不抛异常中断，而是把错误信息写进 state["error"]——交给条件边决策。

4.5 条件边：状态驱动的分支

graph.py：

graph_builder.add_conditional_edges(
"validate_sql",
lambda state: "execute_sql" if state["error"] is None else "correct_sql", # 路由函数
{"execute_sql": "execute_sql", "correct_sql": "correct_sql"}) # 映射
graph_builder.add_edge("correct_sql", "execute_sql")

精读要点： - 路由函数读 state["error"]：为 None → 去执行；非空 → 去纠错。 - 这就是“控制流由数据状态驱动”——graph 的走向取决于运行时的 state，而非写死。 - 纠错后无条件进入执行（correct_sql → execute_sql）。

注意：本项目纠错是“一次性”的（纠错后直接执行，不再二次校验）。扩展练习会让你把它改成“循环纠错直到通过或达上限”。

4.6 节点 11：correct_sql（纠错）

correct_sql.py：把原 SQL + 错误信息 + 全部上下文一起喂回大模型重写：

result = await chain.ainvoke({
"query": query, "table_infos": ..., "metric_infos": ..., "date_info": ..., "db_info": ...,
"sql": sql, # 出错的 SQL
"error": error, # validate_sql 捕获的错误
})
return {"sql": result} # 覆盖 state 里的 sql

让大模型“看着错误改作业”，比从头重写更可能改对。

4.7 节点 12：execute_sql（执行 + 回传结果）

execute_sql.py：

async def execute_sql(state, runtime):
dw_mysql_repository = runtime.context["dw_mysql_repository"]
result = await dw_mysql_repository.execute_sql(state["sql"]) # 真正在 dw 库执行
writer({"type": "progress", "step": "执行SQL", "status": "success"})
writer({"type": "result", "data": result}) # ← 用 result 类型推送数据

dw_mysql_repository.execute_sql 把结果行转成 list[dict]（[dict(row) for row in result.mappings().fetchall()]），便于 JSON 序列化推给前端。注意它只 writer 不 return——结果通过流式事件出去，不需要写回 state。

4.2 lifespan：长连接客户端的启停

qdrant_client_manager.init()
es_client_manager.init()
meta_mysql_client_manager.init()

FastAPI 的 Depends 把对象的“装配过程”声明出来，按需、按请求构造。本项目的依赖链：

get_meta_session / get_dw_session   （每请求新建 session，用 async with 自动关闭）
        ↓
get_*_repository                    （用 session/client 构造 repository）
        ↓
get_query_service                   （把所有 repository + embedding client 装进 QueryService）

关键代码：

column_qdrant_repository = Depends(get_column_qdrant_repository),
... ) -> QueryService:

精读要点（呼应第 3 讲 4.5）： - session 用 Depends(get_meta_session) 每请求新建，async with 保证请求结束自动关闭——和 lifespan 里的“长连接单例”形成对比：连接池长存、session 短命。 - repository 是对 session/client 的薄封装，依赖注入让它们自动装配。 - QueryService 拿到全套依赖，成为路由可直接调用的“业务门面”。

4.5 SSE 流式：QueryService 如何转发 graph 事件

backend/app/services/query_service.py：

async def query(self, query: str):
context = DataAgentContext(embedding_client=self.embedding_client,
column_qdrant_repository=self.column_qdrant_repository, ...) # 装 Context
state = DataAgentState(query=query)
try:
async for chunk in graph.astream(input=state, context=context, stream_mode="custom"):
yield f"data: {json.dumps(chunk, ensure_ascii=False, default=str)}\n\n" # ← SSE 格式
except Exception as e:
yield f"data: {json.dumps({'type':'error','message':str(e)}, ensure_ascii=False)}\n\n"

精读要点： - 这里把第 6/7 讲的 runtime.context 真正“喂”进 graph——Context 在此装配。 - graph.astream(..., stream_mode="custom")：配合节点里的 stream_writer，逐个产出节点推送的事件（progress / result / error）。 - SSE 格式：每条消息是 data: <内容>\n\n（两个换行结尾）。这是 SSE 协议规定，浏览器 EventSource/前端按此解析。 - ensure_ascii=False：中文不转义，前端可读；default=str：兜底序列化（如 datetime）。 - 整个函数是异步生成器（yield），与 StreamingResponse 配合实现“边算边推”。

4.6 前后端约定的事件协议（回顾）

type 含义 示例
progress 节点进度 {"type":"progress","step":"召回字段","status":"running"}
result 查询结果 {"type":"result","data":[{...}]}
error 错误 {"type":"error","message":"..."}

节点用 writer(...) 推送（第 6/7 讲），service 包成 data: ...\n\n 转发，前端按 type 渲染。这套协议是前后端解耦的契约。

六、常见坑

  • 前端跨域被拦：检查 CORS 白名单是否包含前端实际地址。

八、思考题

  1. 为什么连接型客户端在 lifespan 建（单例），而 session 在 Depends 建（每请求）？把 session 也做成单例会出什么问题？
  2. SSE 相比“一次性返回全部结果”，对用户体验和服务端资源各有什么影响？什么场景下流式是必须的？
  3. Depends 的依赖链是“声明式”的——路由只声明它要 QueryService，FastAPI 自动把整条链装配好。这种 IoC（控制反转）相比手动 new 对象有什么好处？
  4. query_service.query 是异步生成器，一旦客户端中途断开连接，服务端的 graph 还会继续跑吗？该如何优雅处理？

4.2 前端如何消费 SSE

前端向 POST /api/query 发请求，按 SSE 逐条读取 data: {...}，根据 type 分别处理： - progress：更新进度条/步骤状态（running/success/error）——让用户看到“正在召回字段…”。 - result：拿到 data（结果行数组），渲染成表格。 - error：弹出错误提示。

这正是第 8 讲“事件协议”在前端的落地。建议学生打开浏览器开发者工具的 Network 面板，观察 /api/query 的 EventStream。

# 教案详案 · 第 6 讲：问数智能体（上）——召回与过滤

> 教师授课用逐段细案，配合 `06-问数智能体（上）-召回与过滤.md`（学生教案）使用。
> 体例同第 1 讲详案：⏱ 时间 / 🗣 讲稿 / ✍ 板书 / ❓ 提问 / 💻 上机 / ⚠ 预案。

---

## 一、本讲定位与教学法说明

- **性质**：全课最“硬”的一讲（代码密度最高），第一次真正进入智能体内部。
- **核心矛盾**：学生第一次见 LangGraph，容易被 State/Context/Node/Edge 四个概念绕晕，也容易把“召回”和“过滤”混为一谈。
- **两个必须钉死的认知**：
  1. **State 是流动的数据，Context 是注入的依赖**（分清这两者，后面节点全通）。
  2. **召回求“全”(recall)，过滤求“准”(precision)——两段式**。
- **教学法**：先讲清四概念（地图），再顺着“图的连线”逐节点走（路线），最后上机看真实召回/过滤结果（实景）。**概念→结构→节点→实证**。
- **总时长**：4 学时（理论约 95 分钟 + 上机约 85 分钟）。
- **前置检查**：知识库已构建（`./run.sh build-kb` 跑过），否则召回为空，上机无法观察。

### 段落 1 · LangGraph 四概念（22 min）

⏱ 0:08–0:30

> 本段是地基，绕晕了后面全崩。建议用“工厂流水线”的比喻贯穿。

🗣 **比喻引入**：
> “把智能体想象成一条流水线。**State 是流水线上传送的那个‘工件’**——每个工位往上面加点东西；**Context 是工位旁边的‘工具箱’**（钻头、扳手）——和具体工件无关，是干活的家伙什；**Node 是工位**；**Edge 是传送带的走向**。”

✍ **板书（四概念表，副板）**：
```
State   = 流动的数据(工件)   随查询变化、会被改写
Context = 注入的依赖(工具)   与查询无关、运行时注入
Node    = 工位(async函数)    读state、用context、返回要改的state片段
Edge    = 传送带走向          决定执行顺序，可条件分支
```

🗣 **逐个落到代码**：

1. **State** — 打开 `backend/app/agent/state.py`，逐字段念一遍，强调它装了“从输入到输出的一切”：
   ```python
   class DataAgentState(TypedDict):
       query: str                          # 输入
       keywords: list[str]                 # 关键字节点产出
       retrieved_columns/values/metrics    # 三路召回产出
       table_infos / metric_infos          # 合并产出
       sql: str                            # 生成产出
       error: str                          # 校验产出 → 驱动分支
   ```
   ❓提问：“看这个 State 的字段顺序，能不能猜出节点的执行顺序？”（能——字段几乎就是流水线顺序，这是好的 State 设计。）

2. **Context** — 打开 `backend/app/agent/context.py`：
   ```python
   class DataAgentContext(TypedDict):
       embedding_client; column_qdrant_repository; value_es_repository
       metric_qdrant_repository; meta_mysql_repository; dw_mysql_repository
   ```
   🗣：“全是‘工具’——向量库、ES、数据库的访问对象。注意：**这里没有 query**，因为工具和具体问哪句话无关。”

3. **Node** — 先给“节点函数长什么样”的统一模板（不展开具体节点）：
   ```python
   async def 某节点(state, runtime: Runtime[DataAgentContext]):
       依赖 = runtime.context["..."]        # 从 Context 取工具
       ...用 state 的数据干活...
       return {"要更新的字段": 值}            # 只返回改动片段，框架自动合并进 state
   ```
   🗣 **重点敲黑板**：“依赖是 `runtime.context[...]` **取**出来的，不是 `import` 进来的。记住这点，段落 4 会解释为什么——它关系到能不能写单元测试。”

4. **Edge** — 留到段落 2 看真实连线。

⚠ **预案**：若学生纠结 TypedDict 是什么——一句话带过：“就是带字段类型标注的字典，本质还是 dict，节点返回 dict 就能合并。”不要展开 Python 类型系统。

### 段落 2 · 图的结构：并行 fan-out/fan-in（12 min）

⏱ 0:30–0:42

🗣 **讲稿**：打开 `backend/app/agent/graph.py`，**只看 add_edge 部分**，带学生顺着连线读：

```python
add_edge(START, "extract_keywords")
add_edge("extract_keywords", "recall_column")    # ┐
add_edge("extract_keywords", "recall_value")     # ├ 一个扇出到三个：fan-out
add_edge("extract_keywords", "recall_metric")    # ┘
add_edge("recall_column",  "merge_retrieved_info")  # ┐
add_edge("recall_value",   "merge_retrieved_info")  # ├ 三个汇聚到一个：fan-in
add_edge("recall_metric",  "merge_retrieved_info")  # ┘
```

✍ **板书（画并行结构）**：
```
        extract_keywords
        /      |       \         ← fan-out (并行触发)
 recall_column value  metric
        \      |       /         ← fan-in (都完成才继续)
        merge_retrieved_info
         /            \
   filter_table   filter_metric   ← 又一次 fan-out
```

❓ **关键提问（必问，承接第1讲扣子）**：“三路召回为什么能并行？并行时它们会不会互相打架？”

🗣 **答案（钉死认知2的伏笔）**：
> “能并行，因为三路查的是不同的库（Qdrant/ES/Qdrant），互不依赖。**不打架，因为它们写的是 State 里不同的字段**——column 写 `retrieved_columns`、value 写 `retrieved_values`、metric 写 `retrieved_metrics`。各写各的，自然不冲突。这是并行节点设计的铁律：**别写同一个 key**。”

⚠ **预案**：有学生会问“万一两个节点非要写同一个 key 呢？”——答：“LangGraph 要你定义一个 reducer（合并函数）来决定怎么合，否则会冲突。本项目刻意避开了这种情况。”（留作第6讲思考题2）

### 段落 3 · 节点 1：extract_keywords（10 min）

⏱ 0:42–0:52

🗣 **讲稿**：打开 `backend/app/agent/nodes/extract_keywords.py`：
```python
keywords = jieba.analyse.extract_tags(query, allowPOS=allow_pos)  # 只取名词/动词/形容词等
keywords = list(set(keywords + [query]))                          # 把原始query也塞进去兜底
return {"keywords": keywords}
```
要点三连：
1. **用规则（jieba）不用大模型**——分词是成熟技术，没必要用 LLM，省钱省时。
2. `allowPOS` 只留有检索意义的词性（名词、动词…），滤掉“的、了、吗”。
3. **把原始 query 也加进去**——兜底，万一分词丢了关键信息，整句还能召回。

🗣 **承上启下**：“注意这个节点**没用** Context 里的任何工具——它只靠 jieba。下一个节点就不一样了，要动用大模型和向量库。”

✍ **板书（副板，记录节点产出）**：
```
节点1 extract_keywords: query --jieba--> keywords (规则,不用LLM)
```

### 段落 4 · 节点 2-4：三路召回（重点，25 min）

⏱ 0:52–1:17

> 三路结构几乎一样，**精讲 recall_column 一路**，另两路一句话带过。

🗣 **讲稿**：打开 `backend/app/agent/nodes/recall_column.py`，分三块讲：

**第①块：从 Context 取工具**
```python
embedding_client         = runtime.context["embedding_client"]
column_qdrant_repository = runtime.context["column_qdrant_repository"]
```
🗣 **回收段落1的伏笔（讲透“为什么注入而非import”）**：
> “看，工具是从 `runtime.context` **取**的。如果改成在文件顶部 `import` 那个真实的 repository 实例，会怎样？——测试这个节点时，你就**必须连真的向量库**才能跑。而现在，我测试时可以塞一个假的（mock）repository 进 context，**不连数据库也能测节点逻辑**。这就是依赖注入的价值：**可测试、可替换**。”

**第②块：LLM 扩展关键词（两层扩词）**
```python
chain = PromptTemplate(template=load_prompt("extend_keywords_for_column_recall"),
                       input_variables=["query"]) | llm | JsonOutputParser()
result = await chain.ainvoke({"query": query})
keywords = list(set(keywords + result))     # jieba的 + LLM扩的，合并去重
```
❓提问：“第 1 个节点已经用 jieba 抽了关键字，这里为什么又用大模型再扩一遍？”
🗣答：“**为了召回率**。jieba 抽的是‘字面词’，大模型能扩出‘同义/相关词’——用户问‘营收’，模型能联想到‘销售额、金额’。两层扩词 = 尽量不漏。这就是召回阶段‘宁多勿漏’的体现。”
🗣 顺势讲 `prompt | llm | JsonOutputParser()` 这个 **LCEL 管道**：“`|` 把‘填提示词→调模型→解析输出’串成一条链，`JsonOutputParser` 保证拿到的是 Python list 而不是一坨字符串。”

**第③块：逐关键词检索 + 去重**
```python
retrieved_columns_map = {}
for keyword in keywords:
    embedding = await embedding_client.aembed_query(keyword)   # 文本→向量
    for payload in await column_qdrant_repository.search(embedding):  # 向量→相似字段
        retrieved_columns_map.setdefault(payload.id, payload)  # 按字段id去重
return {"retrieved_columns": list(retrieved_columns_map.values())}
```
🗣 **回收第5讲伏笔**：“记得第 5 讲吗？同一个字段，name/description/每个 alias 都建了 point。所以一次检索同一字段可能命中多次——这里用 `map` 按 `payload.id` **去重**，呼应上来了。”

🗣 **另两路一句话带过**：
> “`recall_value.py` 把向量库换成 ES（全文检索取值），`recall_metric.py` 换成指标向量库，**结构和这一路一模一样**。课后对照着看，会发现智能体节点高度模式化——这正是好工程的特征。”

✍ **板书（副板）**：
```
节点2-4 召回(并行):
  字段→ [LLM扩词] → embedding → Qdrant → 按id去重
  取值→ [LLM扩词] → ES全文检索
  指标→ [LLM扩词] → Qdrant
依赖来自 context (可注入mock → 可测试)
召回原则: 宁多勿漏(高recall)
```

### 段落 5 · 节点 5-7：合并与过滤（难点，15 min）

⏱ 1:17–1:32

> 时间有限，merge 讲“三件事”，filter 讲“两段式收口”。

#### 5a. merge_retrieved_info（合并，7 min）

🗣 **讲稿**：打开 `backend/app/agent/nodes/merge_retrieved_info.py`，**不逐行**，只讲它干的三件事（这是理解重点，代码细节让学生课后读）：
1. **指标→字段补全**：指标 GMV 关联了 `order_amount`，若这字段没被召回，从 meta 库补进来。
2. **取值并入字段**：把召回的取值“华东/华南”挂到 `region_name` 的 examples 上——**让大模型看到这个字段实际长什么样**。
3. **补主外键**（最关键）：
   ```python
   for table_id in table_to_columns_map.keys():
       key_columns = await meta_mysql_repository.get_key_columns_by_table_id(table_id)
       ...把没召回到的主键/外键补进来...
   ```
   ❓提问：“为什么非要补主外键？召回到的字段还不够吗？”
   🗣答：“**多表查询要 JOIN，JOIN 靠主外键**。用户问‘各地区销售’，召回了 `region_name`(地区表) 和 `order_amount`(订单表)，但这俩表怎么连起来？靠 `region_id` 这个外键。如果不补，大模型没法写 JOIN，第 7 讲的生成就会出错。”

🗣 收口：“merge 这一步，把零散的召回结果，**组装成大模型能直接用的结构化上下文**（table_infos + metric_infos）。”

#### 5b. filter_table / filter_metric（过滤，8 min）

🗣 **讲稿**：打开 `backend/app/agent/nodes/filter_table.py`：
```python
chain = ...load_prompt("filter_table_info")... | llm | JsonOutputParser()
result = await chain.ainvoke({"query": query, "table_infos": yaml.dump(...)})
# result 形如 {"fact_order":["order_amount","region_id"], "dim_region":["region_id","region_name"]}
for table_info in table_infos[:]:             # 注意 [:] 切片副本
    if table_info["name"] not in result:
        table_infos.remove(table_info)        # 整表无关→删
    else:
        for column_info in table_info["columns"][:]:
            if column_info["name"] not in result[...]:
                table_info["columns"].remove(column_info)  # 字段无关→删
```
🗣 **三个讲点**：
1. **两段式收口（钉死认知2）**：“召回求全、有噪声；过滤用大模型把无关表/字段裁掉，求准。**高召回→高精度**，这是检索增强的经典套路。”
2. **prompt 是关键**：打开 `backend/prompts/filter_table_info.prompt`，指出它严格约束模型：只能从候选选、不许新增、要保留 join 主外键、只输出 JSON。“**可控性靠 prompt 硬约束**——这个理念第 7 讲生成 SQL 时还会反复出现。”
3. **`list[:]` 的坑**：“为什么用切片副本遍历？因为**边遍历边删原列表会跳元素**。这是 Python 常见 bug，记住。”

✍ **板书（副板）**：
```
节点5 merge: 补字段+并取值+补主外键 → 结构化上下文(table_infos/metric_infos)
              (补主外键→为了能JOIN)
节点6-7 filter: LLM裁剪无关表/字段 (求"准"precision)
              prompt硬约束 + list[:]切片防跳元素
```

### 💻 上机任务 2：观察过滤前后的对比（20 min）

🗣 **引导**：merge 后和 filter 后都有 `logger.info`。让学生在日志里找出：
- `合并召回信息: 表信息-[...]` （过滤前候选）
- `过滤后的表信息: [...]` （过滤后保留）

**分步骤**：
1. 在日志里定位这两行。
2. 对比：过滤掉了哪些表/字段？保留的是不是真的“回答这个问题所必需”的？
3. 讨论：过滤是“求准”，但如果裁过头会怎样？

❓ **检查点**：“过滤前后表的数量变化是多少？被裁掉的表，确实和问题无关吗？”

### 💻 上机任务 3：改 prompt 看召回变化（25 min）

**分步骤**：
1. 打开 `backend/prompts/extend_keywords_for_column_recall.prompt`，看它怎么让模型扩词。
2. 修改它（如要求“多扩展 5 个近义词”或“只扩 1 个”），保存。
3. 重跑上机任务 1，对比召回数量和质量的变化。
4. ⚠ **预案**：改完记得改回来（或用 git 还原），别影响后续课。

🗣 **讲解**：“你刚刚做的，就是 **prompt 工程**——同一套代码，改改提示词，行为就变了。这也是为什么 prompt 文件被单独抽出来（`backend/prompts/`）而不是写死在代码里：**便于调优、便于版本管理**。”

## 六、本讲常见问题预案

| 学生可能问 | 应对 |

## 七、板书最终态

```
今天范围: 关键字 → 召回(全) → 合并 → 过滤(准) →(下讲:生成…)

四概念: State=工件(流动数据)  Context=工具(注入依赖)
        Node=工位(读state/用context/返回片段)  Edge=走向

结构:   extract → [column|value|metric 并行] → merge → [filter_table|filter_metric]
        并行不打架: 各写各的state key

节点1 jieba抽词(规则,不用LLM)+原query兜底
节点2-4 召回: LLM扩词→检索→去重; 依赖注入(可测试); 宁多勿漏

节点6-7 filter: LLM裁剪(求准) + prompt硬约束 + list[:]防跳元素
```

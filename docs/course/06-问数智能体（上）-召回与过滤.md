## 一、教学目标

1. 理解 LangGraph 的核心抽象：**State（状态）/ Context（上下文/依赖）/ Node（节点）/ Edge（边）**。
2. 看懂图的**并行 fan-out / fan-in** 结构。
3. 掌握前 8 个节点：抽取关键字、三路并行召回、合并、过滤。
4. 理解“用 LLM 做关键词扩展”和“用 LLM 做相关性过滤”两种 LLM 用法。

## 二、教学重点

- State 与 Context 的分工：State 是流动的数据，Context 是注入的依赖。
- 节点函数签名 `async def node(state, runtime)` 与“返回部分 state 字典”的合并语义。
- 召回三路并行、过滤裁剪候选。

## 三、教学难点

- 依赖通过 `runtime.context[...]` 注入而非 import（可测试性）。
- 并行节点的写入互不冲突的原因（各写各的 state key）。
- LLM 输出用 `JsonOutputParser` 解析的稳定性。

## 四、原理精讲

### 4.1 LangGraph 的四个核心概念

| 概念 | 在本项目 | 说明 |
| --- | --- | --- |
| **State** | `DataAgentState`（`backend/app/agent/state.py`） | 一个 TypedDict，承载查询、关键字、召回结果、SQL 等，**在节点间流动** |
| **Context** | `DataAgentContext`（`backend/app/agent/context.py`） | 一个 TypedDict，装各种**依赖**（repository、embedding client），运行时注入 |
| **Node** | `backend/app/agent/nodes/*.py` | 一个 async 函数，读 state、用 context 干活、返回“要更新的 state 片段” |
| **Edge** | `graph.py` 里的 `add_edge` | 节点间的连接，决定执行顺序；条件边可分支 |

**State vs Context 的分工**（关键）：
- State = **数据**：随这次查询流动、会被节点改写。
- Context = **依赖**：和具体查询无关的“工具”（数据库连接、模型客户端），由外部注入。

看 `state.py`：
```python
class DataAgentState(TypedDict):
    query: str                              # 用户查询
    keywords: list[str]                     # 抽取的关键字
    retrieved_columns: list[ColumnInfo]     # 召回的字段
    retrieved_values:  list[ValueInfo]      # 召回的取值
    retrieved_metrics: list[MetricInfo]     # 召回的指标
    table_infos:  list[TableInfoState]      # 合并后的表信息
    metric_infos: list[MetricInfoState]     # 合并后的指标信息
    date_info: DateInfoState; db_info: DBInfoState
    sql: str                                # 生成的 SQL
    error: str                              # 校验错误（驱动条件边）
```

看 `context.py`：
```python
class DataAgentContext(TypedDict):
    embedding_client: HuggingFaceEndpointEmbeddings

    value_es_repository: ValueESRepository
```

### 4.2 图的结构：并行召回（fan-out / fan-in）

看 `backend/app/agent/graph.py` 的边定义（节选）：
```python
graph_builder.add_edge(START, "extract_keywords")
graph_builder.add_edge("extract_keywords", "recall_column")    # ┐
graph_builder.add_edge("extract_keywords", "recall_value")     # ├ fan-out：一个节点扇出到三个
graph_builder.add_edge("extract_keywords", "recall_metric")    # ┘
graph_builder.add_edge("recall_column",  "merge_retrieved_info")  # ┐
graph_builder.add_edge("recall_value",   "merge_retrieved_info")  # ├ fan-in：三路汇聚
graph_builder.add_edge("recall_metric",  "merge_retrieved_info")  # ┘
graph_builder.add_edge("merge_retrieved_info", "filter_table")    # 又一次 fan-out
graph_builder.add_edge("merge_retrieved_info", "filter_metric")
```

`extract_keywords` 后**同时**触发三个召回节点（并行），三者都完成后才进入 `merge_retrieved_info`（汇聚）。**并行的前提**：三个节点写的是不同的 state key（`retrieved_columns`/`retrieved_values`/`retrieved_metrics`），互不冲突。

### 4.3 节点 1：extract_keywords（jieba 分词）

`backend/app/agent/nodes/extract_keywords.py`：
```python
async def extract_keywords(state, runtime):
    writer = runtime.stream_writer
    writer({"type": "progress", "step": "抽取关键字", "status": "running"})
    keywords = jieba.analyse.extract_tags(state["query"], allowPOS=allow_pos)  # 只取指定词性
    keywords = list(set(keywords + [state["query"]]))                          # 加上原始 query 兜底
    writer({"type": "progress", "step": "抽取关键字", "status": "success"})
    return {"keywords": keywords}     # 只返回要更新的字段
```

要点：用 `allowPOS` 限定名词/动词/形容词等有意义的词性；把原始 query 也放进去做兜底；**返回 dict 片段**，LangGraph 自动合并进 state。

### 4.4 节点 2-4：三路召回（含 LLM 关键词扩展）

以字段召回 `recall_column.py` 为例：
```python
async def recall_column(state, runtime):
    writer = runtime.stream_writer
    writer({"type": "progress", "step": "召回字段", "status": "running"})
    embedding_client          = runtime.context["embedding_client"]            # ← 依赖从 context 取
    column_qdrant_repository  = runtime.context["column_qdrant_repository"]
    # 1) 用 LLM 扩展关键词（提高召回）
    chain = PromptTemplate(template=load_prompt("extend_keywords_for_column_recall"),
                           input_variables=["query"]) | llm | JsonOutputParser()
    result = await chain.ainvoke({"query": state["query"]})
    keywords = list(set(state["keywords"] + result))
    # 2) 逐关键词向量化 + Qdrant 检索 + 去重
    retrieved_columns_map = {}
    for keyword in keywords:
        embedding = await embedding_client.aembed_query(keyword)
        for payload in await column_qdrant_repository.search(embedding):
            retrieved_columns_map.setdefault(payload.id, payload)              # 按 id 去重
    writer({"type": "progress", "step": "召回字段", "status": "success"})
    return {"retrieved_columns": list(retrieved_columns_map.values())}
```

精读要点：
- **两层关键词扩展**：jieba 已抽一批，这里再用 LLM 扩一批（同义词/相关词），合并去重——尽量提高召回率。
- 依赖全部来自 `runtime.context`，**不在节点里 import 具体实例**——这让节点可在测试中注入 mock。
- `retrieved_columns_map` 按字段 id 去重（呼应第 5 讲：同一字段有多个 point，会被多次命中）。
- `取值召回 recall_value.py`、`指标召回 recall_metric.py` 结构几乎一致，只是换了 repository 和 prompt。

`extract_keywords` 用规则（jieba），召回里用 LLM 扩展——**规则 + 模型结合**，各取所长。

### 4.5 节点 5：merge_retrieved_info（合并与补全）

`merge_retrieved_info.py` 是前半段最复杂的节点，干三件事：

1. **指标→字段补全**：指标的 `relevant_columns` 若没被召回，从 meta 库补进来。
2. **取值并入字段**：把召回的取值挂到对应字段的 `examples` 上（让大模型看到“地区有华东/华南”）。
3. **补主外键**：每张表显式补上主键/外键字段——否则大模型没法写 `JOIN`。

```python
# 显式补齐主外键（否则多表 join 缺键）
for table_id in table_to_columns_map.keys():
    key_columns = await meta_mysql_repository.get_key_columns_by_table_id(table_id)
    column_ids = [c.id for c in table_to_columns_map[table_id]]
    for key_column in key_columns:
        if key_column.id not in column_ids:
            table_to_columns_map[table_id].append(key_column)
```

最终把召回的零散信息，组装成结构化的 `table_infos`（表→字段树）和 `metric_infos`，写回 state。**这一步把“检索结果”翻译成“大模型能直接用的上下文”。**

### 4.6 节点 6-7：filter_table / filter_metric（LLM 相关性过滤）

召回偏向“宁多勿漏”（高召回），但候选里有噪声。过滤节点用 LLM 把无关的表/字段裁掉（提精度）。看 `filter_table.py`：
```python
chain = PromptTemplate(template=load_prompt("filter_table_info"),
                       input_variables=["query", "table_infos"]) | llm | JsonOutputParser()
result = await chain.ainvoke({"query": query,
                              "table_infos": yaml.dump(table_infos, allow_unicode=True, sort_keys=False)})
# result 形如 {"fact_order":["order_amount","region_id"], "dim_region":["region_id","region_name"]}
for table_info in table_infos[:]:                 # 用切片副本遍历，边遍历边删
    if table_info["name"] not in result:
        table_infos.remove(table_info)            # 整张表无关 → 删表
    else:
        for column_info in table_info["columns"][:]:
            if column_info["name"] not in result[table_info["name"]]:
                table_info["columns"].remove(column_info)  # 字段无关 → 删字段
```

精读要点：
- prompt（`backend/prompts/filter_table_info.prompt`）严格约束 LLM：只能从候选里选、不能新增、要保留 join 主外键、只输出 JSON。
- 用 `list[:]` 切片副本遍历，避免“边遍历边删原列表”的坑。
- 这是“**召回高 recall → 过滤提 precision**”的经典两段式检索增强。

### 4.7 进度流式输出协议

每个节点开头/结尾都 `writer({"type":"progress","step":..., "status":"running"/"success"/"error"})`。这是和前端约定的 SSE 协议（第 8 讲详讲），让用户实时看到“进行到哪一步”。

## 六、常见坑

- 并行节点若误写了同一个 state key，会互相覆盖——本项目靠“各写各 key”避免。
- LLM 返回非合法 JSON 时 `JsonOutputParser` 会报错；prompt 里必须强约束“只输出 JSON”。
- 过滤过狠（把必需表裁掉）会导致后续生成 SQL 失败——这是 precision/recall 的权衡。

## 七、扩展练习

### 基础级
1. 给 `DataAgentState` 加一个字段（如 `keywords_expanded`），在召回节点里把 LLM 扩展出的关键词单独存进去，便于调试。
2. 统计一次查询中，三路召回各自的耗时（在节点里加计时日志），分析瓶颈在哪。

### 进阶级
3. 召回目前是“关键词逐个检索”。改造成**批量向量化**（一次 `aembed_documents` 多个关键词）减少请求次数，对比性能。
4. 过滤节点完全信任 LLM。设计一个“安全网”：如果 LLM 把所有表都裁掉了（result 为空），回退到“保留召回的全部表”，避免空候选。

### 挑战级（指向课程设计）
5. **新增一路召回**：当前只有 列/值/指标 三路。增加一路“**表级语义召回**”（直接用表的 name+description 建向量索引并召回），并接进图的 fan-out/fan-in。需要改：知识库构建（建表向量索引）、新增 repository、新节点、graph 连边。
6. **多轮对话方向预研**：当前 State 只有单轮 `query`。设计一个支持“上下文追问”的 State 扩展方案（如加 `history`），并说明召回/生成节点要如何利用历史。为第 9 讲多轮对话大作业铺垫。

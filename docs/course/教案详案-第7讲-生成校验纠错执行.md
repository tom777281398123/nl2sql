# 教案详案 · 第 7 讲：问数智能体（下）——生成-校验-纠错-执行

> 教师授课用逐段细案，配合 `07-问数智能体（下）-生成校验纠错执行.md`（学生教案）使用。
> 体例同前：⏱ 时间 / 🗣 讲稿 / ✍ 板书 / ❓ 提问 / 💻 上机 / ⚠ 预案。

---

## 一、本讲定位与教学法说明

- **性质**：全项目的“精华收口”一讲。大模型在这里真正写出 SQL，而且系统能**自我纠错**。
- **核心矛盾**：学生会觉得“生成 SQL = 调一次大模型，结束”。本讲要让他们看到：**生成只是开始，校验和纠错才是‘可控性’的灵魂**；并第一次理解 LangGraph 的**条件边（控制流由数据驱动）**。
- **三个必须钉死的认知**：
  1. **可控性不靠模型自觉，靠 prompt 硬约束 + 下游校验**。
  2. **条件边 = 控制流由 state 决定**（`error` 字段决定走执行还是纠错）。
  3. **EXPLAIN 校验：不动数据就能查错**（能查语法/对象错，查不出业务逻辑错）。
- **教学法**：顺着“校验→分支”这条主线讲，把条件边作为高潮。**结构先行、分支收尾、上机造错验证**。
- **总时长**：4 学时（理论约 90 分钟 + 上机约 90 分钟）。

### 段落 1 · 后半段整体结构（12 min）

⏱ 0:08–0:20

🗣 **讲稿**：打开 `backend/app/agent/graph.py`，看后半段连线，**先让学生发现“这条边和前面不一样”**：
```python
add_edge("add_extra_context", "generate_sql")
add_edge("generate_sql", "validate_sql")
add_conditional_edges("validate_sql",                                  # ← 注意：不是 add_edge！
    lambda state: "execute_sql" if state["error"] is None else "correct_sql",
    {"execute_sql": "execute_sql", "correct_sql": "correct_sql"})
add_edge("correct_sql", "execute_sql")
add_edge("execute_sql", END)
```

❓ **引导发现**：“前 7 个节点的边都是 `add_edge(A, B)`——A 完了一定去 B。这里 `validate_sql` 后面是 `add_conditional_edges`——它**会根据情况走不同的路**。这就是条件边，我们段落 4 详讲。先把整张图看完整。”

✍ **板书（画完整后半段状态机）**：
```
add_extra_context → generate_sql → validate_sql
                                        │
                       error is None? ──┤
                        是↓             否↓
                    execute_sql ←── correct_sql
                        │
                       END
```

🗣 定调：“今天就沿着这张图，从左到右一个节点一个节点走，重点停在 `validate_sql` 那个岔路口。”

### 段落 2 · 节点 8：add_extra_context（12 min）

⏱ 0:20–0:32

🗣 **讲稿**：打开 `backend/app/agent/nodes/add_extra_context.py`：
```python
today = datetime.today()
date_info = DateInfoState(date=today.strftime("%Y-%m-%d"),
                          weekday=today.strftime("%A"),
                          quarter=f"Q{(today.month - 1)//3 + 1}")
db_info = await dw_mysql_repository.get_db_info()    # select version() + dialect
return {"date_info": date_info, "db_info": db_info}
```

❓ **提问（制造认知冲突）**：“用户问‘统计**去年**各地区销售’。大模型怎么知道‘去年’是哪一年？”
🗣 **答**：“它不知道——除非你告诉它‘今天是哪天’。这就是 `date_info` 的作用。同理，‘上季度’要靠 `quarter` 算。**时间是相对的，必须注入绝对锚点。**”

🗣 **db_info 的作用**：“`get_db_info()` 查出数据库方言（MySQL）和版本。为什么要这个？——不同数据库 SQL 语法不同（分页、日期函数）。告诉大模型‘你在给 MySQL 8 写 SQL’，它才不会用 Oracle 的语法。”

✍ **板书（副板）**：
```
节点8 add_extra_context:
  date_info(今天/星期/季度) ← "去年""上季度"需要绝对时间锚点
  db_info(方言/版本)        ← 决定SQL语法
```

⚠ **预案**：有学生问“为什么不让大模型自己用 NOW()？”——答：“可以，但把日期算好喂进去，对‘去年/上季度’这类相对时间更稳，也便于调试看上下文。”

### 段落 3 · 节点 9：generate_sql + prompt 硬约束（重点，22 min）

⏱ 0:32–0:54

> 本段是“可控性”理念的集中体现，务必讲透 prompt。

🗣 **讲稿**：打开 `backend/app/agent/nodes/generate_sql.py`，分两块。

**第①块：上下文拼装**
```python
chain = ...load_prompt("generate_sql")... | llm | StrOutputParser()
result = await chain.ainvoke({
    "query": query,
    "table_infos":  yaml.dump(table_infos,  allow_unicode=True, sort_keys=False),  # 过滤后的精简表
    "metric_infos": yaml.dump(metric_infos, ...),
    "date_info":    yaml.dump(date_info, ...),
    "db_info":      yaml.dump(db_info,   ...),
})
return {"sql": result}
```
🗣 三个讲点：
1. **喂的是“过滤后”的精简上下文**——回收第 6 讲：召回求全、过滤求准，到这里喂给大模型的已经是“又准又少”的。呼应第 1 讲“喂对喂准喂少”。
2. **`yaml.dump(allow_unicode=True)`**：“为什么转成 YAML 而不是 JSON 喂给模型？YAML 更省 token、中文不转义、层次清楚。”
3. **`StrOutputParser`**：“SQL 是纯文本，不是 JSON，所以用 Str 解析器，不是上节课的 Json 解析器。”

**第②块：prompt 硬约束（钉死认知1）**
🗣 打开 `backend/prompts/generate_sql.prompt`，**逐条念“任务要求”并解释它防的是什么**：
```
1. 只能用真实存在的表与字段，禁止编造        → 防幻觉
2. 有指标定义必须严格遵循其业务口径          → 口径一致(防"销售额含不含退款"那种错)
3. 只能查询,不能写入/更新/删除               → 安全
4. 语法必须符合指定的数据库类型与版本         → 方言(配合db_info)
5. 默认只生成一条SQL                         → 可执行
6. 仅输出纯文本SQL,禁止Markdown代码块         → 可解析(否则```sql```会让执行失败)
```

✍ **板书（重点框起来）**：
```
┌──────────────────────────────────────────┐
│ 可控性不靠模型"自觉",                       │
│ 靠 prompt硬约束 + 下游校验。                │
└──────────────────────────────────────────┘
generate_sql: 精简上下文(YAML) → LLM → 纯文本SQL
prompt 6条约束 = 防幻觉/口径/安全/方言/单条/可解析
```

❓ **提问**：“第 6 条‘禁止 Markdown 代码块’——如果不约束，大模型很爱输出 ```​```sql ... ```​```，会发生什么？”（答：执行时把 ``` 也当 SQL，语法错。这是真实高频坑。）

### 段落 4 · 节点 10 + 条件边：validate_sql（高潮难点，20 min）

⏱ 0:54–1:14

> 本讲最重要的 20 分钟。把“校验”和“条件边”作为一个整体讲。

#### 4a. validate_sql 怎么校验（8 min）

🗣 **讲稿**：打开 `backend/app/agent/nodes/validate_sql.py`：
```python
try:
    await dw_mysql_repository.validate_sql(state["sql"])   # 内部: execute("explain {sql}")
    return {"error": None}                                 # 通过
except Exception as e:
    return {"error": str(e)}                               # 失败,记下错误,不抛出
```
打开 `dw_mysql_repository.validate_sql` 看一眼：就是执行 `EXPLAIN {sql}`。

🗣 **讲透 EXPLAIN（钉死认知3）**：
> “为什么用 `EXPLAIN` 而不真跑一遍？`EXPLAIN` 让数据库**只做解析和查询规划，不真正取数据**。好处：不动数据、开销小、还能查出语法错、表/字段不存在等问题。”
❓提问：“`EXPLAIN` 能查出‘本该 SUM 金额却写成了 COUNT’这种错吗？”
🗣答：“**查不出**——那是逻辑/口径错，语法完全合法。EXPLAIN 只管‘能不能跑’，不管‘跑得对不对’。逻辑错要靠结果验证或评测来抓（第 9 讲评测大作业）。”

🗣 **最关键的一句**：“注意校验失败**没有抛异常**，而是把错误信息写进 `state['error']`。为什么不抛？——因为它要把这个错误**交给下一步的‘岔路口’去决策**。”

#### 4b. 条件边：控制流由数据驱动（12 min，高潮）

🗣 **讲稿**：回到 `graph.py` 的 `add_conditional_edges`，**慢讲**：
```python
add_conditional_edges(
    "validate_sql",
    lambda state: "execute_sql" if state["error"] is None else "correct_sql",  # 路由函数
    {"execute_sql": "execute_sql", "correct_sql": "correct_sql"})              # 名称→节点 映射
```
拆三部分：
1. **从哪个节点出发**：`validate_sql`。
2. **路由函数**：读 `state["error"]`——为 None（校验通过）返回 `"execute_sql"`；非空（有错）返回 `"correct_sql"`。
3. **映射**：把返回的名字对应到真实节点。

✍ **板书（钉死认知2，画"数据决定走向"）**：
```
        validate_sql 产出 state["error"]
                    │
         路由函数读 error:
   error is None ─→ "execute_sql"   (校验通过,直接执行)
   error 非空    ─→ "correct_sql"   (有错,先纠错)

⇒ 控制流由 STATE 决定,不是写死的!
  这就是"条件边" = 状态驱动的分支
```

🗣 **拔高（点出本质）**：
> “前 9 个节点是‘直路’——A 完一定去 B。这里第一次出现‘岔路’，而**走哪条岔路，取决于运行时 state 里的数据**。这就是状态机/工作流引擎的精髓：**控制流是数据驱动的**。你们以后做任何 Agent、任何流程编排，都会反复用到这个思想。”

⚠ **预案**：学生常问“纠错完还会再校验吗？”——答：“**本项目纠错后直接执行，不二次校验**（看 `add_edge('correct_sql','execute_sql')`）。也就是只给一次改错机会。这是个可以改进的点——把它改成‘循环纠错直到通过或达上限’，正是第 7 讲的进阶练习。”

### 段落 5 · 节点 11-12：correct_sql / execute_sql（12 min）

⏱ 1:14–1:26

#### 5a. correct_sql（6 min）

🗣 **讲稿**：打开 `backend/app/agent/nodes/correct_sql.py`，重点看喂给模型的是什么：
```python
result = await chain.ainvoke({
    "query": query, "table_infos": ..., "metric_infos": ..., "date_info": ..., "db_info": ...,
    "sql": sql,        # ← 出错的那条SQL
    "error": error,    # ← validate_sql 捕获的错误信息
})
return {"sql": result}  # 覆盖 state 里的 sql
```
❓提问：“纠错时除了原来的上下文，还多喂了什么？为什么这能提高改对的概率？”
🗣答：“多喂了**出错的 SQL + 具体错误信息**。这就像你改 bug——**有报错信息时改得又快又准，没有时只能瞎试**。让大模型‘看着错误改作业’，比从头重写更可能对。”

#### 5b. execute_sql（6 min）

🗣 **讲稿**：打开 `backend/app/agent/nodes/execute_sql.py`：
```python
result = await dw_mysql_repository.execute_sql(state["sql"])   # 真正在 dw 库执行
writer({"type": "progress", "step": "执行SQL", "status": "success"})
writer({"type": "result", "data": result})                    # 用 result 事件推数据
```
🗣 两个讲点：
1. **结果转 list[dict]**：看 `dw_mysql_repository.execute_sql`——`[dict(row) for row in result.mappings().fetchall()]`，方便 JSON 序列化推给前端。
2. **它只 writer 不 return**：
   ❓提问：“其他节点都 `return {...}`，为什么 execute_sql 不返回？”
   🗣答：“它是**终点节点**（下一步就是 END）。结果通过**流式事件**(`type:result`)直接推给前端，不需要写回 state 给下游用——因为没有下游了。”

🗣 收口到编译：“`graph = graph_builder.compile()` 把这张图编译成可执行对象。运行时 `graph.astream(..., stream_mode='custom')` 配合每个节点的 `writer`，就实现了我们一路看到的流式进度。这套流怎么变成前端能收的 SSE，是下一讲的事。”

✍ **板书（副板）**：
```
节点11 correct_sql: 喂[原SQL+错误信息]→LLM重写 (像看报错改bug)
节点12 execute_sql: dw库执行→转list[dict]→writer推result
                    (终点节点,只writer不return)
```

### 💻 上机任务 2：造错，触发纠错分支（35 min，核心）

> 目标：让学生**亲眼看到条件边走了“否”那条路**。

🗣 **引导**：提供两种造错方式，任选：

**方式 A（改 prompt 让它写错）**：临时编辑 `backend/prompts/generate_sql.prompt`，删掉“只能用真实存在的字段”那条约束，并加一句诱导“可以使用你认为合理的字段名”，让模型更可能编字段。重跑，看是否触发纠错。

**方式 B（直接验证校验逻辑）**：写个小脚本调用 `dw_mysql_repository.validate_sql("select foo from bar")`，观察它抛出的错误信息——理解 `error` 字段是怎么来的。

**分步骤（以 A 为例）**：
1. 备份并修改 prompt。
2. 重跑整图，在日志里找 `校正SQL` 步骤：
   ```sh
   grep -E "校正SQL|SQL验证失败|校正后的SQL" logs/app_$(date +%Y%m%d).log | tail
   ```
3. 确认看到：验证失败 → 校正 → 校正后的新 SQL → 执行成功。
4. ⚠ **务必还原 prompt**（`git checkout backend/prompts/generate_sql.prompt`），否则影响后续。

❓ **检查点**：“纠错时大模型收到的‘错误信息’长什么样？它根据这个信息把 SQL 的哪里改了？”

## 六、本讲常见问题预案

| 学生可能问 | 应对 |
| --- | --- |
| 为什么用 EXPLAIN 不直接跑 | 不动数据、开销小、能查语法/对象错；逻辑错查不出 |
| 校验失败为什么不抛异常 | 要把 error 写进 state,交给条件边决策,而非中断 |
| 纠错后还会再校验吗 | 不会,只一次→进阶练习改成循环 |
| 大模型输出带```sql```怎么办 | prompt第6条约束;仍出现可在生成后清洗 |
| execute_sql 为什么不 return | 终点节点,结果走流式事件,无下游需要state |
| 条件边和普通边区别 | 普通边固定走向;条件边由路由函数读state决定走向 |

## 七、板书最终态

```
今天范围: 补上下文 → 生成 → 校验 ─对→执行 / ─错→纠错→执行
```

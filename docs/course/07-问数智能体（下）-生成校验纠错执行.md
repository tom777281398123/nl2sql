## 四、原理精讲

### 4.1 后半段的整体结构

```
add_extra_context → generate_sql → validate_sql ──(error is None)──→ execute_sql → END
                                        │                               ▲
                                        └──(error 非空)──→ correct_sql ──┘
```

`validate_sql` 后是一个**条件边**：校验通过直接执行，校验失败先纠错再执行。这就是系统“可控性”的核心闭环。

### 4.2 节点 8：add_extra_context（补充上下文）

`backend/app/agent/nodes/add_extra_context.py`：
```python
async def add_extra_context(state, runtime):
    dw_mysql_repository = runtime.context["dw_mysql_repository"]
    today = datetime.today()
    date_info = DateInfoState(date=today.strftime("%Y-%m-%d"),
                              weekday=today.strftime("%A"),
                              quarter=f"Q{(today.month - 1)//3 + 1}")
    db_info = await dw_mysql_repository.get_db_info()        # 数据库方言+版本
    return {"date_info": date_info, "db_info": db_info}
```

为什么需要这一步？
- **日期信息**：用户问“今年”“上季度”，大模型需要知道“今天是哪天、现在第几季度”才能算出时间范围。
- **数据库信息**：方言（MySQL）和版本决定 SQL 语法（函数名、分页写法）。`get_db_info()` 执行 `select version()` 并取 dialect（`backend/app/repositories/mysql/dw/dw_mysql_repository.py`）。

### 4.3 节点 9：generate_sql（生成）

`generate_sql.py`：
```python
chain = PromptTemplate(template=load_prompt("generate_sql"),
                       input_variables=["query","table_infos","metric_infos","date_info","db_info"]) | llm | StrOutputParser()
result = await chain.ainvoke({
    "query": query,
    "table_infos":  yaml.dump(table_infos,  allow_unicode=True, sort_keys=False),  # 过滤后的表
    "metric_infos": yaml.dump(metric_infos, allow_unicode=True, sort_keys=False),  # 指标口径
    "date_info":    yaml.dump(date_info, ...),
    "db_info":      yaml.dump(db_info,   ...),
})
return {"sql": result}
```

精读要点：
- 输入是**过滤后的精简上下文**（第 6 讲的成果）——喂得准、喂得少。
- 用 `yaml.dump(..., allow_unicode=True)` 把结构化信息转成可读文本喂给大模型（YAML 比 JSON 更省 token、更易读）。
- 用 `StrOutputParser`（SQL 是纯文本，不是 JSON）。

prompt（`backend/prompts/generate_sql.prompt`）里把“可控性”写死成硬约束：
```
1. 仅允许使用数据表信息中真实存在的表与字段，禁止编造。      ← 防幻觉
2. 若有指标定义，必须严格遵循其业务口径。                  ← 口径一致
3. 只能查询，不能写入/更新/删除。                          ← 安全
4. 语法必须符合数据库环境指定的类型与版本。                ← 方言
5. 默认只生成一条 SQL。                                    ← 可执行
6. 仅输出纯文本 SQL，禁止 Markdown 代码块。                ← 可解析
```

> **关键认知**：可控性不是靠模型“自觉”，而是靠 prompt 硬约束 + 下游校验。这是 LLM 应用工程的精髓。

### 4.4 节点 10：validate_sql（校验）——条件边的驱动者

`validate_sql.py`：
```python
async def validate_sql(state, runtime):
    dw_mysql_repository = runtime.context["dw_mysql_repository"]
    try:
        await dw_mysql_repository.validate_sql(state["sql"])   # 内部执行 EXPLAIN <sql>
        return {"error": None}                                 # 校验通过
    except Exception as e:
        return {"error": str(e)}                               # 校验失败，记录错误信息
```

校验用 `EXPLAIN`（`dw_mysql_repository.validate_sql` 执行 `explain {sql}`）：
- `EXPLAIN` 只解析和规划，**不真正执行**，能在不动数据的前提下发现语法错误、表/字段不存在等问题。
- 关键：**校验失败不抛异常中断，而是把错误信息写进 `state["error"]`**——交给条件边决策。

### 4.5 条件边：状态驱动的分支

`graph.py`：
```python
graph_builder.add_conditional_edges(
    "validate_sql",
    lambda state: "execute_sql" if state["error"] is None else "correct_sql",   # 路由函数
    {"execute_sql": "execute_sql", "correct_sql": "correct_sql"})               # 映射
graph_builder.add_edge("correct_sql", "execute_sql")
```

精读要点：
- 路由函数读 `state["error"]`：为 None → 去执行；非空 → 去纠错。
- 这就是“**控制流由数据状态驱动**”——graph 的走向取决于运行时的 state，而非写死。
- 纠错后无条件进入执行（`correct_sql → execute_sql`）。

> 注意：本项目纠错是“一次性”的（纠错后直接执行，不再二次校验）。扩展练习会让你把它改成“循环纠错直到通过或达上限”。

### 4.6 节点 11：correct_sql（纠错）

`correct_sql.py`：把**原 SQL + 错误信息 + 全部上下文**一起喂回大模型重写：
```python
result = await chain.ainvoke({
    "query": query, "table_infos": ..., "metric_infos": ..., "date_info": ..., "db_info": ...,
    "sql": sql,          # 出错的 SQL
    "error": error,      # validate_sql 捕获的错误
})
return {"sql": result}   # 覆盖 state 里的 sql
```

让大模型“看着错误改作业”，比从头重写更可能改对。

### 4.7 节点 12：execute_sql（执行 + 回传结果）

`execute_sql.py`：
```python
async def execute_sql(state, runtime):
    dw_mysql_repository = runtime.context["dw_mysql_repository"]
    result = await dw_mysql_repository.execute_sql(state["sql"])     # 真正在 dw 库执行
    writer({"type": "progress", "step": "执行SQL", "status": "success"})
    writer({"type": "result", "data": result})                      # ← 用 result 类型推送数据
```

`dw_mysql_repository.execute_sql` 把结果行转成 `list[dict]`（`[dict(row) for row in result.mappings().fetchall()]`），便于 JSON 序列化推给前端。注意它**只 `writer` 不 `return`**——结果通过流式事件出去，不需要写回 state。

### 4.8 graph 的编译与运行

`graph.py` 末尾：
```python
graph = graph_builder.compile()
```
编译成可执行图。运行用 `graph.astream(input=state, context=context, stream_mode="custom")`——`stream_mode="custom"` 配合节点里的 `stream_writer`，实现自定义事件流（第 8 讲会看到 service 如何转发为 SSE）。

## 六、常见坑

- 生成的 SQL 带了 Markdown ```` ```sql ````，导致执行失败——靠 prompt 第 6 条约束避免；若仍出现可在 generate 后加清洗。
- 纠错只做一次，若大模型一次没改对，仍会执行失败——见扩展练习的“循环纠错”。
- `execute_sql` 直接执行大模型生成的 SQL，存在安全风险（虽 prompt 约束只读，但不够）——见扩展练习“安全护栏”。

## 七、扩展练习

### 基础级
1. 在 `validate_sql` 失败时，把 `error` 也通过 `writer` 推一条更友好的提示给前端。
2. 给 `add_extra_context` 增加“上一年/本月起止日期”等更多时间信息，看是否提升时间类问题的准确率。

### 进阶级
3. **循环纠错**：把“校验→纠错→执行”改成“校验→纠错→再校验”，最多重试 N 次，N 次仍失败则返回错误。需要改条件边逻辑和 state（加重试计数）。
4. 给 `generate_sql` 加 few-shot 示例（在 prompt 里放 2–3 个“问题→SQL”样例），观察对复杂问题的提升。

### 挑战级（指向课程设计）
5. **SQL 安全护栏方向**：实现一个独立的“安全校验节点”，在执行前用 SQL 解析（如 `sqlglot`）确保：只含 SELECT、无多语句、无危险函数，并强制加 `LIMIT`/超时。把它接进图，拦截危险 SQL。这是第 9 讲“SQL 安全”大作业的核心。
6. **自洽/多候选**：让 `generate_sql` 一次生成 3 条候选 SQL，分别校验，选第一条通过的执行（或投票）。对比单条生成的稳定性提升。

## 八、思考题

1. 为什么 `validate_sql` 用 `EXPLAIN` 而不是真正执行一遍来校验？`EXPLAIN` 能发现哪些错误、发现不了哪些错误？
2. 条件边的“路由函数”读的是 state。如果一个节点忘了设置 `error`（既不是 None 也没赋值），会发生什么？如何防御？
3. 纠错节点把“错误信息”喂回大模型。为什么给出错误信息能提高改对的概率？这与人改 bug 的过程有何相似？
4. `execute_sql` 只 `writer` 不 `return`，而其他节点都 `return` 一个 dict。为什么它可以不返回？（提示：它是终点节点，结果走流式而非 state）

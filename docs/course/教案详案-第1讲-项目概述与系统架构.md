> 包含：课时分配、讲稿要点（怎么讲）、板书设计、提问设计、上机分步、时间提示、易错点预案。
> 体例：⏱ 时间 / 🗣 讲稿 / ✍ 板书 / ❓ 提问 / 💻 上机 / ⚠ 预案。

---

## 一、本讲定位与教学法说明

- **性质**：导论课。不写代码，目标是建立“为什么这么设计”的心智模型——这是后续 8 讲能否学懂的地基。
- **核心矛盾**：学生大四、有数仓/SQL 基础，容易觉得“NL2SQL 不就是让大模型写 SQL 吗”。本讲要打破这个天真认知，引出“知识库 + 召回 + 校验”的必要性。
- **教学法**：先抛“天真方案”→ 让学生发现它会崩 → 引出工程解法 → 跑通一次建立感性认识。**先破后立、先体验后拆解**。
- **总时长**：4 学时（理论约 90 分钟 + 上机约 90 分钟，含课间）。

## 三、逐段细案（理论部分）

### 段落 0 · 开场与课程总览（10 min）

⏱ 0:00–0:10

🗣 **讲稿要点**：
- 自我介绍 + 课程定位：这是一门**项目实训**，我们要从 0 看懂并能改造一个工业级的“自然语言问数”系统。
- 一句话点题：“**掌柜问数——问一句，出报表，人人都是数据掌柜。**”
- 设个钩子：“今天下课前，你们每个人会在自己电脑上，用中文问一句话，让它自动写 SQL 查出数仓里的结果。”
- 说明本讲不写代码，但**最重要**——它决定后面学不学得懂。

✍ **板书（主板，保留整节）**：
```
掌柜问数 = 自然语言 → SQL → 数仓结果
课程主线：看懂它 → 改造它 → 创造你的增强
今天的问题：为什么不能"直接让大模型写SQL"？
```

❓ **开场提问（暖场，举手即可）**：“在座有多少人能熟练写多表 JOIN 的 SQL？”→ 引出“会写 SQL 的人是少数，但要查数的人是多数”。

---

### 段落 1 · 问题引入：翻译鸿沟（10 min）

⏱ 0:10–0:20

🗣 **讲稿要点**：
- 企业数据躺在数仓里，但业务人员（运营、老板、销售）不会写 SQL。
- 传统链路：业务提需求 → 数据团队排期写 SQL → 出报表。**慢、堵、贵**。
- 掌柜问数要把这条链路压成一句话。
- 给学生一个画面感：老板想知道“上个月华东卖得最好的三个产品”，传统要等数据组半天，现在一句话几秒出。

✍ **板书（副板）**：
```
传统: 业务 → [等] → 数据组写SQL → [等] → 报表
掌柜: 业务 → 一句话 → 秒出
技术名词: NL2SQL（自然语言转SQL）
```

⚠ **预案**：若学生问“这不就是 ChatGPT 写 SQL 吗？”——**正好**，顺势进入段落 2，不要急着否定，让他们带着这个想法去“撞墙”。

---

### 段落 2 · 天真方案的崩溃（核心环节，20 min）

⏱ 0:20–0:40

> 本段是全讲的“引爆点”，务必讲透。采用“假设—反驳”三连。

🗣 **讲稿（带学生一起推演）**：

先把“天真方案”写在黑板上，郑重其事地：
> **天真方案**：把数仓所有建表语句拼进 prompt，让大模型直接写 SQL。

然后逐条引导学生“拆台”：

1. **“表太多放不下”**
   - ❓提问：“真实数仓有多少张表？”（引导：动辄上千张、上万字段）
   - 🗣：全塞进 prompt → 爆上下文窗口、token 费用爆炸。**放不下。**

2. **“大模型会幻觉”**
   - 🗣：它可能编造不存在的字段名；可能误解业务口径——比如“销售额”到底算不算退款、含不含税？模型不知道你公司的口径。
   - ❓提问：“如果模型把 `order_amount` 当成含退款的金额，但你们公司口径是不含退款，会发生什么？”（答案错得很隐蔽，比报错更可怕）

3. **“结果不可控”**
   - 🗣：可能生成 `DELETE`（危险）、可能语法不符合你的数据库版本、可能一次吐三条 SQL。**没法直接拿去执行。**

最后收口，写下本讲**最重要的一句话**：

✍ **板书（重点框起来）**：
```
┌────────────────────────────────────────────┐
│ 掌柜问数的准确性，不靠"更大的模型"，          │
│ 而靠"给模型喂对、喂准、喂少"的工程设计。      │
└────────────────────────────────────────────┘

三个问题 → 三招破解：
  表太多放不下   → 多路召回+过滤（只喂相关的）   [第5,6讲]
  大模型幻觉     → 元数据知识库（真实schema约束）[第4,5讲]
  结果不可控     → 校验→纠错 + prompt硬约束      [第7讲]
```

🗣 **过渡句**：“这三招，就是我们这门课接下来要一招一招拆开学的。今天先把全貌看清。”

⚠ **预案**：时间紧时，幻觉那条可只举“编造字段名”一个例子；但“喂对喂准喂少”那句板书**绝不能省**。

### 段落 3 · 数仓与星型模型对齐（15 min）

⏱ 0:40–0:55

> 大数据专业的“主场”，快讲、当复习，重点是**和本项目的具体表对齐**。

🗣 **讲稿要点**：
- 快速对齐两个概念（不展开）：**业务库(OLTP)管“干活”，数仓(OLAP)管“复盘”**。
- 本项目数仓用经典**星型模型**：中心一张事实表 `fact_order`，周围四张维度表 `dim_region/customer/product/date`。
- 维度表答“谁、什么、何时、何地”；事实表存“多少”（度量：金额、数量）+ 外键。

✍ **板书（画星型图）**：
```
        dim_date
            │
dim_region ─┼─ dim_customer
            │
       [fact_order]   ← 度量: order_amount, order_quantity
            │             外键: 各 dim 的 id
       dim_product
```

❓ **提问（连接到代码，为上机铺垫）**：“等会上机你们打开 `meta_config.yaml`，要找出：哪些是维度表、哪个是事实表、哪两个字段是‘度量’。”

🗣 **强调**：这套星型模型在 `backend/conf/meta_config.yaml` 和 `scripts/mysql/init/02-dw-schema.sql` 里，**等会上机会亲眼看到**。

### 段落 4 · 三大支柱与数据流（25 min）

⏱ 0:55–1:20

> 本段信息密度高，建议**边画边讲**，最后让学生复述。

#### 4a. 三大支柱（8 min）

🗣 **讲稿**：自底向上讲，强调“地基→中枢→门面”。

✍ **板书（分层画）**：
```
       前端(Vue:5173)
            │ SSE流式
   ┌────────▼────────┐
   │ API服务(FastAPI) │ 支柱三:服务化  [第8讲]
   └────────┬────────┘
   ┌────────▼────────┐
   │ 问数智能体(12节点)│ 支柱二:智能体  [第6,7讲]
   │ LangGraph编排     │
   └────────┬────────┘
   ┌────────▼─────────────────┐
   │ 元数据知识库              │ 支柱一:知识库  [第4,5讲]
   │ MySQL(meta)+Qdrant+ES     │
   └──────────────────────────┘
        最终SQL在 MySQL(dw) 上执行
```

🗣 **关键澄清**（务必讲，是高频混淆点）：
> “注意两个 MySQL 用途完全不同：**meta 库存‘描述数据的数据’（schema、指标），dw 库存‘真实业务数据’**。后者才是 SQL 真正查的地方。”

#### 4b. 端到端数据流（17 min）

🗣 **讲稿**：用学生上机会问的那句“**统计各地区销售排行前三的产品**”当例子，走一遍 9 步。一边说一边在星型图旁边标号。

✍ **板书（编号流程，与上机对照）**：
```
1 抽取关键字(jieba)         → [地区,销售,产品]
2 多路召回(并行):
    字段→Qdrant向量  取值→ES全文  指标→Qdrant向量
3 合并(补主外键、并取值)
4 过滤(LLM裁掉无关表/字段)
5 补上下文(日期/数据库方言)
6 生成SQL(LLM)
7 校验(EXPLAIN) ─错→ 纠错 ─→
8 执行(dw库)
9 全程SSE把进度+结果流式推前端
```

🗣 **强调流式**：“注意第 9 条——不是算完一次性返回，而是**每一步都实时推给你**，等会你会看到进度条一格一格亮。”

❓ **即时提问（检验吸收）**：“第 2 步为什么能‘并行’？”（引导：三路查不同的库、互不依赖。这题第 6 讲会深入。）

### 段落 5 · 小结与课堂提问（10 min）

⏱ 1:20–1:30

🗣 **小结三句话**：
1. NL2SQL 的难点不在“写 SQL”，在“**喂对上下文**”。
2. 三大支柱：知识库（地基）、智能体（中枢）、服务化（门面）。
3. 准确性 = 工程设计，不是模型规模。

❓ **课堂提问（点名 2–3 人，留作上机思考）**：
- “为什么校验和执行要分两个节点？”（思考题 1）
- “向量检索和全文检索各擅长什么？”（思考题 3，上机对照实验会验证）

🗣 留扣子：“这两个问题，第 5、7 讲我们用实验回答。先记在脑子里。”

## 四、上机部分细案（80 min）

⏱ 1:40–3:00（课间后）

> 上机前确认机房环境：Docker 已装、项目已拉取、`2.资料` 的模型已就位（否则 embedding 起不来）。建议教师课前用 `./run.sh start` 预热一遍。

### 💻 上机任务 1：跑通一次，建立感性认识（30 min）

**分步骤**：
1. 终端进入项目根目录。
2. 启动：
   ```sh
   ./run.sh start
   ```
   ⚠ **预案**：首次启动会拉镜像 + embedding 加载模型，**慢**（几分钟）。提前预热；或讲解 `run.sh` 时让它在后台跑。
3. 检查状态，等 5 项全绿：
   ```sh
   ./run.sh status
   ```
   ⚠ 若 embedding 不健康，多半是模型没挂载——现场对照第 2 讲 4.4（这里只需让它通过，原理下讲细说）。
4. 首次需构建知识库（若机房是干净环境）：
   ```sh
   ./run.sh build-kb
   ```
5. 浏览器开 http://127.0.0.1:5173 ，输入：
   ```
   统计一下各个地区销售排行前三的产品
   ```
6. **盯着进度条**，对照黑板上的 9 步流程，逐格确认。

🗣 **巡场引导**：让学生说出“现在进行到第几步了”，把抽象流程和屏幕现象绑定。

### 💻 上机任务 2：读懂星型模型（25 min）

**分步骤**：
1. 打开 `backend/conf/meta_config.yaml`。
2. 在纸上填表：

   | 表名 | role | 是维度还是事实 |
   | --- | --- | --- |
   | dim_region | ? | ? |
   | fact_order | ? | ? |
   | ... | | |
3. 找出 `fact_order` 里所有 `role: foreign_key` 的字段，画出它连到哪些维度表。
4. 找出两个 `role: measure` 的字段（答案：`order_quantity`、`order_amount`）。

❓ **检查点**：抽查 2 名学生画的星型图，纠正“把外键当度量”等常见错误。

### 💻 上机任务 3：用 curl 看“流”（25 min）

**分步骤**：
1. 终端执行：
   ```sh
   curl -s -N -X POST http://localhost:8000/api/query \
     -H 'Content-Type: application/json' \
     -d '{"query":"统计一下各个地区销售排行前三的产品"}'
   ```
2. 观察输出是一行行 `data: {...}`，每行对应一个节点事件。
3. 找出最后一条 `"type":"result"`，看结果数据。

🗣 **讲解**：“这就是‘流式（streaming）’——服务端边算边推。对比一下：如果是一次性返回，你会干等十几秒看不到任何反馈。这也是第 8 讲要实现的 SSE。”

❓ **延伸**：“为什么问数系统特别需要流式？”（引导：链路长、含多次大模型调用、耗时；实时反馈体验好。）

## 六、本讲常见问题预案（教师备查）

| 学生可能问 | 应对 |
| --- | --- |
| “直接用 ChatGPT 写 SQL 不行吗？” | 不急否定，引到段落 2 让其发现三个崩溃点 |
| “meta 和 dw 有啥区别？” | meta=描述数据的数据(schema/指标)，dw=真实业务数据；SQL 查的是 dw |
| “embedding 起不来” | 模型未挂载，第 2 讲详解；本讲先让它通过即可 |
| “为什么是 `fronted` 不是 `frontend`？” | 项目目录拼写如此，将错就错，提醒别打错 |
| “这套以后会不会被更强的大模型取代？” | 开放讨论，留到第 9 讲思考题 3 |

## 七、板书最终态（下课前黑板应有的样子）

```
掌柜问数 = 自然语言 → SQL → 数仓结果

【核心】准确性靠"喂对/喂准/喂少"的工程，不靠模型大小

三问 → 三招:
  放不下  → 多路召回+过滤
  幻觉    → 元数据知识库
  不可控  → 校验→纠错 + prompt约束

三大支柱: 知识库(地基) → 智能体(中枢) → 服务化(门面)
  注意: meta=描述数据  dw=真实数据

数据流 9 步: 关键字→召回→合并→过滤→上下文→生成→校验/纠错→执行→流式
```

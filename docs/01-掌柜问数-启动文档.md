# 掌柜问数 — 启动文档

> 默认所有命令均在项目根目录（含 `Makefile` 和 `pyproject.toml` 的目录）下执行；Python 命令统一使用 `uv run` 包装，无需手动 `activate`。

## 1. 启动中间件（MySQL / Elasticsearch / Qdrant / Embedding）

```sh
# 启动（首次会拉镜像，耐心等待）
make middleware

# 关闭
make down

# 查看状态 / 日志
make ps
make logs

# 清理容器与数据卷（保留 embedding 模型缓存）
make clean
```

启动成功后会监听以下端口（详见 `Makefile`）：

| 服务 | 端口 |
| --- | --- |
| MySQL | `localhost:3307` |
| Elasticsearch | `localhost:9200` |
| Kibana | `localhost:5601` |
| Qdrant HTTP | `localhost:6333` |
| Qdrant gRPC | `localhost:6334` |
| Embedding (TEI) | `localhost:8081` |

> `docker/.env.debug` 中的 `MYSQL_PORT` 控制宿主机 MySQL 映射端口；如果你的本机没有占用 `3306`，也可以改回 `3306`。

### MySQL 业务账号

- 默认业务账号为 `storekeeper / 178121`，对 `dw` 与 `meta` 两个库具有全部权限（由 `docker/.env.debug` 与 `scripts/mysql/init/01-create-databases.sql` 共同维护）。
- 后端 `backend/conf/app_config.yaml` 中的 `db_meta` / `db_dw` 默认就使用该账号；如修改密码请两处同步更新。
- 如果你之前已经启动过中间件、MySQL 数据卷里还没有 `storekeeper` 用户，请执行 `make clean && make middleware` 让初始化脚本重新跑一次（注意 `make clean` 会清空 `dw` / `meta` 数据，重新写入示例数据由 `scripts/mysql/init/*.sql` 完成）。

## 2. 启动前端

前端工程位于 `fronted/` 目录（注意拼写，是 `fronted` 不是 `frontend`）：

```sh
cd fronted

# 第一次启动需要安装依赖
npm install

# 启动 dev server（默认 http://127.0.0.1:5173）
npm run dev

# 关闭：Ctrl + C
```

## 3. 启动后端

后端入口在 `backend/main.py`，源码内部使用 `backend.app.*` 绝对导入，**必须以模块方式启动**，并在项目根目录下执行：

```sh
# 推荐：用 uv 直接运行（自动使用项目 .venv）
uv run python -m backend.main

# 等价写法（已 activate .venv 时）
python -m backend.main
```

> 不要写成 `python backend/main.py`，那样会因 `backend.app.*` 这类绝对导入找不到包而报错。

启动成功后会监听 `http://0.0.0.0:8000`，前端通过 CORS 白名单 `http://localhost:5173` / `http://127.0.0.1:5173` 调用。

## 4. 三种启动方式怎么选

上面 1~3 节是「手动分层启动」。实际开发中还有两条更省事的路径：`./run.sh` 一键起停，以及在 PyCharm 里点运行调试。三者的区别如下。

### 4.1 `run.sh` 一键起停（推荐日常使用）

`run.sh` 把中间件、后端、前端**三层一起管**，还会自动等 embedding 模型就绪、检测端口占用、记录 PID 与日志。

```sh
./run.sh start            # 一键全启：中间件 + 后端 + 前端
./run.sh stop             # 一键全停
./run.sh restart          # 重启全部
./run.sh status           # 查看各组件状态 + 端口健康检查
./run.sh logs             # 跟踪后端 + 前端日志
./run.sh build-kb         # 构建/重建元数据知识库

# 也可只操作某一层
./run.sh start backend    # 只启后端（后台进程，无调试）
./run.sh start middleware  # 只启中间件
```

特点：
- 后端以 `nohup uv run python -m backend.main &` **后台进程**方式启动，PID 写入 `.run/`，日志写入 `logs/backend.out`（前端同理写 `logs/frontend.out`）。
- `start` 会先 `make middleware`，并**等 `http://localhost:8081/health` 就绪**再起后端（embedding 本地加载需要 warmup）。
- 内置端口占用检测（`fail_if_port_busy`），避免重复启动。
- **首次使用**：起完后按提示执行一次 `./run.sh build-kb` 构建知识库（注意 `.env` 里 `SYS_ISCLEAN_CONFIG=true` 会先清空再重建，详见 CLAUDE.md）。

### 4.2 PyCharm 点击运行 / 调试（需要断点时用）

PyCharm 运行的入口是 **`debug_main.py`**（不是 `backend/main.py`）：

```python
# debug_main.py —— PyCharm 调试专用入口
import uvicorn
from backend.main import app          # 跑的是同一个 app

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8000, reload=False)
```

为什么单独有这个文件：
- 项目用 `backend.app.*` 绝对导入，命令行必须 `python -m backend.main`（module 模式）。但 **PyCharm 的 pydevd 调试器在 module 模式下常出现 uvicorn 不执行 / 断点失效**。
- `debug_main.py` 改用**普通脚本模式**运行（Run Configuration 的 Script path 指向它），既能正确 import 到 `app`，断点又稳。
- `reload=False` 是必须的：`reload=True` 会派生子进程，断点会失效。

⚠️ PyCharm 运行**只起后端这一个进程**，不管中间件和前端。所以调试前要**先把中间件拉起**（`make middleware` 或 `./run.sh start middleware`）、并确保知识库已构建，否则后端启动后查询会因连不上 MySQL/ES/Qdrant 而报 500。

### 4.3 对比速查

| 维度 | 手动分层（1~3 节） | `./run.sh start` | PyCharm 跑 `debug_main.py` |
|------|------|------|------|
| 中间件 | 自己 `make middleware` | ✅ 自动拉起 + 等就绪 | ❌ 需自己先拉起 |
| 后端 | ✅ 前台 | ✅ 后台进程（PID+日志） | ✅ 前台（IDE 控制台） |
| 前端 | 自己 `npm run dev` | ✅ 自动 install + 启动 | ❌ 不管 |
| 知识库 | 自己 build | 提示 `build-kb` | 不涉及 |
| **断点调试** | ❌ | ❌ | ✅（唯一可调试） |
| 适用场景 | 想逐层理解/排查 | 日常开发、演示 | 调后端逻辑、打断点 |

> 三种方式跑的后端是**同一个 `app`**，服务行为一致；区别只在「管的范围」和「能不能断点」。注意 `run.sh` 与 PyCharm 都占用 `8000` 端口，**不要同时启动后端**。

### 4.4 常见问题排查

**现象：`./run.sh stop` 说"前端/后端未在运行"，但 `./run.sh start` 又报"端口已被占用"。**

这通常是因为该层服务**不是 `run.sh` 启动的**（比如在 PyCharm 里手动起了前端，或从旧目录残留了进程）。`run.sh` 只认自己记录在 `.run/*.pid` 里的进程：

- `stop` 时查 PID 文件，没记录 → 报"未在运行"（但端口上其实有个"野"进程还活着）；
- `start` 时检测到端口被占 → `fail_if_port_busy` 主动中止，防止重复启动（这是它在正确工作）。

**典型来源**：项目目录搬迁后，旧路径下遗留的 `vite` / `uvicorn` 进程一直没关，仍占着 5173 / 8000。可用工作路径确认：

```sh
# 看是谁占用端口（前端 5173；后端把 5173 换成 8000）
lsof -nP -iTCP:5173 -sTCP:LISTEN
# 输出的 COMMAND/NAME 里若是旧项目路径，即为遗留进程
```

**处理**：杀掉占端口的进程，再用 `run.sh` 正常补起：

```sh
# 杀掉占用 5173 的进程（vite 会派生子进程，连父进程一起清）
kill $(lsof -nP -tiTCP:5173 -sTCP:LISTEN)

# 端口释放后，单独把该层补起来
./run.sh start frontend     # 或 ./run.sh start backend

# 最后确认整体状态全绿
./run.sh status
```

**根治建议**：
- 不要混用两种方式起**同一层**——要么全程 `run.sh`，要么 PyCharm 只调后端（`debug_main.py`），其余交给 `run.sh`。
- 项目目录搬迁后，确认旧目录无用即删除，避免以后又从旧路径启动出"幽灵进程"。

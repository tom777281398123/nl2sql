## 📊 项目架构总览

```plaintext
这是一个基于 LangGraph 的 NL2SQL（自然语言转SQL）智能问数系统，采用状态机工作流模式处理用户查询
```

### 📁 工程目录速览

```text
storekeeper-nl2sql/
├── backend/          # 后端 (FastAPI + LangGraph)，入口: backend/main.py
│   ├── app/          # 业务代码，绝对导入 backend.app.*
│   │   ├── agent/    # LangGraph 工作流：state / context / nodes / graph
│   │   ├── api/      # FastAPI 路由层
│   │   ├── clients/  # MySQL / ES / Qdrant / Embedding 客户端
│   │   ├── repositories/  # 数据访问层
│   │   ├── services/      # 应用服务
│   │   └── ...
│   └── conf/         # app_config.yaml / meta_config.yaml
├── fronted/          # 前端 (Vue3 + Vite)，注意目录名是 fronted 不是 frontend
├── docker/           # docker-compose 与数据卷
├── scripts/          # MySQL 初始化脚本
├── docs/             # 项目文档
├── Makefile          # 一键起停中间件
├── pyproject.toml    # 由 uv 管理的依赖声明
└── uv.lock           # uv 依赖锁文件
```

> 环境管理统一使用 `uv`（见 `docs/00-掌柜问数-环境配置.md`），后端必须以模块方式启动：`uv run python -m backend.main`。

### 🎯 工作流程总结

```plaintext
用户查询 
  ↓
1. 关键词抽取 (jieba)
  ↓
2. 三路并行召回 (字段/值/指标)
  ↓
3. 合并召回信息 + 补充元数据
  ↓
4. 双路并行过滤 (表/指标)
  ↓
5. 添加上下文 (日期/数据库信息)
  ↓
6. LLM生成SQL
  ↓
7. 验证SQL ──失败──> 校正SQL ──> 执行SQL
  │                    ↑
  └────成功────────────┘
  ↓
8. 执行SQL返回结果

```

### 📊节点详解 (Node Details)

```plaintext
 🔹 extract_keywords - 关键词抽取
    技术: jieba.analyse.extract_tags (默认 TF-IDF 算法) + 词性过滤
    输入: 用户查询
    输出: 关键词列表 (含原始 query 本身，便于后续整句召回)
    作用: 提取名词、动词、形容词、英文、成语等有意义的词汇，用于后续召回
    词性白名单: n / nr / ns / nt / nz / v / vn / a / an / eng / i / l
🔹 recall_column - 字段召回
    流程:
    使用LLM扩展关键词（同义词、相关词）
    对每个关键词计算embedding
    在Qdrant中向量搜索相似字段
    去重后返回ColumnInfo列表
    存储: Qdrant向量数据库
🔹 recall_value - 值召回
    作用: 从用户查询中提取具体数值或枚举值
    示例: "北京地区的销售额" → 召回"北京"这个地区值
    存储: Elasticsearch全文检索
🔹 recall_metric - 指标召回
    作用: 召回与查询相关的业务指标定义
    示例: "销售额"、"订单量"、"客单价"等
    存储: Qdrant向量数据库
🔹 merge_retrieved_info - 合并召回信息
    核心逻辑:
        将指标的相关字段补充到字段列表
        将召回的值添加到对应字段的examples
        按table_id分组字段
        自动补充主键/外键字段（保证JOIN能力）
        构建完整的TableInfo和MetricInfo结构
        依赖: MetaMySQLRepository查询元数据
🔹 filter_table - 表格过滤
    技术: LLM智能过滤
    输入: 所有召回的表信息 + 用户查询
    输出: JSON格式 {表名: [相关字段列表]}
    作用: 剔除无关表和字段，减少prompt长度
🔹 filter_metric - 指标过滤
    作用: 从召回的指标中筛选出真正相关的指标
    技术: LLM判断指标与查询的相关性
🔹 add_extra_context - 添加额外上下文
    添加内容:
    当前日期信息（年、季度、星期）
    数据库方言和版本
    其他运行时上下文
🔹 generate_sql - 生成SQL
    输入:
    用户查询
    过滤后的表信息
    过滤后的指标信息
    日期上下文
    数据库信息
    技术: LLM + Prompt模板
    输出: 可执行的SQL语句
🔹 validate_sql - 验证SQL
    方法: 使用MySQL的EXPLAIN命令验证SQL语法
    成功: 返回error=None
    失败: 返回错误信息，触发校正流程
🔹 correct_sql - 校正SQL（条件节点）
    触发条件: validate_sql返回错误时
    输入: 原始SQL + 错误信息 + 所有上下文
    输出: 修正后的SQL
    特点: 让LLM理解错误原因并修复
🔹 execute_sql - 执行SQL
    操作: 在DW数据库执行最终SQL
    输出: 查询结果集
    流式返回: 通过SSE推送给前端
```

### 1️⃣ 数据存储架构

```plaintext
┌─────────────────────────────────────────────────┐
│          元知识库构建流程 (build_meta_knowledge)   │
└─────────────────────────────────────────────────┘

MySQL Meta库 (结构化元数据)
├── table_info    ← 表定义
├── column_info   ← 字段定义 (含examples示例值)
├── metric_info   ← 指标定义
└── column_metric ← 字段-指标关联关系

Qdrant (向量索引)
├── data-agent-column   ← 字段的向量索引
│   └── 索引内容: 字段名、描述、别名
└── data-agent-metric   ← 指标的向量索引
    └── 索引内容: 指标名、描述、别名

Elasticsearch (全文索引)
└── data-agent-value    ← 字段值的全文索引
    └── 索引内容: 具体的枚举值/实例值

```
